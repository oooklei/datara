 1 方案概述 
 本方案为从零搭建数据治理工具平台提供完整的功能规划与技术选型指引。 
 设计目标 
 数据治理工具是一个 一站式数据管控平台 ，帮助企业和团队完成从数据采集、存储、处理到治理、运维的全流程管理。通俗来讲，它就像数据的"管家"： 
 
 数据从哪里来 → 数据源管理：把各种数据库、文件、API 接入进来 
 数据怎么同步 → 批量同步：自动建表、自动分区、数据量核对 
 数据存在哪里 → 数据仓库搭建：规划数据分层，让数据有序存放 
 数据怎么处理 → 批处理 + 流处理：离线跑批 + 实时计算 
 任务怎么编排 → DAG工作流：任务依赖、断点恢复、SQL多结果表依赖、参数传递 
 数据好不好 → 数据质量：自动检查 + 在线核查 + 下载修复 
 数据安不安全 → 数据安全：权限、脱敏、加密、审计 
 数据怎么管 → 元数据 + 数据标准 + 指标管理：知道有哪些数据、是什么意思、指标怎么算 
 数据怎么共享 → 数据共享服务：数据库同步、文件导出、API接口 
 系统怎么装 → 一键部署：Doris/Kafka/Flink等组件自动安装 
 系统怎么跑 → 运维监控：部署、告警、性能管理一条龙 
 国产化要求 → 信创适配：支持国产数据库、操作系统、芯片 
 
 
 什么是数据治理？ 数据治理不是某一个单一的技术，而是一整套管理数据的方法和工具。它解决的核心问题是： 数据在哪里（发现）、数据是什么（理解）、数据好不好（质量）、数据安不安全（安全）、数据怎么用（服务） 。简单说，就是让数据从"混乱"变成"有序"，从"能用"变成"好用"。

 4 数据仓库搭建与建模 
 解决"数据怎么存"的问题，含三阶段建模和规范的数据分层。 
 数仓分层架构 
 ┌──────────────────────────────────────────────────────────────┐
│ ODS 层 — 原始数据层：从数据源原样同步，不做加工 [全量/增量同步] │
├──────────────────────────────────────────────────────────────┤
│ DWD 层 — 明细数据层：清洗、标准化、维度退化后的明细事实表 [ETL清洗] │
├──────────────────────────────────────────────────────────────┤
│ DWS 层 — 汇总数据层：按主题、维度进行轻度/重度汇总聚合 [聚合/预计算]│
├──────────────────────────────┬───────────────────────────────┤
│ DIM 层 — 维度层：公共维度表 │ ADS 层 — 应用层：面向应用的宽表/指标│
├──────────────────────────────┴───────────────────────────────┤
│ TMP 临时层 — 临时表/中间结果，跑批过程中产生，跑完即清理 │
└──────────────────────────────────────────────────────────────┘ 
 
 为什么要分层？ 数据仓库就像一个工厂。 ODS 是原料仓库（直接搬进来）， DWD 是加工车间（清洗、标准化）， DWS 是半成品仓库（按类别汇总好）， ADS 是成品展厅（直接可用的数据）， DIM 是说明书库（维度信息）。分层让每一步都有迹可循。

用户/商品/订单... 事实表/维度表/明细表 一键物理化到数仓

 5 批数据处理 
 解决"数据离线怎么算"和"数据怎么同步到数仓"的问题，含ETL批处理和批量数据同步。 
 
 什么是批处理？ 批处理就是把一大堆数据"攒到一起"，在固定时间（比如每天凌晨2点）一次性处理。就像洗衣机，你不会每件衣服单独洗，而是攒一批一起洗。批处理适合 不需要实时、数据量大、需要复杂计算 的场景。 
 
 5.1 ETL批处理 
 ETL 三步流程 
 [E - Extract: 从数据源抽取数据] → [T - Transform: 清洗/转换/聚合] → [L - Load: 加载到目标数仓表] 
 核心功能 
 
 功能 说明 
 可视化ETL设计器 拖拽式流程编排，将抽取→转换→加载用可视化节点连接，无需写代码 
 SQL脚本任务 编写SQL进行数据转换、聚合、关联，支持多段SQL顺序执行和变量传递 
 脚本任务 支持 Python / Shell / Java 自定义脚本，处理SQL无法完成的复杂逻辑 
 任务调度与DAG 定时调度（Cron/依赖触发），任务间DAG依赖编排，上游完成下游才执行 
 增量/全量同步 支持全量覆盖、增量追加、CDC变更捕获（基于日志/时间戳/标记字段） 
 容错与重试 任务失败自动重试、支持断点续跑、脏数据隔离、告警通知 
 
 常用ETL转换算子 
 
 算子类型 功能 示例

 查找替换 按映射表替换值 M→男, F→女 
 表达式 自定义计算字段 profit = revenue - cost 
 去重 按主键/全字段去重 DISTINCT 去重

 5.2 批量数据同步与自动分区 
 ODS层是原始数据同步层，一般不做加工，只需要把源表数据同步到数仓。当数据源有几十上百张表时，一张张手动建表、配同步任务太麻烦，也不清楚每张表同步了多少数据。需要：批量选表 → 自动建表+自动分区 → 自动同步 → 数据量核对。 
 批量同步向导（5步完成） 
 Step 1: 选择数据源
├── 选择已注册的数据源连接
└── 测试连接 → 进入下一步

Step 2: 选择表
├── 自动扫描数据源下所有表
├── 表格展示：表名、行数、大小、字段数、最后更新时间
├── 支持搜索/筛选（按表名前缀、按行数范围）
├── 勾选要同步的表（支持全选/反选）
└── 显示已选数量：已选 25 张表

Step 3: 同步配置
├── 目标库：选择ODS层数仓（Doris/Hive/达梦等）
├── 建表策略：
│ ├── 自动建表（推荐）← 根据源表结构自动生成DDL
│ ├── 仅同步不建表（表已存在）
│ └── 建表并覆盖（危险！删除已有表重建）
├── 分区策略：
│ ├── 按天分区（推荐）← dt=2026-09-11
│ ├── 按月分区 ← dt=2026-09
│ ├── 不分区
│ └── 按字段分区 ← 选择某个日期字段作为分区字段
├── 同步模式：
│ ├── 全量同步（每次覆盖全表数据）
│ ├── 增量同步（基于时间戳/CDC）
│ └── 首次全量+后续增量（推荐）
├── 目标表名规则：ods_源库名_源表名（可自定义前缀）
└── 字段类型映射：自动映射（MySQL BIGINT → Doris BIGINT）

Step 4: 调度配置
├── 调度方式：手动执行 / 定时调度（Cron）
├── 调度周期：天/小时/自定义
├── 并发控制：同时同步几张表（默认5张并行）
├── 失败策略：自动重试N次，全部失败告警
└── 是否加入DAG工作流：是（生成一个批量同步工作流）

Step 5: 确认执行
├── 展示配置摘要
├── 预览生成的DDL（可编辑修改）
├── 点击"开始同步"
└── 进入同步进度看板 
 自动建表与分区 
 自动建表逻辑： 
 源表结构 → 字段类型映射 → 生成目标库DDL → 执行建表

示例：MySQL源表 → Doris目标表

源表DDL：
CREATE TABLE user_info (
 id BIGINT PRIMARY KEY,
 user_name VARCHAR(100),
 phone VARCHAR(20),
 create_time DATETIME,
 status INT
);

自动生成的Doris DDL：
CREATE TABLE ods_mysql_user_info (
 id BIGINT,
 user_name VARCHAR(100),
 phone VARCHAR(20),
 create_time DATETIME,
 status INT
)
PARTITION BY (dt) -- 自动加分区字段
DISTRIBUTED BY HASH(id) BUCKETS 10 -- 自动分桶
PROPERTIES("replication_num"="3"); 
 分区自动创建： 
 
 分区模式 说明 自动创建逻辑 
 按天分区 每天一个分区 每次同步时自动创建当天分区 
 按月分区 每月一个分区 每月首次同步时自动创建当月分区 
 预创建分区 提前创建未来N天分区 定时任务每天创建未来7天的分区

 6 流数据处理 
 解决"数据实时怎么算"的问题，对持续产生的数据流进行毫秒级/秒级处理。 
 
 批处理 vs 流处理： - 批处理 ：数据攒一批 → 定时处理 → 分钟/小时级延迟 → 数据量大但不要实时 - 流处理 ：数据来了就处理 → 持续不断 → 毫秒/秒级延迟 → 数据量可能不大但要求快 - 简单选择原则： 需要看"今天"的数据用批处理，需要看"此刻"的数据用流处理 
 
 流处理架构 
 [数据源] → [Kafka 消息队列缓冲] → [流处理引擎 Flink/Spark SS] → [实时数仓 Doris]
 ↓ [Redis/HBase]
 [Checkpoint] [实时大屏/告警]
 状态持久化·容错

 实时数据采集 CDC实时捕获数据库变更（基于Binlog/WAL），日志实时采集，IoT设备数据接入

 窗口计算 滚动窗口、滑动窗口、会话窗口，按时间或数量切分数据流做聚合

 9 元数据管理 
 解决"有哪些数据、是什么意思"的问题，元数据是数据的"数据"。 
 
 什么是元数据？ 元数据就是"描述数据的数据"。比如一张用户表：表名、字段名、字段类型、字段注释、表的归属业务域、谁创建的、什么时候更新的——这些都是元数据。没有元数据管理，你的数仓就像一个没有目录的图书馆，找不到书也不知道书是什么。 
 
 元数据分类 
 
 类型 内容 来源 用途 
 技术元数据 表名、字段名、类型、分区、索引、存储格式 数据库/数仓自动采集 技术定位、血缘分析 
 业务元数据 业务名称、业务描述、归属主题域、业务负责人 人工标注 业务理解、数据目录 
 管理元数据 负责人、SLA、生命周期、安全级别、访问权限 管理员配置 数据管理、运维 
 操作元数据 ETL任务、执行频率、数据量、调度依赖 调度系统采集 影响分析、运维监控 
 
 核心功能 
 
 功能 说明 
 元数据采集 自动从数据源/数仓/调度系统采集技术元数据，支持定时和触发式采集 
 元数据目录 树形/卡片浏览所有数据资产，搜索表/字段，查看详情和数据样本 
 血缘分析 追踪数据从哪来、到哪去：表级血缘 + 字段级血缘，可视化DAG图 
 影响分析 某张表/字段变更时，分析下游受影响的所有表、任务、报表 
 数据资产地图 全局数据资产可视化地图，按业务域/主题域展示数据分布 
 标签管理 为表/字段打业务标签，支持标签分类体系和标签搜索 
 
 

 
 
 10 数据标准管理 
 解决"数据应该长什么样"和"指标怎么算"的问题，含数据标准规范和 指标管理体系 。 
 
 为什么需要数据标准？ 比如"性别"字段：A系统用 M/F，B系统用 男/女，C系统用 1/0。没有统一标准，数据集成时就乱套了。 
 为什么需要指标管理？ "活跃用户数"：A按登录算，B按点击算，C按交易算。没有统一口径，同一个指标不同人算出来不一样。 
 
 10.1 数据标准 
 
 功能 说明 
 数据元标准 定义每个数据项的标准名称、英文名、类型、长度、格式、业务含义 
 代码标准 枚举值标准化：性别(M/F)、币种(CNY/USD)、状态(01/02/03)等代码字典 
 指标标准 统一定义业务指标：口径、计算公式、统计周期、归属主题域 
 命名规范 表命名规范（ods_前缀/dwd_前缀）、字段命名规范（snake_case）、任务命名规范 
 标准映射 将实际表字段映射到数据标准，检测是否合规，生成差异报告 
 标准发布 标准审批流程：起草→评审→发布→执行，版本管理

 13 DAG工作流引擎 
 支持可视化DAG编排、任务依赖、跨工作流依赖、数据血缘关联、 断点恢复+自动续跑 ，以及 SQL多结果表依赖管理 。 
 13.1 DAG工作流核心能力 
 
 功能 说明 
 可视化DAG编排 拖拽式DAG流程设计，节点间连线表示依赖，支持分支/合并/循环/条件判断 
 任务依赖管理 上游成功→下游执行；支持跨工作流依赖、跨周期依赖、外部依赖 
 数据血缘关联 每个DAG节点关联数据表，自动生成任务级+数据级血缘关系图 
 断点恢复+自动续跑 上游报错→手动修复→标记恢复→自动触发下游节点继续执行，无需重跑整个DAG 
 
 13.2 断点恢复机制 
 Step 1: 正常执行 A → B → C → D 依次执行
 ✅ ✅ ✅ ✅

Step 2: C节点报错! A → B → C → D
 ✅ ✅ ❌ ⏸️(阻塞)
 DAG暂停，等待处理

Step 3: 告警通知 邮件/钉钉/飞书/短信通知运维人员

Step 4: 人工处理 运维人员在IDE中修复SQL / 处理脏数据 / 修复依赖

Step 5: 标记恢复 点击"恢复运行"按钮
 A → B → C → D
 ✅ ✅ 🔄 ▶️(自动续跑) 
 断点恢复三种策略 
 
 策略 说明 
 从失败节点重跑（默认） 只重跑C节点，然后自动触发D节点继续执行。A和B不重跑 
 从失败节点上游重跑 重跑C及C之前的部分/全部节点，然后续跑D 
 跳过失败节点 标记C为"手动处理完成"，直接触发D节点执行 
 
 13.3 SQL多结果表依赖管理 
 用户编写SQL脚本时，一个脚本里经常包含多个INSERT语句，每条INSERT产出一张结果表。下游工作流可以精确依赖其中的某一张结果表，并选择依赖的调度周期。 
 典型场景 
 -- 一个SQL脚本产出3张表
INSERT INTO dwd_order_detail SELECT ... FROM ods_order; -- 结果表1
INSERT INTO dwd_user_summary SELECT ... FROM ods_user; -- 结果表2
INSERT INTO dwd_product_stats SELECT ... FROM ods_product; -- 结果表3 
 下游工作流B只需要依赖"结果表1"完成，不需要等结果表2和表3全部跑完。 
 SQL脚本结果表自动解析 
 
 能力 说明 
 自动解析 SQL脚本保存时，自动解析所有INSERT/CREATE语句，提取目标表名 
 结果表注册 将解析出的结果表注册为"任务产出表"，作为下游可选的依赖目标 
 手动标注 支持用户手动标注结果表（自动解析不准时兜底） 
 结果表列表展示 在任务详情页展示该任务的所有产出表列表 
 
 跨工作流表级依赖配置 
 工作流B - 节点配置
├── 依赖类型：任务依赖 / 表依赖 ← 选择"表依赖"
├── 依赖来源：工作流A / SQL任务A
├── 依赖结果表：[下拉选择] dwd_order_detail ← 精确到表
├── 依赖周期：当前调度周期 / 上一个调度周期 / 指定N个周期前
└── 等待策略：等待完成 / 跳过等待 
 依赖周期说明 
 
 周期类型 说明 场景 
 当前调度周期（T） 依赖同一调度周期内的上游产出 常规场景，T+0执行 
 上一个调度周期（T-1） 依赖昨天/上一轮的产出 日依赖周、周依赖月 
 指定N个周期前（T-N） 依赖N个周期之前的产出 月报依赖本月每天的数据 
 
 依赖检查机制 
 下游任务启动前检查：
1. 上游SQL任务是否已执行 → 否则等待
2. 上游SQL任务是否成功 → 失败则告警/阻断
3. 上游任务产出的指定结果表是否有数据 → 空则告警
4. 结果表的数据时间分区是否匹配当前依赖周期 → 不匹配则等待

 20 信创适配方案 
 信息技术应用创新（信创）要求使用国产化技术栈，替代国外产品。 
 
 什么是信创？ 信创 = 信息技术应用创新，核心要求是使用国产软硬件替代国外产品，实现自主可控。在数据治理领域，信创主要体现在：国产数据库、国产操作系统、国产芯片、国产中间件。 
 
 信创全栈适配对照表 
 
 类别 国产产品 
 国产数据库 达梦DM8 / 人大金仓KingbaseES / 南大通用GBase / 神通数据库 / OceanBase / 华为GaussDB / PingCAP TiDB 
 国产数仓/OLAP Apache Doris(国产开源) / StarRocks(国产开源) / GaussDB DWS / SelectDB 
 国产操作系统 银河麒麟V10 / 统信UOS / openEuler(华为) / 方德桌面OS 
 国产芯片 华为鲲鹏(ARM) / 飞腾(ARM) / 海光(x86) / 龙芯(MIPS) / 兆芯(x86) 
 国产中间件 东方通TongWeb / 金蝶Apusic / 宝兰德BES / 中创InfoGate 
 国产消息队列 RocketMQ(阿里巴巴开源) / Pulsar / 华为DMS 
 国产安全产品 国密SM2/SM3/SM4算法 / 国产SSL证书 / 国产VPN 
 
 信创适配策略 
 
 层次 开源方案 信创替代方案 适配难度 
 关系型数据库 MySQL / PostgreSQL 达梦DM8 / 人大金仓Kingbase 中等 
 OLAP数仓 Greenplum / Presto Doris / StarRocks / GaussDB DWS 较低 
 计算引擎 Spark / Flink Spark / Flink (原生支持国产芯片) 低 
 消息队列 Kafka RocketMQ / Pulsar 低 
 操作系统 CentOS / Ubuntu 麒麟OS / 统信UOS / openEuler 低 
 芯片 Intel x86 鲲鹏 / 飞腾 / 海光 中等 
 加密 AES / RSA 国密SM2/SM3/SM4 较高 
 
 
 信创适配建议： 采用 "双轨并行" 策略——同时支持开源技术栈和国产技术栈，通过抽象数据源适配层、SQL方言转换层，让同一套代码在不同数据库上运行。逐步替换：先数据库→再操作系统→最后芯片。
