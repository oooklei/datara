# 客户需求归并：以当前系统验证电商核心业务

来源：`D:\需求\数据治理工具\9月15日会议-需求厘清要点.txt`、`9月17日会议-需求厘清要点.txt`、`10月13日验证演示会议纪要.txt`、`核心功能注解.txt`。9 月 17 日是 9 月 15 日的补充；重复条目合并。执行边界按用户最新说明及 `docs/designs/2026-10-29-dbx-unified-target-design.md`：**电商是功能检验的业务载体，不开发新的电商业务系统；旧材料不产生当前目标之外的新功能。**

## 统一需求结构

| 能力域 | 归并后的客户需求（只表述业务目的） | 当前目标的实现归属 | 电商仿真怎么验证 |
|---|---|---|---|
| 数据开发与探索 | 能在一个 SQL IDE 浏览表、视图、过程和函数，跨库/Schema 查数、编辑 SQL、查看结果/历史、保存与导出，并利用 AI 辅助理解数据。 | **DBX 原版 IDE/AI 是主实现**；Datara 提供项目上下文、变量和 owner/共享治理。旧 Datara IDE/AI Agent 不再作为独立实现。 | 用订单、订单行、支付、退款跨 Schema 对账；验证对象树、查询、历史和导出。AI 若已配置，问“已付未发订单”和“退款率口径”，核对授权与可追溯结果。 |
| 数据接入与同步 | 能从源表或目标表出发设计数据同步；跨 Schema 同名表变化时可以发现并处理映射；批处理结果可信。 | **DBX 提供连接/schema/SQL，海豚提供 DAG/调度，Datara 提供脚本、变量和网关**。旧双导航表单与旧直连同步不是当前实现依据。 | 用订单源表→数仓明细验证当前可用的设计与运行路径。目标表反选、自动映射、动态探测若当前组合无等价操作，记录具体缺口，不能用一条手写 SQL 冒充完全实现。 |
| 编排与依赖 | 同一个 DAG 中设计、试运行、调度 SQL/Python/Shell；任务间、工作流间及文件/表/外部结果依赖可配置时间窗、周期、超时和策略。 | **海豚 DAG 与运行后台**是事实源，Datara 为宿主/网关。海豚并行线负责实现，本线仅提供业务事实和联合验收场景。 | 每日订单对账依赖支付、库存和前置日批；检查同日期/批次传播、试运行和正式运行记录。未实现的依赖类型不能由本线因仿真硬加。 |
| 变量与参数 | 工作流和节点的文本参数可选变量、校验引用、显示当前值；运行记录可追溯最终值，敏感值脱敏。 | **Datara 变量域为真源**，按当前目标设计的作用域解析并投影到海豚；DBX IDE 仅通过已接入的 Datara 桥使用变量。 | 用 `biz_date`、`batch_id`、`currency`、`source_schema` 在现有输入点预览、补全、解析；改变日期后核对订单分区，检查运行快照与脱敏。旧材料“所有文本框”理解为对已支持执行输入点的契约核对，不据此新建功能。 |
| 治理与质量 | 资产按业务域组织；身份证、手机号、统一社会信用代码三条预制规则；质量规则、任务、异常、报告、告警能说明数据是否可信；指标看板和一致性检查可核对。 | **Datara 保留 10 个治理菜单**，执行按目标设计走 DBX/编排；旧资产地图、旧数仓建模/逆向工程 UI 被 DBX schema/ER 替代。质量覆盖度、指标审核不恢复。 | 会员、商品、订单、支付、库存、退款按域整理；运行预制规则及订单支付对账，核对命中行、任务计数、报告和告警。系统/工作流/表三级报告及第三方报告 API 逐项按当前接口实测，不能因存在报告页即判全部满足。 |
| 实时与开放服务 | 外部系统可以安全地获取更新及时的业务数据；有 API-Key 授权和可观测的流处理结果。 | 当前目标保留 Datara Open API/API-Key；流处理运行归海豚。旧自研流组件和独立流开发页不恢复。 | 以订单/支付变更事件或当前可用的数据流验证端到端时效，再以第三方调用凭据验证可见范围。只有静态快照时如实记录为降级，不称实时。 |
| 脚本、资源与运行环境 | SQL/Python/Shell 脚本可上传、管理版本，在有权限的节点试运行；运行节点、SSH、监控与成功/失败数可查询。 | Datara 脚本/资源/SSH/监控，正式 DAG 执行归海豚；SQL 走 DBX。 | 对账 SQL、质量摘要 Python、文件检查 Shell 使用现有资源管理和试运行入口；检查版本、可用节点、授权和结果计数。无授权 SSH 节点时明确环境缺口，不伪造运行结果。 |
| 身份、安全与共享 | 不同用户只看到有权项目与资源；敏感信息受保护；管理员切换账号后权限完整恢复。 | **Datara 身份、项目成员权限与 DBX 连接/配置 owner 共享**是当前目标的明确要求。旧会议“安全优先级低”已被较新裁定覆盖。 | `zhangsan` 未授权时项目/监控/连接均按权限隐藏或拒绝；只共享指定连接后只增加该资源；撤销后立即失效；切回 admin 后项目及功能完整恢复。 |
| 血缘与影响分析 | 能追溯数据来自哪里、SQL 改动影响哪些下游业务结果。 | DBX schema/ER/血缘/历史承载数据探索；Datara 的**每日影响分析**读取执行历史。旧独立元数据、资产地图、血缘页不恢复。 | 订单→支付对账→净收入指标建立实际执行证据；改变订单金额字段时检查受影响结果，不把手工画线当自动影响分析。 |

## 消除旧材料之间的冲突

1. **AI**：旧《注解》写 Datara 自研 Agent + OpenMetadata/DataHub/Vanna；现目标用 DBX AI。客户“自然语言辅助数据治理”意图保留，实现归属唯一是 DBX AI；外部组件不作为新增任务。
2. **IDE**：旧材料提出增加对象编辑，现目标采用 DBX 原版。按 DBX 当前版本验证其对象能力，保留成熟 IDE；只补 Datara 明确负责的 owner、共享和变量接入。
3. **同步与流**：旧材料的独立组件/导航与新目标“DBX 数据访问 + 海豚 DAG”不同。验证客户的业务结果与交互路径，缺少的旧交互如实标差异；不恢复旧模块。
4. **元数据与数仓建模**：旧逆向工程、资产地图、采集任务与新目标 DBX schema/ER 冲突。DBX 为当前入口；Datara 治理中仍存在的业务域字段可用于检验域归类。
5. **指标与安全优先级**：旧会议将指标、权限列为低优先级；当前目标明确保留指标看板及 owner 隔离，按新裁定执行。
6. **质量**：旧会议去掉“覆盖度”及“审核”，当前目标保留 10 项治理能力。三条预制规则已经存在，但只有规则定义不等于真实行级质量运行。
7. **实施分工**：旧材料要求完整复刻海豚；本次用户明确本线只负责非海豚，海豚由并行线开发。跨线用同一电商样本做最终验证。

## 验收标注方法

每条能力在验证清单中记录：**业务事实主键 → 操作入口 → 输入/输出 → 权限身份 → 实际运行证据 → 与客户意图的差异**。结果只标“原样实现、变通实现、降级实现、超预期实现、未覆盖、待验证”之一。变通与超预期都需要业务结果证据；降级要写缺少的动作或数据；未验证不能记为实现。先盘点现有实现与数据，再补当前目标的缺口；验证临时数据按命名空间清理，保留经验证的电商仿真基线。
