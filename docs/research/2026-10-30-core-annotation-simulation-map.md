## 六条后端重构要求的落实

1. `D:\dbx-main` 用于理解原版 DBX，但其源码标为 0.6.29；当前 1.9 实例为 0.6.60，接口实现以部署同版源码和运行行为复核，再补缺；保留原版 SQL IDE。
2. 先冻结后端身份、owner、变量、执行与资源契约，再验证前端交互；现有前端可用于核对，不把其旧行为作为标准。
3. 海豚功能由并行线依据 `D:\dolphinscheduler-dev` 负责；本线只提供业务样本和跨线验收，不改其源码。
4. 变量引用按当前目标设计 §九及已实现的作用域处理；检查已有 SQL、脚本、规则、配置等接入点，先核对再补目标缺口。敏感值不进入日志、URL 或静态产物。
5. SQL IDE 后端由 DBX 提供查询和资源能力，Datara 提供变量注入与身份/owner 网关；前端以已有成熟 DBX IDE 为基础。
6. 以真实源表和必要的确定性合成数据核对**现有功能**；不为仿真新增电商业务应用或旧注解特有组件。无真实支付、物流、GTIN 回执时明确标记为合成数据。

## 已确认的逻辑差异及处理

- 旧注解要求自研 AI Agent 集成 OpenMetadata/DataHub/Vanna；新目标设计删除 Datara 自研 AI，采用 dbx AI。按较新的用户指定目标执行，仿真只检验 dbx AI 的授权与结果可追溯性。
- 旧注解提出“后端冻结后才开展前端”；目前已有前端和用户实测缺陷。先修复验证路径所需的前端映射和权限显示，但以真实后端行为决定通过与否。
- 旧注解要求完整复刻海豚；当前用户明确要求本线只做非海豚功能，海豚线并行。本线不重复开发，保留跨线业务场景作为最终联合验收输入。
- “所有输入文本均可引用变量”与 SQL 直传 DBX 可能冲突：统一在 Datara 授权网关完成变量解析与参数绑定；DBX 原生 IDE 若绕过网关，先阻断越权运行，不能声称变量已贯通。

## 仿真完成判定

以项目 33 的营销→商品/库存→购物车→订单/支付→退款→复购记录，逐项检验当前目标内的治理、变量、资源、DBX IDE/连接、影响分析能力。履约若缺事实表，用现有订单状态验证可表达的部分；不据此开发物流应用。每项区分“已有并验证”“当前目标缺口待补”“旧注解提及但本次不实施”。验证临时数据仅按专用命名空间清理；保留既有电商源表和已有质量规则。当前质量规则运行仅做结构校验、统计 0 行，不能将其记为行级通过；是否需要补行级执行只依 2026-10-29 目标设计的质量执行要求判定。
