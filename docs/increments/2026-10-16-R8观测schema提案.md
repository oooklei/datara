# R8 观测 schema 提案（前端消费视角）

日期：2026-10-16

## 性质声明

**本文件为前端（Trae / R8 侧）单方面提案，非冻结、非契约。**文中全部实体命名（stream_job / stream_observation 等均为提案名）、字段命名与结构皆为草案；最终以后端（Codex）契约与迁移 schema 为权威。前端契约层当前处于 RED 哨兵态（所有 I/O 方法抛 `I8_STREAM_NOT_WIRED`，不发出真实请求），后端 schema 冻结后前端逐字段对齐，冲突时一律以后端为准。

## 1. 事实来源

- worktree `trae-r4-red`（分支 `trae/r4-red`）内 `datara-web/src/services/rebuild/streamApi.ts`（I8 流处理契约层，RED 阶段；方法名/参数/返回类型逐字引用）。
- worktree 内 `datara-web/src/services/rebuild/metricsApi.ts`（I9 契约层）。streamApi 以 `import { type MetricValue, type TimeWindowQuery } from './metricsApi'` 复用共用类型，并 `export type { TimeWindowQuery }` re-export 供 View 单源导入——即 **`TimeWindowQuery` 与 `MetricValue` 是 streamApi 直接复用的 metricsApi 共用类型**。
- 共享协议字段（Codex 通报）：`workflow_version_id`、`attempt_no`、`variable_snapshot_id`/`sha256`、`resource_version_id`/`sha256`、`status`、`metrics(success_count, failed_count, skipped_count, read_count, write_count)`、`error(code, category, stage, retryable)`、`log_ref`。
- 计划正本 `docs/increments/2026-10-14-datara-platform-rebuild.md`「运行表时间戳闭环」已列流运行表名：`stream_job_attempt`、`stream_checkpoint`、`stream_metric_snapshot`、`stream_failure_event`（另含 `execution_event`）。

## 2. 观测实体草案（命名仅为提案）

| 提案实体 | 职责 | 计划正本对应运行表 | 前端类型（streamApi） |
|---|---|---|---|
| `stream_job` | 流作业（长驻进程面）主实体 | 正本未单列，暂按聚合/视图提案 | `StreamJobRow` |
| `stream_job_attempt` | 作业尝试（含重启历史） | `stream_job_attempt`（L103） | `StreamAttemptRow` |
| `stream_checkpoint` | 位点/检查点（分区位点与提交位点） | `stream_checkpoint`（L104） | `StreamCheckpointRow` |
| `stream_metric_snapshot` | 流指标时间序列点 | `stream_metric_snapshot`（L105） | `StreamMetricPoint` |
| `stream_failure_event` | 故障恢复 / 漂移注入事件 | `stream_failure_event`（L106；`execution_event` L102 关系待定） | `StreamRecoveryEventRow` |
| `stream_observation` | §8.4 观摩聚合视图（含窗口结果、错误样本子结构，非独立落表提案） | 正本未单列 | `StreamObservation`（子结构 `StreamWindowResult` / `StreamErrorSampleRow`） |

## 3. 字段提案表

来源列取值：`共享协议字段`（Codex 通报）/ `新提案`（前端契约或本文件新增）。消费点列均为 streamApi 具体方法，签名逐字引用。

### 3.1 `stream_job` → `listStreamJobs(window: TimeWindowQuery): Promise<StreamJobRow[]>`

| 字段 | 类型 | 来源 | 前端消费点 |
|---|---|---|---|
| `job_id` | string | 新提案（前端 `StreamJobRow.jobId`；共享协议未含） | `listStreamJobs`；并被 attempt/checkpoint/metric/event 各实体外键引用（`listStreamAttempts` 等的 `jobId?` 过滤参数） |

## 4. O6 注记

「唯一事件号 / 唯一 id」为执行附录对设计的实例化细化。本提案将其落在 `stream_failure_event.event_id`（前端 `StreamRecoveryEventRow.eventId`）上，仅是前端单方面的实例化示例；`stream_metric_snapshot`、`error_samples` 等其余观测行是否也需要唯一 id、由谁生成，均未定。**后端 schema 冻结时应将唯一事件号/唯一 id 的最终设计回填设计正本（或在设计正本作对应注记），本提案不构成裁定。**

## 5. 开放问题清单（给 Codex）

1. **SSE 事件结构**：SSE 的 event 名、`data` 载荷 schema 是否逐字段对齐本提案 §3.6（`StreamObservation`）？推送是全量快照还是增量？重连时 `Last-Event-ID` 与位点恢复如何衔接？
2. **log_ref 指向物**：`log_ref` 指向 `task_instance_log` 行、`execution_event` 行、还是对象存储/日志文件？前端凭 log_ref 拉取日志的端点与鉴权方式是什么？
3. **metrics 五计数的产出方**：`success_count / failed_count / skipped_count / read_count / write_count` 由执行器逐事件产出还是聚合器汇总？`read_count/write_count` 与前端 `recordsIn/recordsOut`、`success/failure/skipped` 与前端 `counters{success,failure,skipped}` 的口径是否一一对应？是否沿用 `MetricValue` 的 known/estimated 包装？
4. **流作业与工作流版本的关系**：长驻进程（stream job）是否挂在 `workflow_version_id` 之下？`attempt_no` 与流作业重启（`StreamAttemptRow.attemptId`）是否同一语义？`variable_snapshot_id` / `resource_version_id` 是否需要在观测查询结果中透出（前端当前无字段承载）？
5. **error 结构映射**：共享协议 `error(code, category, stage, retryable)` 与前端 `StreamErrorSampleRow{sample, flow}` 如何对应？`flow`（consumed/emitted/failed/dead-letter）与 `stage` 是否同一维度？
6. **status 语义**：共享协议 `status` 与 `StreamJobRow.state`（running/paused/stopped/failed）、`StreamWindowResult.status`（success/failure/skipped）三处是否同一枚举体系？
7. **事件唯一号规则（O6）**：`stream_failure_event` / `execution_event` 的事件 id 生成规则、全局唯一性保证，以及与 SSE event id 的关系。
