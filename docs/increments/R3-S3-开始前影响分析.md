## 上一步改动及影响

R3-S2 仅新增 `datara-backend/rebuild/governance/{__init__,contracts,models}.py` 和 `tests/rebuild/test_governance_contracts.py`。Models 目前仅由测试导入，尚未被 `rebuild.api.app` 导入；因此当前重建 API 启动不创建治理表。未改旧 API、旧表、正式业务前端、Compose 服务或 R2 数据生成逻辑。S2 SQLite contract suite 现为 26 passed；其后只修一处 Ruff 行宽，需复跑 lint 作为 S3 前基线。

## S3 影响范围与边界

- 只新增 rebuild 专属版本记录表、迁移 runner、迁移 revision module 与测试。
- 迁移只能向 `datara_rebuild_i0` 增加治理表；不访问/写入 `datara_meta` 旧业务表，不导入 I18-I23 源数据，不执行 DROP/清库。
- `Base.metadata.create_all` 不能单独充当版本迁移记录；revision、checksum、开始/结束时间、状态/尝试次数及失败摘要必须落表。
- MySQL DDL 可能隐式提交，不能承诺物理事务回滚；采用仅增量、幂等、失败可续跑的 forward-recovery。坏 revision checksum 必须拒绝；相同已完成 revision 跳过；相同失败 revision 允许重试；不得用空状态覆盖已完成记录。
- 运行日志/迁移表字段不写任何 secret。新 runtime 表均由数据库生成 `created_at/updated_at/generated_at`；Entity 表使用数据库生成 created/updated 时间。
- 本步骤验收只运行本机 SQLite 测试、静态检查与编译。真实 MySQL schema 创建和后台日志核对属于 R3-S7，届时先 dry-run 并再次核对 1.9 隔离 schema。

## 细化步骤

1. 复跑 S2 pytest、Ruff、compileall，固化基线。
2. 先新增 revision runner 失败测试：初次 apply、重复 apply、校验和冲突、故障状态留痕/同 revision 重试、表部分已存在时继续、created/updated/generated 数据库时间戳。
3. 实现迁移记录模型与 revision registry；revision 使用明确编号/摘要；只创建治理模型表，不执行源数据导入。
4. 本地 SQLite 故障注入：revision 中途抛错后状态为 failed，重试同 checksum 完成；checksum 变化 fail-closed。
5. 运行完整 rebuild tests、Ruff、compileall；更新证据与状态。本地通过不代表远端迁移已执行。
