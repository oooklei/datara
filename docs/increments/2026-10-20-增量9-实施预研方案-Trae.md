## ② 技术要点

### 2.1 §5A.4 尾随配置 UI 设计建议（行内「定时」/画布内入口）

权威设计 §5A.4（L514-518）已裁定形态：**调度不是独立菜单页，而是尾随每个工作流的配置**；入口两条 = 工作流列表行内「定时」+ 画布内调度配置入口。旧前端实证（权威设计 §附录 A L1039）：`DagListView.vue`（206 行）行内「定时」按钮 + `ScheduleDialog`。

建议组件形态与交互流（以旧实证为蓝本，按新前端范式重构）：

- **行内入口**：任务中心工作流列表行操作区「定时」按钮（旧实证 `DagListView.vue` L179 `<button class="op-btn" @click="openSchedule(r)">定时</button>`），携带该行工作流标识打开对话框；real 模式限定（旧实证 L126 mock 模式仅提示——新前端无 mock 态，此分支不需要）。
- **画布内入口**：建议画布顶栏工具区按钮（当前激活工作流 Tab 即 `wf` 定位键），打开同一 ScheduleDialog；具体落位（顶栏 vs 属性面板）可在拆票时定，语义上两入口必须复用同一组件与同一契约方法，避免双写。
- **ScheduleDialog 双视图**（旧实证 `datara-web/src/views/dag/ScheduleDialog.vue`：`editing`/`editId` 双态，L52-53）：
  - 列表视图：该工作流的定时计划表（名称/crontab/状态/优先级/失败重试/操作），操作列 = 上线|下线切换、编辑、删除（旧实证 L179 表头行）；后端删除语义 = 先 offline 再删（`api/wf_schedule.py` L209-221 注释「online 状态先下线再删，避免 master 空引用」）。
  - 表单视图：新建/编辑共用；**保存后初始 offline**（后端 create 固定 `state="offline"`，L163），成功提示带首次触发时间（旧实证 L125 `下次触发：${created.nextFireTimes?.[0]}`）。
- **cron 编辑与即时预览**：6 段含秒、`?` 等价 `*`；输入变更即调 `POST /crontab-preview` 展示未来 3 次触发时间；**预览未通过禁止提交**（旧实证 `submitForm` L106-110 先 doPreview 再拦截）。预览带 timezone 参数（后端 `_validate_crontab(crontab, timezone)` 按调度时区计算，`wf_schedule.py` L45-54）。
- **调度策略四字段的表单承载建议**：表单内独立「调度策略」分组，避免与基础项（名称/crontab/有效期 start_time/end_time）混排：
  - `misfirePolicy`：三选单选 `FIRE_ONCE`（默认，补最近一次）/`SKIP`（仅当轮恰逢）/`FIRE_ALL_LIMITED`（补发至 catches 上限），每项带一句语义说明；
  - `concurrencyPolicy`：三选单选 `ALLOW`（默认）/`FORBID`（占用中跳过并消耗窗口）/`QUEUE`（保留最旧 due 待容量释放）；
  - `maxRunningInstances`：数字输入，≥1（后端 `max_running_instances < 1` 报 PARAM_INVALID，`wf_schedule.py` L115-116）；
  - `timezone`：默认 `Asia/Shanghai`，选项用后端 ZoneInfo 校验回显错误（L117-120）。
  - 可见性建议：四字段进阶分组（折叠或「高级」），与旧实证表单（现只有基础项，L70）形成增量；后端 `_payload` 已输出全部字段驼峰面（L74-93），回读填充无缺口。

### 2.2 scheduleApi RED→GREEN 接线方案（端点清单对照）

**契约现状**（`datara-web/src/services/rebuild/scheduleApi.ts`，124 行，RED）：方法清单冻结为 5 个（L87-93 `R6_CONTRACT_METHODS`：listTriggers/registerTrigger/listQueue/listRuntimeEvents/listAlerts）；端点前缀草案 `/api/v1/rebuild/schedule/*`（文件头 L3 自述「最终以后端契约为权威」）；哨兵 `R6_SCHEDULER_NOT_WIRED`（L84，词形被测试冻结，test L63-66 X13-A 改名回归守卫）；类型面 TriggerRegistration（kind 五枚举 MANUAL/CRON/DEPENDENCY/EVENT/TRIAL，L15）/ScheduleQueueEntry/ScheduleRuntimeEvent/ScheduleAlert。

**后端实有端点**（T55 交付，7 端点，`datara-backend/api/wf_schedule.py`，经 `api/main.py` L111 挂载 prefix `/api/v1`）：

| 后端端点 | 方法 | 权限 | 语义 |
|---|---|---|---|
| `/api/v1/crontab-preview` | POST | edit_definition | crontab 校验 + 未来 3 次触发预览（timezone 感知） |
| `/api/v1/workflow-definitions/{wf}/schedules` | GET | get_current_user | 某工作流定时列表（倒序；`{wf}` 兼容定义 id 与数字 code） |
| `/api/v1/workflow-definitions/{wf}/schedules` | POST | edit_definition | 新建（初始 offline，返回预览） |
| `/api/v1/schedules/{schedule_id}` | PUT | edit_definition | 更新（crontab 变更重校验；update_time 驱动 master 缓存重算） |
| `/api/v1/schedules/{schedule_id}` | DELETE | edit_definition | 删除（先 offline 再删） |
| `/api/v1/schedules/{schedule_id}/online` | POST | run_instance | 上线（上线前 crontab 再校验） |
| `/api/v1/schedules/{schedule_id}/offline` | POST | run_instance | 下线 |

**对照结论（关键 gap）**：

1. **面错位**：R6 契约是「调度运行时观测面」（触发注册/队列/事件流/告警），T55 交付是「定时 CRUD+策略面」（DS 对标 t_wf_schedule）。5 方法中仅 listTriggers/registerTrigger 与 CRON 定时计划部分语义重叠；缺 listSchedules/updateSchedule/deleteSchedule/online/offline/previewCrontab 六个 CRUD 面方法；TriggerRegistration 类型缺四字段与 failRetry/workerGroup/priority/state。
2. **位置缺口**：T55 交付挂在顶层 `api/main.py`（8000 旧后端链路）；`rebuild/api/app.py`（8001，新前端唯一事实源）**零调度端点**。新前端单 BASE 禁第二后端分派（权威设计 §7.1 L932-935），故 GREEN 前必须有 rebuild 侧端点（语义平移，非迁移——权威设计 §附录 A L883 已将旧 `api/wf_schedule.py` 标「禁迁移（I7 在建）」，T55r 核查完成的是 RT 语义收口，rebuild 侧需按同语义自研补建）。
3. **接线方案建议**：a) 契约层扩展——按 P2-1 R6 清单冻结契约的变更流程报备后，将 `scheduleApi.ts` 扩为「CRUD 面 + 观测面」两段：CRUD 段方法对齐上表 7 端点（类型 ScheduleRow 对齐 `_payload` 17 键驼峰面），观测段 3 方法（listQueue/listRuntimeEvents/listAlerts）留待运行时观测面与增量 8 execution 域衔接，不删不弃；b) 哨兵替换——按现有工厂模式逐方法替换 `notWired`，UI 层不感知切换（`scheduleApi.ts` L112-115 注释已声明此切换方式）；c) 事件契约模式参照 legacy `views/dag/InstanceRunsView.vue`（文件头 L5 自述）。
4. **定位键建议**：`{wf}` 路径参数沿用后端「兼容定义 id 与数字 code」语义（`wf_schedule.py` L57-64）；新前端在项目工作区 `/p/:projectId` 上下文下，工作流定位键应与增量 3 项目作用域守护对齐（project_id 注入由底座承担）。

### 2.3 调度策略四字段的承载与校验（前后端对齐点）

- **后端校验基线**（`wf_schedule.py` `ScheduleBody.validate_policies` L110-120）：misfire ∈ {FIRE_ONCE, SKIP, FIRE_ALL_LIMITED}；concurrency ∈ {ALLOW, FORBID, QUEUE}；max_running_instances ≥ 1；timezone 走 ZoneInfo 可实例化校验。前端表单应先行同规则校验（枚举前端写死白名单、数字 min=1、timezone 提交前提示），错误回显对齐后端 PARAM_INVALID 报文。
- **优先级裁剪**：`priority` 后端钳制 1-5（create L164 `max(1, min(..., 5))`）；`fail_retry_times ≥ 0`、`fail_retry_interval ≥ 1`（L166-167）。表单 min/max 与此对齐。
- **数据库迁移**：四列经 `_ensure_column` 幂等补列（`common/db.py` L124-127，t_wf_schedule，含默认值）；rebuild 侧补建时建模应对齐（含四字段默认 FIRE_ONCE/ALLOW/1/Asia/Shanghai）。
- **策略机语义（验收断言依据）**：`master/schedule.py`（186 行）——Leader-only（`schedule_loop` 仅持 master gate 时扫描，L176-177，即 fencing 语义；`failover.py` 的 fence_token 属实例恢复侧，非调度侧）；扫描周期 `SCAN_SECONDS=10`；补发上限 `MAX_MISFIRE_CATCHUP=100`；SKIP 仅当 `due[0] == current` 触发（L149-150，即当前实现为**边界敏感**语义——这正是 T55 裁定的技术背景）；FIRE_ONCE 取 `due[-1]`；FIRE_ALL_LIMITED 补发至 100 上限；FORBID 消耗窗口（`entry["next"] = following`）、QUEUE 保留最旧 due 待容量释放（L158-162）；timezone 感知（`_schedule_now` 转调度时区 L23-25）。
- **测试基线**：`tests/test_schedule_policies.py` 8 用例（misfire 三策略 / SKIP 两种边界 / queue skip 容量释放 / FORBID / max_running caps / timezone cron 时钟）——rebuild 侧补建票与前端契约测试可据此重放同语义断言。

### 4.2 T55 SKIP 语义裁定（单列，⛔ 融合宣告硬前置）

- **裁定内容**（权威设计 §6.6 L913、WBS L550）：调度 SKIP 策略二选一——**A 严格等值**（错过即跳过，仅当轮恰逢才触发）/** B `SCAN_SECONDS` 宽限**（扫描周期 10s 内的迟到视为准点触发）。
- **技术背景**：当前 `master/schedule.py` L149-150 实现为 `due[0] == current` 才补发（严格边界敏感）；`test_schedule_policies.py` 两个 SKIP 边界用例（L88 `test_skip_normal_due_fires_at_exact_second`、L106 `test_skip_current_equals_first_fires_at_minute_boundary`）固化了现语义。选 B 则策略机需放宽比较窗口（如 `current - due[0] < SCAN_SECONDS`），后端测试需回归。
- **阻塞面**：① 9.1 验收闭环中「按策略触发」的 SKIP 分支 Playwright 断言不能写死（A/B 断言不同）；② 融合宣告被红线 7 挡（WBS L327：裁定解禁前不得宣告正式融合；权威设计 §7.2 L953-954 八门唯一准绳）；③ B 组调度管理行 ⛔ 状态维持（权威设计 §3.3 L215）。
- **不阻塞面**（已在权威设计显式放开，§5A.4 L518）：UI 开发、契约接线、契约测试全绿——WBS 退出标准 2 允许「裁定未到达时 UI 与契约测试全绿即计开发面收口，融合宣告挂起并在 STATE.md 登记阻塞」。
- **需要用户裁定什么**：单选 A 或 B；若选 B，是否连带修正现网 master/schedule.py 语义（影响 8 个策略测试中 2 个 SKIP 边界用例）。
- **解阻后可立即开工**：① 9.1 闭环 Playwright 的 SKIP 分支断言补全；② 9.2 裁定回归测试记录与收口；③ 融合宣告条件核验（八门过门清单核验）——三件均在 WBS 9.2 责任线建议（Codex）范围内。
