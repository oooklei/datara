## 一、任务分解建议

WBS 增量 16 目标（L471-473）：DDL 写路径落地 = 对象 DDL 编辑**双轨**（非 table 对象走源码文本编辑器，13 变体 `ObjectSourceKind` 不含 table/index；table 走结构化编辑器）+ **八步管控面** + **对象编辑全链路收口**。任务包 16.1（DDL 双轨编辑器 + 八步管控 + confirm_phrase 人工闸，⛏）/ 16.2（对象编辑全链路收口：DDL 执行/落库/发布/审计/回滚，⛏），责任线建议均为 Claude，验收门 = R5-B 分阶段边界（v4 U1/U3）+ A7 红线 + 门 1（rb 域契约回归）。

基于现状盘点（见 §三），建议实施序分四波（供拆票参考，票级粒度见 §五）：

| 波次 | 内容 | 对应 WBS 包 | 性质 |
|---|---|---|---|
| 波 1 | 后端阶段 D 补齐：G-B3 ConfirmGate / G-B1 DdlExecutor / G-B2 RollbackManager 新建 + G-B5 ExecutionLedger 接线 + #24/#25 装配注入 + project_id 占位修正 | 16.2 后端面 | 后端先行（写路径闸门组件缺位，前端无契约可对） |
| 波 2 | 前端契约 RED→GREEN 转绿：sqlIdeDdlApi 契约形态按后端 wire format 重塑（snapshot 两阶段绑定链对齐）+ 契约测试改写 + CONTRACT_REGISTRY/COPY_LEDGER 登记 | 16.1 前置 | 契约先行（现行 RED 契约与后端 wire format 存在结构性差异，见 §二.2） |

## 二、技术要点

### 2.1 双轨编辑形态（权威设计 §5.3.1 对标 DBX）

- **源码文本轨**：非 table 对象，`ObjectSourceKind` 13 变体 = VIEW / MATERIALIZED_VIEW / PROCEDURE / FUNCTION / TRIGGER / EVENT / SEQUENCE / SYNONYM / JOB / PACKAGE / PACKAGE_BODY / TYPE / TYPE_BODY，**不含 TABLE/INDEX**（DBX 实锚 `crates/dbx-types/src/types.rs:L209-L223`；融合对照清单归档件 §2.1 已亲核登记）。表结构走独立元数据通道，索引为表子对象——ObjectSourceKind 只覆盖「源码型对象」。
- **结构化编辑轨**：table 对象走结构化编辑器，不得以非 table source editor 代替（A5 议程证据 `docs/increments/evidence/2026-10-17-A5-SQL-IDE-contract-agenda.md` L66）。
- **能力分级闸**：capability gate 必须拒绝只读对象/driver 的写入（DBX 已标出 Event、部分 Trigger、OpenGauss Package/PackageBody 等限制，同上 L66）——13 变体 × 驱动矩阵的逐格状态边界须在实施前完成精读登记（增量 11 退出标准第 4 条已要求「DBX DDL 编辑精读锚点补入研读映射登记」，须核对该精读是否已覆盖 13 变体全量）。

### 2.2 前端 RED 契约与后端 wire format 的结构性差异（转绿最大技术点）

实测对照（FE `sqlIdeDdlApi.ts` L41-90 vs BE `rebuild/rb/facade/rb_facade.py` L39-71）：

| 契约方法 | FE 现行（RED）形态 | BE 现行 wire format | 差异结论 |
|---|---|---|---|
| getDefinition | `(datasourceId, objectKind, schema, name) → DdlDefinition{ddlText, updatedAt}` | **rb router 不挂载**——#21 复用 R5-A shared read（`rb/api.py` L9 注：本 router 不重复挂载）；R5-A `sqlIdeApi.getDefinition`（L377）返回 `{definition, capability, constraints}` | FE R5-B 的 getDefinition 与 R5-A 重复；且 R5-A 响应**无 sourceVersion 字段**，而 R5-B 快照绑定链需要它（见 2.3） |
| validatePolicy | `(datasourceId, nextDdlText)` | `POST /validate-policy`，body=`{datasourceId, objectRef, sourceVersion, nextDdlText}` → `{snapshotId, findings, blocked}` | FE 缺 objectRef + sourceVersion 入参 |
| previewImpact | `(datasourceId, nextDdlText) → DdlImpactItem[]` | `POST /preview-impact`，body 同上 → `{snapshotId, impacts, unknownReasons}` | FE 缺 snapshotId/unknownReasons/objectRef/sourceVersion |
| submitConfirm | `DdlConfirmRequest{datasourceId, definition, nextDdlText, policyReport, confirmPhrase}`（**内联 policyReport**） | `POST /confirm`，body=`{datasourceId, objectRef, sourceVersion, nextDdlText, policySnapshotId, impactSnapshotId, confirmPhrase}`（**两阶段 snapshotId 绑定**） | **结构性差异最大**：FE 携带内联策略报告，BE 要求 #22/#23 产出的双 snapshotId 回填；转绿前契约必须重塑 |
| listExecutionRecords | `(datasourceId) → DdlExecutionRecord[]` | `POST /execution-records`，body=`{datasourceId, objectRef?, page, pageSize≤200}` → `{items, page}` | FE 缺分页参数；记录字段需对齐 BE ExecutionRecord 模型（status 枚举含 compensated/recovery-failed，FE 现仅 success/failure/rolled-back，见 `rb_facade.py` L7-8 注与 P2-3 v3 §9.2 状态机） |

**结论**：现行 RED 契约是按早期草案语义写的（文件头 L3 注明语义源自 R5-IDE 影响分析 §4 与 plan I6 草案），与 P2-3 v3 冻结 wire format 不一致。转绿波（波 2）不是简单「把 notWired 换成 request」，而是**契约类型体系重塑**——涉及 A6 契约冻结纪律：方法清单 `R5B_CONTRACT_METHODS`（L72-78）被测试冻结断言（`sqlIdeDdlApi.contract.test.ts` L9-17），重塑须同步改写测试并在 CONTRACT_REGISTRY 登记变更。

### 2.3 快照绑定链与 sourceVersion 贯通

后端快照模型（`rb/models/rb_models.py` L40-75）：PolicySnapshot 绑定 `source_version`（注释明确「ETag from getDefinition」）+ `next_ddl_digest`（SHA-256）；ImpactSnapshot 额外绑定 `policy_snapshot_id`（同一 policy 快照）。ConfirmGate 验证短语 = HASH(project_id + datasource_id + object_ref + source_version + next_ddl_digest + policy_snapshot_id + impact_snapshot_id + ACTOR_SECRET)，任一绑定字段不匹配即拒绝（P2-3 v3 §3.4，归档参考）。**前端链条**：读取对象定义（拿 sourceVersion）→ 编辑 → #22（拿 policySnapshotId）→ #23（拿 impactSnapshotId，且其内已绑定 policySnapshotId）→ #24 提交短语+双 snapshotId → #25 查记录。当前 R5-A `getDefinition` 响应不含 sourceVersion（FE 类型 L377），是绑定链的**断点**，须在波 2 一并处置。

### 2.4 八步管控面

WBS 仅表述「八步管控流程」（L481）/「DDL 八步管控 Playwright 通过」（L486），未枚举八步。现行可考的闸序链：FE 契约头登记「DDL 八步闸（编辑→管控结果→影响预览→确认闸 confirmPhrase→执行→回滚记录）」（`sqlIdeDdlApi.ts` L6，6 节点）；后端组件链 = ConfirmGate → DdlExecutor（写连接隔离 + 前像保存 + 执行 + 记录 + 失败补偿）→ RollbackManager（补偿计划/补偿执行/补偿失败进入人工恢复）→ ExecutionLedger（append-only，P2-3 v3 §3.4-3.7）。八步完整枚举的权威出处（核心设计正本 §13.6）已在归档区，实施前须补全步序清单报监督线核对（见 §四 开放问题 3）。

### 2.5 facade 502 fail-closed 语义与解禁路径

- **fail-closed 机制**：facade 每方法先判 service 是否注入，None 即返回 502 CAPABILITY_UNSUPPORTED（`rb_facade.py` L203-208/#22、L250-255/#23、L302-307/#24、L332-337/#25）；装配层仅注入 `policy_snapshot_service` + `impact_snapshot_service`（`app.py` L939-947，注释明确「#24/#25 services are stage-D undelivered, the facade fails closed (502)」）。
- **解禁路径 = 三件事**：① 补齐 G-B3/G-B1/G-B2 三个服务类（`rb/executor/__init__.py` 实测为空文件，confirm_gate.py / rollback_manager.py 无文件）；② 将 ExecutionLedger（已实现于 `rb/ledger/execution_ledger.py` L17-60：record_execution / record_compensation / list_records，append-only）与 ① 组合为 #24/#25 服务注入 RbFacade；③ 装配层加两参数。**#22/#23 无需动**——已接真实服务。
- **附带缺口**：facade 三处 `project_id=request.datasourceId  # TODO: 用真实 project_id`（`rb_facade.py` L192/L213/L259），须承接增量 3 项目上下文（URL 上下文=授权上下文），否则快照归属与审计链挂错项目。

### 2.6 写路径安全边界（A7 红线落点）

confirm_phrase 人工闸双闸：契约层注释「确认/执行/回滚全部需要用户人工闸——契约层不提供绕过通道」（`sqlIdeDdlApi.ts` L5）+ 服务端 ConfirmGate 短语绑定校验（agent 禁止代填）。preview 不回传样本值（WBS L484）。执行器写账户与只读账户分离（P2-3 v3 §3.5 `_get_write_connection`）。回滚补偿动作本身另记 ExecutionRecord，补偿失败 status=recovery-failed 进入人工恢复（§3.6）。审计可查依赖 #25 + ledger 表（`RbPolicySnapshotRecord` / `RbImpactSnapshotRecord` / `RbExecutionRecordRecord`，`ledger_repository.py` L19/L36/L53，三表已建）。
