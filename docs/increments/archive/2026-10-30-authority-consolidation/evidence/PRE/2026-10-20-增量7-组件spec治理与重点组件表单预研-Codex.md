## 三、目标方案

### 3.1 M1 承载域：建议独立 `rebuild/component_spec/`

建议把 M1 落在独立只读目录域 `datara-backend/rebuild/component_spec/`，由 `rebuild/api/app.py` 挂载为：

- `GET /api/v1/rebuild/components/spec`
- 请求头：可选 `If-None-Match`
- 200：`{"items":[...]}` 裸 JSON，响应头含强 ETag；清单稳定排序，ETag 必须基于实际响应字节。
- 304：空 body，回传同一 ETag。
- 失败：不得返回 200 空清单；使用可辨识错误并保留旧缓存。

选择独立域的理由：component spec 是跨 workflow、resources、dependency 的全局发布目录，不属于任何单一业务域；并入 resources 会混淆“文件版本”与“组件版本”，并入 workflow 会使组件治理错误地从属于工作流实例。它仍由 rebuild 装配层统一认证和登记。

端点读取已发布组件治理表/基线数据，不把 `common/dag_catalog.json` 直接暴露为第二运行时真源。兼容迁移期可以用 catalog 生成/导入基线候选，但响应只来自一个发布视图，并满足：全局唯一 type、published version 精确 join、已发布不可变、`componentRef:{type,version}` 可解析、发布闸门通过。

### 3.2 零私设治理闭环

1. 后端响应决定 palette 条目、分类、schema、可用性、`runtimeOnly` 和适用 workflow types。
2. 新前端只实现通用 renderer、缓存和过滤器，不保留硬编码 C11/C12/C13 字段或静态组件列表。
3. 组件未出现在 spec 时不得由前端 profile 补回；未知 `componentRef` 显示“规格不可用/版本不可解析”，禁止悄悄换成同 type 最新版。
4. degraded 建议定义为“继续使用内存或持久化的最后一次成功响应，并明确陈旧状态；从未成功加载则阻断 palette 并允许重试”。静态 profile 兜底仅能作为旧前端过渡行为，不能进入新前端正式链。
5. 无出处组件治理流程固定为：导出当前 published 清单 → 对照 I0~I11/会议纪要/指定对标产品 → 标记保留、类型专用、runtimeOnly、待裁、建议移除 → 监督线裁定 → 生成新版本/下线动作 → 回归引用与 palette。不得改写已发布版本或让前端先行隐藏来替代后端治理。

### 3.3 spec 结构与域规范落位

建议 M1 传输项至少显式提供：

- 身份与版本：`type`、`publishedVersion`、displayName、分类、适用 workflow types；
- 展示：visual；
- 八段表单 DSL：`inputs/outputs/params/conditions/constraints/exclusions/refs/exports`；
- 执行与呈现：可用性、`runtimeOnly`、静态 ports、behaviors、extensions；
- 引用：所有资源选择结果只保存 `{resourceId, resourceVersion, kind}`，禁止 URL、路径或 `latest`。

发布闸门需新增/复用以下校验：纯 JSON；禁函数/脚本/回调；四白名单合法；八段齐全且引用闭合；type 唯一；executor 存在且可执行；资源引用字段只接受明确版本；已发布版本不可覆盖；`showIf/onChange/text` 函数字段为零。

### 3.4 上传文件扩展

推荐把“上传”建模为通用字段能力，而不是给三个组件写三个专用 UI：

1. spec 的 params 声明资源选择字段，`kind` 固定为当前组件种类，动作由白名单 behavior 触发 resources multipart 上传；
2. 上传成功后将不可变 `{resourceId, resourceVersion, kind}` 写入节点参数；保存工作流时再建立 workflow version × task slot 绑定；
3. C11 仅允许 `.sql`，C13 仅允许 `.py`，C12 仅允许 `.sh`，20 MiB 上限以服务端为准；前端同规则预校验但不拥有规则真源；
4. 上传、选历史版本、清除引用、回读文件名/摘要/版本均由通用 renderer 完成；禁止保存本地路径、下载 URL、base64 正文或 `latest`。

内联文本与资源引用必须冻结为明确规则。建议一期采用二选一且至少一个有效：资源引用存在时执行具体资源版本；否则执行内联字段。UI 必须显示当前生效来源，避免“上传成功但仍执行旧内联文本”。是否允许两者同时保存及切换后是否清空未生效值，列入 §四待裁。

## 六、验收风险

| 风险 | 触发方式 | 必须验证的防线 |
|---|---|---|
| 双真源复发 | 新前端保留 profile palette/schema fallback | 静态搜索负断言 + 首次 spec 失败 E2E，确认不会出现私设组件 |
| ETag 假命中/永不命中 | 排序漂移、包络动态字段、哈希字节与发送字节不同 | 相同数据跨请求 ETag 相同；改一规格 ETag 改变；304 无 body |
| 发布版本漂移 | 节点只存 type 或资源只存 latest | 保存产物断言同时固定 component version 与 resource version |
| 上传成功但执行旧内容 | inline 与 resourceRef 同时存在且优先级不明 | UI 显示生效来源；执行探针证明所选具体 digest 被读取 |
| 资源越权 | 用别的 project 的 resourceId/version | 服务端项目归属负测，返回稳定权限/不存在语义且不泄露元数据 |
| 只做上传控件未闭环 | 选文件后仅显示文件名，未上传/绑定/回读 | WBS 退出链完整 Playwright：选文件→上传→form 引用→保存→回读 |
| 五要素“凭经验填写” | 无外部产品 UI/源码证据就冻结字段和顺序 | 每个要素附来源锚；证据不足标开放项，不得假定通过 |
| 组件删除破坏存量 | 未统计 componentRef 就下线/移除 | 删除前列出版本引用量、存量工作流打开/运行策略、回滚路径 |
| DSL 不可序列化 | showIf/onChange/text 或 URL/回调混入 spec | 发布闸门与 JSON round-trip 测试；白名单逐项负测 |
| 声明可用但不可执行 | spec 有组件而 executor/资源读取链缺失 | `run_publish_gates()` + 最小真实执行；C11/C12/C13 各一条成功与失败证据 |

增量 7 完成声明应同时满足 WBS 退出标准与上述风险防线：M1 一源可用、前端零私设、上传资源版本闭环、三组件五要素有来源且实测、类型过滤正确、无出处组件仅按裁定处置。任何一项只具 UI 或只具 API 证据，都不足以标记 GREEN。
