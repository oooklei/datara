## 三、目标方案

### 3.1 分层架构

建议按「后端小补 → 项目列表页 → 项目工作区 → 成员管理 → 上下文守护 → 工作台」落地：

1. **后端项目小补**：新增 PUT /projects/{id}（改名/描述）+ DELETE /projects/{id}（空项目才可删——有工作流/数据源/资源时 409）；不引入 DS bigint code；flag 开关后置。
2. **项目列表页**：登录后首页 = 项目列表（卡片）；GET /api/v1/rebuild/projects；展示我拥有/参与的项目。
3. **项目工作区**：`/p/:projectId/...` 路由；任务中心、数据集成、数据开发、数据治理全套菜单挂项目下；顶栏当前项目 + 返回项目列表。
4. **项目成员管理**：members 三端点承接；owner/ADMIN 可管理 `can_manage_project`。
5. **上下文守护**：路由守卫校验 projectId 归属（4041/4042 语义）；项目作用域 API 自动注入 project_id——URL 上下文 = 授权上下文，防串项目。
6. **工作台页**：A 组 metrics 域统计指标呈现入口 + 快捷导航。

### 3.2 项目工作区路由设计

| 路由 | 承载 | 说明 |
|---|---|---|
| `/p/:projectId/dag` | 任务中心 | B 组全套能力 |

### 3.3 上下文守护设计

| 层 | 机制 | 说明 |

### 4.2 开放问题（必须先裁定或冻结）

1. **项目列表页与工作台的关系**：登录后首页 = 项目列表（§5A.11），但 A 组工作台（I9）为全局总览——需明确工作台是否在项目列表页之前（全局工作台）还是项目工作区内（项目工作台）。建议：全局工作台 = 项目列表页本身（卡片 + 统计指标入口），项目工作台 = 项目工作区内 metrics 呈现。
2. **PUT/DELETE 409 语义细节**：权威设计明示「有工作流/数据源/资源时 409」——需明确 409 响应体格式（建议 `{code: 4091, msg: "project not empty", data: {workflows: N, datasources: N, resources: N}}`）。
3. **项目成员角色模型**：members 三端点已有 PATCH（L1059）——需明确角色枚举（owner/ADMIN/MEMBER/VIEWER？）与 identity 域 Role 的映射。

## 六、验收风险

| 风险 | 触发征兆 | 验收控制 |
|---|---|---|
| PUT/DELETE 409 语义不一致 | 有工作流/数据源/资源时删除未返回 409 | 409 响应体格式冻结 + 测试覆盖 |
| 路由守卫绕过 | 直接访问 `/p/:projectId/...` 未校验归属 | 越权负断言测试（4041/4042） |

| 菜单挂载遗漏 | 项目工作区全套菜单未全部挂载 | Playwright 逐菜单可达测试 |

预研结论：增量 3 的后端基础已扎实（I1 既有实现 + 九域授权闸门 + 归属链），缺口集中在 PUT/DELETE 两端点（0.4 盘点 G-02 实锚）。前端为全新建（旧前端无项目概念），依赖增量 1/2 骨架。上下文守护（URL 上下文 = 授权上下文）是防串项目的关键机制，须与路由守卫同步落地。按上述 6 票推进并完成后端小补 + 前端四要素 + 工作台闭环后，才具备关闭增量 3 的条件。
