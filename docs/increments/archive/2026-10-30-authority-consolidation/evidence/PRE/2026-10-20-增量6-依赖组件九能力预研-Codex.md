### 1.2 九能力核对口径

| # | 能力 | 真源口径 | DS/Datara 定性 |
|---|---|---|---|
| 1 | 工作流依赖 | `kind=workflow`，selector=workflow，sentinel=0 | DS 复刻 |
| 2 | 任务依赖 | `kind=task`；selector=all_tasks（-1）或 task（正数） | DS 复刻；含 DependentExecute 两个任务分支 |
| 3 | 文件/表状态/外部任务依赖 | `kind=file|table_state|external_task`，各自具备对象、状态和证据模型 | Datara 设计 §6.5 必做扩展 |
| 4 | 时间范围 | `cycle+date_value` 命名窗与 `date_range` offset 扩展互斥输入，统一输出 ISO 8601 左闭右开窗口 | DS 复刻 + 适配；多区间、时区、business_date 固化不可丢 |
| 5 | 轮询周期 | `check_interval_seconds`；C9 草稿默认 10 秒，运行时必须实际消费 | DS UI 默认 + Datara 运行时语义 |
| 6 | 超时 | 窗口 `timeout_seconds`、依赖节点等待 timeout、系统 max-runtime 三套语义分离 | DS 复刻 + Datara 明确化 |
| 7 | 满足/失败策略 | `depend_result` 极性；`failure_policy=fail|waiting`；`failure_waiting_seconds` | 极性为 Datara 扩展；等待策略复刻 |
| 8 | 两层组合判定 | 组内 `join` × 组间 `group_relation`，均支持 AND/OR | DS 复刻；缺省 group_relation=AND 兼容旧 wire |
| 9 | 执行判定与结果反馈 | 两层三态机 + timeout；整工作流/全任务/单任务存在、禁用、成功分支；`parameter_passing` 仅成功后透传 | DS 全链路复刻 |

九能力按权威设计的九行计数；其中第 3 行包含三个扩展 kind，第 7 行包含极性与失败策略，第 9 行承担执行判定。`parameter_passing` 虽未作为“第十能力”计数，已由 v2.1 冻结为不可省略的运行时能力，必须进入实施票与 A5 附卷。

## 三、目标方案

### 3.1 分层架构

建议按“spec 一源 → C9 编辑模型 → dependency 契约 → 判定适配器 → runtime tracker → 证据附卷”落地：

1. **component spec 一源**：后端 C9 spec 发布完整 JSON schema、默认值、枚举、条件显隐、远端选择器和结果反馈定义；新前端只渲染 spec，不复制业务枚举。C9 `componentRef:{type:'dependent',version}` 固定已发布版本。
2. **C9 编辑模型**：顶层为两层 group editor 与策略区；条件行先选 kind，再显示对应对象选择器和状态字段，再选命名窗或 offset 窗，最后配置 depend_result/parameter_passing。交互按 DS 顺序组织并提供服务端表达式预览。
3. **契约模型**：保持 frozen v2.1 的 snake_case wire；把三个扩展 kind 的字段结构单独形成契约增补，经过监督线/独立评审后版本化，不复用 workflow 字段硬塞。旧 v1 wire 只保留明确兼容入口。
4. **判定适配器**：每个 kind 实现统一 `probe(condition, frozen_context) -> satisfied|pending|failed`，并返回结构化 evidence（对象、窗口、观测状态、时间戳、原因）。workflow/task 读取正式 execution 域；file/table_state/external_task 通过受控适配器查询，全部只读、可审计、可超时。
5. **两层组合器**：单一实现同一套 DS 三态规则，先组内、后组间。timeout 作为 tracker 生命周期输出，不混入 DS 三态组合优先级；若保留 API 四枚举，必须在组合前后明确映射并固化测试。
6. **runtime tracker**：按 `check_interval_seconds` 轮询；使用随 run/checkpoint 固化的 workflow version、business_date、时区和 dependency config；禁止读取 latest。处理 failure waiting、节点 wait timeout、系统 max-runtime 三套 deadline，并保证终态 CAS 单写。
7. **值透传**：仅在条件 satisfied 后提取上游 VarPool OUT；按 DS 同名选择规则合并到下游 runtime context，记录来源和冲突处理，不以变量引用替代。

### 3.2 C9 表单目标

| 区块 | 字段/交互 | 默认与校验 | 结果反馈 |
|---|---|---|---|
| 条件组 | group_relation；groups[].join；增删组/项 | 两层 relation 默认 AND；至少一组一项 | 即时展示表达式结构 |
| 条件类型 | kind 五值；workflow/task selector sentinel；扩展 kind 专用字段 | kind/selector/sentinel 强一致 | 字段级诊断，不静默改值 |
| 时间窗 | 模式切换：cycle+date_value 或 date_range | 二选一；cycle 默认 day，date_value 默认 today；切 cycle 清空旧 date_value | 预览 ISO `[start,end)` 和 business_date |
| 轮询/失败 | check_interval_seconds；depend_result；failure_policy；failure_waiting 输入按 DS 分钟呈现 | check 默认 10 秒；waiting 时分钟为正整数，提交前乘 60，溢出拒绝 | 显示换算后的契约秒数 |
| 超时 | timeout_seconds；dependent wait 开关、分钟输入、warn/failed 多选 | 节点 timeout UI 默认 30 分钟、warn；与 failure waiting 互斥 | 展示 deadline、告警/终止语义 |
| 透传 | parameter_passing | 默认 false；仅支持的 workflow/task 条件展示 | 显示预计透传变量与冲突提示 |
| 预览/判定 | preview/evaluate | 使用同一窗口解析器；evaluate 仅只读 | 每项 evidence、组结果、最终 verdict、原因 |

WBS 中“`relation=AND`、`checkInterval=10`、`timeout=30`”应精确解释为：两层 relation 草稿默认 AND；checkInterval 是 DS UI 草稿默认 10 秒；timeout=30 是依赖节点等待 timeout 开启后的 UI 分钟默认，不能写入 `timeout_seconds=30` 冒充窗口判定阈值。

### 3.3 全覆盖附卷设计

A5 附卷作为实施交付物而非事后补文档，至少包含：

1. **S4 九能力表**：能力、我方字段/UI、实现符号、DS/设计锚点、测试 ID、实测证据、差异说明、覆盖结论。
2. **三态真值表**：AND/OR 对 satisfied/pending/failed 的全分支；组内×组间四组合；空集、timeout 映射单列，不用抽样代替穷举。
3. **DependentExecute 三分支表**：workflow(0)、all_tasks(-1)、task(>0)；逐一覆盖不存在、未发布/禁用、无实例、运行中、成功、失败和所需极性。
4. **时间附卷**：所有 date_value；多区间；小时/日/月边界；业务时区与 DST；inclusive→exclusive；business_date 在重试/恢复不漂移。
5. **策略附卷**：failure waiting 与节点 timeout 互斥；两类分钟乘 60、正整数和溢出；warn/failed/WARNFAILED；并发 deadline 单终态和 termination_reason。
6. **扩展 kind 附卷**：每 kind 的字段、探针输入、状态映射、权限/凭据、超时、审计、不可达/错误行为。
7. **端到端证据**：component spec → C9 表单 → save snapshot → publish/run → tracker → verdict/反馈；前后端测试和远端 UI 证据关联到同一用例 ID。

### 4.2 开放问题（必须先裁定或冻结）

1. **三个扩展 kind 的字段结构**：文件是本地/资源/远端路径何种标识，表状态允许哪些谓词，外部任务按何种 provider/task/run 标识；当前契约明确仍未冻结。
2. **扩展 kind 的状态映射**：不存在、不可达、权限拒绝、探针错误分别映射 pending/failed 还是错误终止，是否受 depend_result 极性反转。
3. **timeout 四枚举映射**：DS 组合器只有 SUCCESS/WAITING/FAILED；现实现把 timeout 直接加入组合优先级。需明确 timeout 是条件状态、tracker 终态还是 API 展示派生值，再冻结唯一真值表。
4. **多区间执行语义**：现有 envelope 简化与 v2.1 “逐区间查询、全部成功”冲突，必须决定数据结构与 evidence 返回格式。
5. **all_tasks 范围**：以固化 workflow version 的启用任务全集为准；需要确认跳过、禁用、动态物化节点是否纳入。
6. **默认值命名冲突**：`timeout=30` 必须限定为节点等待分钟默认；窗口 `timeout_seconds` 是否有默认值应继续保持未配置不触发，除非另行裁定。
7. **`parameter_passing` 冲突规则**：需以 DS 源码精读结果冻结同名值选择和多依赖合并顺序；不能凭普通变量优先级推断。
8. **旧验证页去留**：增量 6 应以 `datara-newweb` C9 为正式入口；旧 `DependencyFormValidationView` 可作为迁移参考，但其 GREEN 横幅须避免被验收材料误引为 S4 GREEN。

## 五、拆票建议（L⛏）

| 票号 | 可执行范围 | 产物 | 验收/退出 |

## 六、验收风险

| 风险 | 触发征兆 | 验收控制 |
|---|---|---|
| 把 API GREEN 当成领域 GREEN | 引用旧验证页横幅或 5 方法测试直接关闭增量 | 终验只认 S4/R4 九项与 L6-11 独立 PASS |
| 枚举存在但功能不存在 | 五 kind 类型能编译，扩展请求仍拒绝或只保存不判定 | 每 kind 必须有真实 probe、状态矩阵和端到端 evidence |
| 60 倍单位错误 | UI 分钟直接写入 seconds，或窗口 timeout 与节点 timeout 混用 | 边界只设一个显式转换点；正整数、0/负数、最大值、溢出测试 |
| envelope 代替多区间 | lastX/周/月只产生一个宽窗口 | 附卷逐个 date_value 对 DS 区间序列，验证“所有区间成功” |
| latest 漂移 | 重试时重新取当前 workflow/version/config/time | run 初始化固化 version/config/business_date/timezone；恢复读 checkpoint |
| all_tasks 假阳性 | 任一 task 数据存在就判全部成功 | 先取固化版本启用任务全集，再逐任务存在/禁用/终态判定 |
| proxy 数据串工作流 | task 表只按 task_id/窗口查询 | execution history 必含 project/workflow/version/run/task 归属联合过滤 |
| timeout 破坏 DS 三态 | timeout 直接参与 AND/OR 且优先级无权威依据 | timeout 映射先裁定，组合器穷举测试与附卷同源生成 |
| spec 与 UI 双真源 | C9 在前端写死枚举/默认值 | component spec 契约测试 + UI 禁止私设扫描/评审 |
| 透传污染变量 | 未满足也透传、同名覆盖不确定、恢复重复写 | satisfied 门控、来源追踪、冲突规则、幂等 checkpoint 测试 |
| 外部探针泄漏/副作用 | 前端直连端点、凭据落 JSON、探针产生写操作 | 统一后端适配层、凭据引用、只读权限、审计与超时 |
| 证据附卷后补导致漏项 | 实现结束才手工拼对照表 | 测试 ID 与附卷行从 L6-01 起同步维护；L6-11 只做核验与封版 |

预研结论：增量 6 不是“补一个 C9 大表单”，而是从当前简化 API/代理判定升级为 spec 驱动、冻结快照、真实执行域判定和可恢复 tracker 的端到端能力。现有代码可以复用条件校验、基础窗口、持久化和两层组合骨架，但九能力中仅有部分能力达到“已编码”，没有任何证据支持当前宣告 S4 100% GREEN。按上述 11 票推进并完成 A5 附卷独立评审后，才具备关闭增量 6 的条件。
