## 三 逐项结论

### F1 ✅ 认可 —— 逆向三端点无需独立权限点（材料①）

- 旧侧 A6-18/19/20 **全部** `require_perm("model:write")`（`api/model.py:599/643/689`），
  **没有**任何独立权限点（无 `model:reverse` / `model:scan` 等）。
- 新侧三端点 → `EDIT_DEFINITION`；`EDIT_DEFINITION` 持有面 {admin, developer}
  与旧侧 `model:write` 持有面 {admin, dev} **逐角色一致**。
- **结论：认可** 沿用 `EDIT_DEFINITION`，不为逆向端点引入独立权限点。
- 回改面（若日后裁定变更）：仅 `PERMISSION_MAP` 3 行，契约测试已锁定行为，成本低。

### F2 ✅ 认可 —— 权限粒度为**域级**，与旧侧一致

- 旧侧建模域：2 个权限点（登录 / `model:write`），22 端点。
- 新侧建模域：2 个 `Permission`（`VIEW_ALL` / `EDIT_DEFINITION`），22 端点 → 9 个 operation key。
- 无端点级独立权限点 → **粒度一致**。

### F3 ✅ 认可 —— `/models/er` 旧侧双注册与新侧单注册语义等价

- 旧侧 `GET/PUT /models/er` **各注册两次**：`:191/:196`（静态壳，委托）+ `:421/:435`（实现）。
  静态壳体为 `return get_er(...)` / `return put_er(...)`，**纯委托**。
- Starlette 按注册序首个匹配生效 → 实际生效者为静态壳，语义 = 实现体。
- 旧侧注释 `:185` 明示意图：「Static ER routes must be registered before the integer model-id route below」
  —— 防 `/models/er` 被 `/models/{model_id}` 吞并。
- 新侧**单次注册**（`api.py:220` GET / `api.py:237` PUT），且注册次序
  `GET /models/er`(:220) **先于** `GET /models/{model_id}`(:262) → 等价且满足防吞并约束。
- **结论：认可**（旧侧双注册为无害冗余，非缺陷）。

### F4 ✅ 认可 —— 鉴权失败信封为 fail-closed

- 新侧 `authorize()` 对未知角色/权限**默认拒绝**（`contracts.py:106-107`）
  ↔ 旧侧 `perm not in ROLE_PERMS.get(user.user_role, [])`（`api/auth.py:117`）→ 语义等价。
- 403：新侧 `fail(1004, "无操作权限")`（`api.py:174`）↔ 旧侧 `NO_PERM = 1004`（`common/resp.py:17`）→ ✅
- 401：新侧 `{"code":1001,"msg":"invalid token"}`（`api.py:178`）↔ 旧侧 `TOKEN_INVALID = 1003`
  → **⚠️ 已知分歧，非本评审新发现**（17.2-01 起即登记的候核项）。见 F10。

### F5 ⚠️ 候裁 —— 读端点权限粒度：`analyst` 角色在新侧缺失

- 旧侧读端点只要求**登录**（`get_current_user`），不校验权限点；4 角色（admin/dev/analyst/viewer）
  均可读。
- 新侧读端点要求 `Permission.VIEW_ALL`；而 `Role` 枚举仅 4 值
  （`ADMIN`/`DEVELOPER`/`OPERATOR`/`VIEWER`，`contracts.py:14-19`）—— **无 `analyst`**。
- 旧 `analyst`（持有 `run_instance`, `view_all`）在新侧由 **I23 身份映射**为 `operator`
  （`tests/rebuild/test_governance_legacy_i23_mapping.py:31` 已锁定 `role="operator"`）。
- **风险**：若 `analyst` 未走 I23 映射直接登录 rebuild，`Role("analyst")` → `ValueError`
  → `authorize` 返回 False → **403**；旧侧同场景为 **200**。
- **建议**：维持现状（由 I23 映射覆盖），在 **I1 身份域**候核登记；本评审不擅自增删角色。
  若裁定新增 `ANALYST` 枚举值，将连带影响 `OPERATOR` 的 17 项权限面，须整体重估。

### F6 ⚠️ 候裁 —— `viewer` 权限面较旧侧放宽

- 旧 `viewer` = {`view_all`}（**1** 项）
- 新 `viewer` = {`VIEW_ALL`, `PROJECT_READ`, `WORKFLOW_READ`, `TASK_READ`, `DATASOURCE_READ`,
  `SQL_READ`, `SCHEDULE_READ`, `LINEAGE_READ`, `QUALITY_READ`, `STANDARD_READ`}（**10** 项）
- **对建模域无影响**（建模域只用 `VIEW_ALL` / `EDIT_DEFINITION`）。
- **对其他域有可观察差异**：新 viewer 可读 workflow / task / datasource / sql / schedule /
  lineage / quality / standard，旧 viewer 不可读（旧侧这些端点多要求专属权限点）。
- **归属**：I1 RBAC 角色装配决策（RBAC-01/02/03 已由 Trae 核查收口、RBAC-08 按 S109 裁定暂缓），
  **非建模域 R3 范围**。本评审仅呈报，不擅自改动。

### F7 ⚠️ 候裁 —— 六个旧权限点在新侧 `Permission` 枚举中不存在

- 旧侧权限点 `design_component` / `publish_component` / `model:write` / `meta:write` /
  `ind:write` / `std:write` 在新侧 `Permission` 枚举（`contracts.py:21-53`）中**均不存在**。
- rebuild 全域实际引用的 `Permission` 仅 **5 种**：`EDIT_DEFINITION`(64 处) / `VIEW_ALL`(55) /
  `RUN_INSTANCE`(12) / `MANAGE_USER`(4) / `STANDARD_READ`(1) —— **无任何端点引用上述旧点**。
- **建模域无缺口**。
- **后续风险**：component_design 域票若需 `design_component`，须**新增枚举常量**。
  注：`design_component` 旧持有面 {admin, dev} 与 `EDIT_DEFINITION` 新持有面
  {admin, developer} **恰好一致**，但**语义不同不应合并** —— 合并会让「改组件设计定义」
  与「改数仓模型定义」共用一个权限点，丧失最小授权粒度。
