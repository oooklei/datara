# Codex 对 handoff #48 六项评估议题的正式答复

- 依据：`docs/increments/2026-10-17-分阶段混合集成方案-设计.md` §8、标准 v4 草案、handoff #51/#59/#60/#61；本回执对 #48 六项逐一给出结论和可核验锚点。
- 总体状态：本文件关闭 Codex 对 #48 的答复欠账；不等于关闭所列后续实施或评审任务。

## 1. R8-V 主权四条与依赖锁版

**结论：采纳；补强执行验收细节。**

按设计稿 `:38` 锁定精确版本、vendor wheel 与锁文件，并禁止自动更新；`:41-51` 规定适配隔离、Datara 授权通道和主权边界；`:87-89` 登记供应链风险及并行域隔离。四条主权要求继续作为硬约束，不因使用 Vanna 而放宽。

落地验收补充：wheel 与锁文件记录 SHA-256、来源/版本和许可信息；升级必须显式改版本、可复现构建并人工评审；不允许 CI/部署脚本隐式升级。该补强是证据和流程要求，不改变已裁定架构。

## 2. Phase 0 三项 FAIL 闭环顺序与并行性

**结论：部分采纳。**

依赖图上 P0-1（A2）与 P0-2、P0-3 可并行；P0-4 依赖 A2 双线冻结，不能提前进入 GREEN 接线。见设计稿 `:100-105`、handoff #51 `:1687-1689`。提交和集成验收仍须逐批核实，不能把分支 GREEN 等同 canonical main GREEN。

最新 #61 已报告 P0-2 全链路 GREEN；P0-3 后端端点/E2E 仍在推进；P0-1 的 A2 草案已提交但双线会签未完成，所以 P0-4 仍受冻结门约束。此前 #59 的状态快照已由 #61 更新，不再沿用旧状态。

## 3. R6 加固逐能力对照与工作量

**结论：采纳四能力对照；当前不报未经分解的人日数。**

标准 v4 草案 `:131-132` 要求 R6 自研加固、不外挂 DolphinScheduler，并对重试、容错、补数、优先级逐项核对。当前可证实 Datara 已有部分机制：`datara-backend/master/engine.py:316-317,575-621` 有 retry 默认、错误分类/预算/延迟；`:2038-2054` 有优先级派发；`master/scheduler.py:74-81,313,347` 有命令优先级序；`master/failover.py:25,130` 有运行实例恢复及 failover 重建时的 priority 处理。DS 对照锚包括 `TaskRetryLifecycleEvent.java:46-59`、`TaskFailoverStateAction.java:137-142`、`BackfillWorkflowCommandHandler.java:30+`、`SerialCommandPriorityHandler.java:33+`。

这些锚点只证明机制存在，不证明行为等价、故障语义等价或验收闭环。P2-1 应先产出逐能力矩阵（触发条件、重试预算/退避、状态迁移、故障恢复、补数入口/边界、优先级稳定性、测试证据与缺口），再按依赖拆分给出区间估算。当前风险初判：failover/backfill 高，retry/priority 中；不是工期承诺。

## 4. R5-A 只读边界（U1/U3）

**结论：采纳。**

R5-A 保留对象发现、元数据读取、跨 Schema 只读查询、SQL 编辑/执行结果读取、历史与导出等只读能力；DDL 执行、对象编辑持久化、发布/审计写闭环及回滚进入 R5-B 的后续冻结与验收。依据标准 v4 草案 `:119-125`、设计稿 `:72`、handoff #51 `:1690`。

`ObjectSource.editable` 或类似能力标记只表达驱动支持能力，不等于用户授权、项目权限或允许 R5-A 写入。DDL 精读仍是实现前置研究，不代表 R5-A 开放 DDL 执行。

## 5. 并行轨撞车风险保障

**结论：部分采纳，细化共享区写入门禁。**

独立文件域可并行。共享 handoff/编号池、canonical main 暂存区与提交区串行写入：先核对最新编号；同一文件设置单一 owner；提交限定单 pathspec；stage 后逐字检查 staged diff；发现冲突时保留两方原始变更并交文件 owner 合并裁定，不覆盖他人内容。依据 handoff 起始约定 `:14-17`、#51 `:1691`、#52 `:1722-1724`。

子智能体可做隔离只读调查；报告/代码结论须由主智能体复核源码或文档锚点后采纳，避免未经核实的二手结论进入正式回执。

## 6. D9 分工及 Phase 3 预研边界

**结论：采纳分工与阶段门。**

Trae 主研 DBX 全量能力与原版 SQLIDE 融合清单；Codex 做独立评审、锚点复核和异议回执。依据设计稿 `:20,:58,:60` 及融合清单 `:1-6,:8-25,:38-46`。D9 冲突/歧义以 DBX 为准；原版 UI 优势作为候选吸收项，不得反向覆盖 DBX 语义。O7 未证实内容必须继续明示。

正式 Phase 3 前端融合改造需等待后端能力冻结、七项协议和运行验收前置满足；Phase 1 可开展 DBX 研读、融合矩阵和风险预研，不提前把研究文档称作后端实现完成。当前 Codex T-1 回执对融合清单判定 FAIL（修订后复评），详见 `2026-10-17-Codex-T1-P1-7-review.md`；因此 D9 的分工已答复，但 P1-7 本身尚未通过验收。
