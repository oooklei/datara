1. **提交纪律**：每任务恰一提交，message 格式 `<type>(<scope>): [T-xx] <描述>`，type/scope 沿用仓库现有风格（feat/fix + 域名）。

3. **约定沿用**：契约测试命名（`__tests__/*.contract.test.ts`）、后端测试命名（`tests/rebuild/test_*.py`）、`routes.contract.test.ts` 基线同步、`BATCH_SWITCHES` 菜单候批模式、登记簿门禁——**全部沿用 codex 既有惯例，不引入新范式**。
4. **汇报**：每任务完成向用户一句话汇报（任务号 + 提交号 + 测试结果）。
5. **偏差处理**：实施中发现与计划不符（如审计发现已有实现、白名单位置与预判不符）→ 缩减/调整任务，在 §7 变更记录追加一行，不静默改道。

## 6. codex 回归接续设计（本计划的核心约束）

**原则：codex 回归后 10 分钟内可无损续作。**

1. **同区同分支**：全部代码工作发生在 codex 原工作区、原分支；codex 回归即身处现场，无迁移成本。
2. **git log 即施工日志**：每提交带 `[T-xx]` 标记，`git log --oneline` 可直接对照 §3 台账还原进度。
3. **handoff 备忘**：计划副本 + 台账快照落至 C 盘工作区 `.codex-evidence/HANDOFF-20261026.md`（未跟踪文件，不污染分支；`.codex-evidence/` 本就是 codex 自查其证据的首选目录）。codex 回归时 `git status` 第一眼即见。
4. **权威分离**：本计划权威版在 D 盘 `docs/increments/`（文档权威区）；C 盘仅放工作副本（遵循"Agent worktree 仅代码隔离，不作文档/状态权威"）。
5. **接续动线（codex 回归后）**：
   1. 读 `.codex-evidence/HANDOFF-20261026.md` → 指回本计划权威版；
   2. `git log --oneline -20` 对照台账，确认已完成任务与提交号；
   3. 工作区若干净且存在 `pending` 任务 → 从第一个 pending 续作（沿用 §4 协议，取消豁免、恢复正式流程闸门）；
   4. 若台账全部 `done/closed-noop` → 直接进入统一核验（差距报告 §7 放行门）；
   5. 若发现工作区有我方遗留未提交件（违反 §4.2 的异常）→ 以 `git stash list` 与台账提交号核对后处置。
6. **互不踩踏**：我不改写 `.codex-evidence/` 既有内容、不动 codex 未跟踪证据件；新增仅限 handoff 备忘一个文件。
