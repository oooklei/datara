## 1. 设计原则与安全边界

1. R5-A 与 R5-B 分门：R5-A 提供受项目授权的只读对象定义和查询能力；R5-B 才执行对象定义变更。R5-A 的 `getDefinition` 由 R5-B 编辑流程复用，不复制 source-reader 或创建第二条 wire route。
2. “P2-2 GREEN + A5 生效”是进入 R5-B 生产实现的全局门。进入后仍需逐方法满足 A5 与标准 v4 A1-A7；前置通过不代表任一 R5-B 方法已实现或可写生产目标库。
3. 每次校验和提交绑定同一 `projectId + datasourceId + 完整 ObjectRef + sourceVersion/ETag + nextDdlText digest`。对象版本或文本变更后，旧 policy/impact/confirm 证据不得重用，返回稳定 409。
4. 写入只允许经服务端权限、策略、影响预览和用户确认闸。Agent 不代填 `confirmPhrase`；数据库 driver 的 `editable` 声明不授予 Datara 用户写权限。
5. 不确定的权限、对象身份、方言、依赖影响、恢复能力一律显式 `unknown`/`unsupported` 并阻断需要该能力的提交；不得按空列表、无影响或成功状态处理。
6. 普通历史清理不得级联删除 DDL 审计/执行记录；平台记录本身仍必须按 project ACL、最小凭据暴露和审计要求保护。

## 3. DDL 写入生命周期

### 3.1 权威八步

依核心设计正本 §13.6，单次写入严格执行：

```text
权限校验
→ 依赖检查
→ 影响对象预览
→ DDL 脚本快照
→ 用户确认
→ 执行
→ 结果记录
→ 失败回滚或补偿脚本
```

八步是职责/顺序合同，不代表失败后所有数据库 DDL 都能事务回滚。R5-B 设计深化必须逐 driver/ObjectKind 明确原子性与补偿能力；无法安全恢复的操作应在执行前 block/unsupported，不得承诺虚假的自动回滚。补偿动作本身需再次授权、记录并验证结果。

### 3.2 端到端状态和绑定

1. **读取与授权**：认证主体 → project membership → datasource 所属项目 → ObjectRef 的读取/写入权限；不可见资源跨项目返回 404，已可见但缺少操作权限返回 403。取回定义及 `sourceVersion`。
2. **策略校验**：提交 `nextDdlText`，计算其 digest；服务端生成 policy snapshot（snapshotId、project、datasource、ObjectRef、sourceVersion、DDL digest、policy version、findings、createdAt/expiry）。任何 block 阻断后续 confirm。
3. **影响预览**：使用同一目标/版本/文本和 policy digest 生成 impact snapshot；明确对象依赖、下游、权限范围与 unknown；不能将“未查到”表示为“无影响”。
4. **冻结提交意图**：用户确认请求携带完整 ObjectRef、base sourceVersion、next DDL、policy/impact snapshot IDs 与 `confirmPhrase`。服务端验证调用者、授权、短语、快照有效性、全部 digest 一致和 sourceVersion CAS；任一不一致均拒绝且不执行。
5. **前像和执行**：执行前保存原定义/可恢复前像，建立 DDL 专属持久 record；写权限与只读查询凭据分离，执行器按已验证 capability 进行单一目标操作。不得接受任意 SQL、绕开 ObjectRef 或把 R5-A query port 升权为写端口。
6. **记录和终态**：保存操作者、项目/数据源/对象、脚本 hash、执行时间、policy/impact refs、结果、失败摘要及 compensation refs；记录不得写连接凭据、用户确认短语或不必要的定义明文。稳定区分 success、failure、rolled-back/compensated 与恢复失败。
7. **补偿/回滚**：仅按相应 driver/ObjectKind 经验证的恢复方案执行；执行自身另记 actor/action/outcome。回滚失败进入显式人工恢复状态，不伪装为原操作失败已恢复。

当前 A5 #24 没有冻结更细粒度的 idempotency/并发令牌字段；R5-B 子契约需在不削弱上述绑定条件下明确重复提交的冲突行为和重放保护，并按契约版本管理，不得在实现中私自改变 v1.0 请求签名。

| ID / 优先级 | 契约锚点与现状 | 必须交付 | 验收证据与解除门 |
|---|---|---|---|
| **G-B1 P0：DDL 执行器** | A5 #24；设计正本 §13.6 八步；当前无生产写 executor。 | 仅按 ObjectRef/driver capability 执行受控 DDL；隔离只读与写连接、超时/取消/连接销毁策略；不给任意 SQL 写入口。 | A1 先红后绿；真实目标 DB 成功/拒绝/权限/超时用例；证明 read-only path 不能写、写账户不能跨项目/目标；P2-2 GREEN 后接入。 |

| **G-B5 P0：DDL 专用执行记录** | A5 #24/#25 与 §5（append-only ≥365 日）；设计正本 §13.6 结果记录。 | 新建或明确扩展 DDL ledger，记录 actor/project/datasource/ObjectRef/action/script hash/time/outcome/failure/compensation refs；独立 retention，不随 SQL history 删除。 | 成功/失败/补偿/补偿失败全状态可分页回查；跨项目隐藏 404、缺权限 403；TTL/删除集成测试证明 audit 不级联丢失；R5-A query audit 不替代此项。 |
| **G-B6 P0：Policy snapshot 绑定** | A5 #22；A5 §1 第 12 条版本漂移 409。 | 持久或可验证的不可变 policy snapshot，绑定 project、datasource、ObjectRef、sourceVersion、DDL digest、policy revision、findings、expiry。 | block 永不可 confirm；任何绑定字段变化、snapshot 过期/伪造或 sourceVersion 漂移均拒绝；相同有效 snapshot 可审计重读。 |
| **G-B7 P0：Impact snapshot 绑定** | A5 #23/#24；影响预览提交前必展示并与 policy digest 同源。 | 可审计 impact snapshot，绑定同一 ObjectRef、sourceVersion、DDL digest 与 G-B6 policy snapshot；包含影响对象与 unknown 理由。 | confirm 必须引用有效 impact snapshot；变更定义、对象版本、权限范围或 policy digest 后旧 snapshot 失效；真实 unknown 与权限过滤用例通过。 |

### 4.1 跨项门禁（防止 G-B1~G-B7 拆项漏掉安全合同）

- **授权与 CAS（覆盖 #21-#25）**：逐请求 project/datasource/object ACL；完整 ObjectRef；sourceVersion/ETag 在 read→policy→impact→confirm 一致，变化 409。分别覆盖不可见 404 和项目内权限 403。
- **snapshot 与前像闭环（覆盖 G-B2/G-B6/G-B7）**：前像、policy 和 impact 都必须与同一对象、版本及 DDL digest 绑定；保存与验证顺序有原子边界，不能只把 snapshotId 当无内容的占位字段。
- **审计与失败闭环（覆盖 G-B2/G-B5）**：写操作和补偿动作独立形成记录；成功、失败、部分变更、恢复成功、恢复失败有明确终态；禁止把 R5-A query audit update 当作 append-only DDL ledger。
- **契约版本**：若 R5-B 细化请求字段、状态或失败枚举，按 A5 §6 升版本并双线会签；不得静默改变冻结 v1.0。
