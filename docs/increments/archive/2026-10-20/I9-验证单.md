### seek 修复验证（I8 验证单·遗留观察项 1 → 销项）

场景：流任务重启按已提交位点续跑，不整题重放（独立 topic + 独立 consumer group，隔离历史数据）。

| 阶段 | 期望 | 实测 |
|---|---|---|
| ① 首跑消费 10 条 | totalIn==10 | **10** ✓ |
| ② stop → 追投 5 条 → run 重启（同 job 同 group，restarted=true） | 新代际 totalIn==5（修复态）；==15 即 earliest 整题重放（未修复态） | **5** ✓ |
| ③ 位点终值 | `datara-i9seek-<ts>:0 → 15` | **15** ✓ |

- 判定依据：`worker/stream/engine.py` L55 `total_in = 0` 为每代运行时实例字段，重启后代际计数从 0 起 → 5=按位点续跑仅消费新消息；15=earliest 重放（修复前路径）
- VERDICT：`{"pass":true,"j1_totalIn":10,"restart_generation_totalIn":5,"offsets_final":{"src1:kafka":{"partitions":{"datara-i9seek-1789830750:0":15}}}}`

## 二、实测发现并修复的缺陷（已部署 1.9 复测通过）

### 1. listDefinitions 传 page_size=500 触发后端 422 → 任务中心画布整片空白（门6 抓出，F56d 引入）

- 现象：real 模式 /#/dag 工作流页签内容区空白，GraphWorkbench 不挂载；ETL/流页签同样空白。角色回归首轮 6 项 FAIL（保存按钮=0 / 画布直达失败）。
- 根因：[graphApi.ts](../../datara-web/src/services/graphApi.ts) `listDefinitions` 无 tag 分支透传 `pageSize:500`（TaskCenterView loadDefPool 传参），tag 分支硬编码 500；后端 `PageQuery` 校验 `page_size ≤ 200` → **422 Unprocessable Entity** → `loadDefPool` catch 吞掉留空池 → `docIds` 全空 → 画布 v-if 不渲染。本地 vitest 无真实分页上限覆盖，静态门无法发现。
- 修复：两分支统一钳制 200（`Math.min(pageSize, 200)`；定义量几十级足够）。重建部署后 26/26 全绿。
- 教训：mock→真切换类改动，**前端传参需对照后端 Pydantic 校验边界**；回归矩阵必须包含候选池渲染项（已纳入本轮回归）。

### 2. 部署过程性修正（非代码缺陷）

- **mv dist 导致 bind-mount 悬挂**：按 deploy_i9.sh `mv dist dist.bak && mkdir dist && tar 解压` 覆盖前端时，容器 bind-mount 仍指向旧 inode（即 dist.bak），新 dist 目录容器不可见 → nginx 持续返回旧包（index-B9iQLCCc.js）。`docker restart datara-web` 重新挂载后生效（新包 index-aYrK1pSy.js）。
- **处置沉淀**：后续覆盖前端一律「原位清空 + 解压」（保 inode）或覆盖后 `docker restart datara-web`；F59 install.sh 发布包按此修订。
- api/worker 容器重启后 nginx upstream IP 失效 → 8090 代理 502（docker 内嵌 DNS 不更新已解析 upstream）→ 同样以 restart datara-web 恢复。
