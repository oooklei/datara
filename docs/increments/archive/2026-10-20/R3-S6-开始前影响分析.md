## S5 → S6 影响范围

- S5 新增独立静态页 `datara-web/public/rebuild-validation-r3.html`，不改变正式 Vue、菜单、路由或 SPA 构建入口；页面所有业务交互调用 R3-S4 governance API。
- S4/S5 API 依赖 12 张 `rebuild_governance_*` 业务表及 `rebuild_schema_migration` 版本表。生产启动只建 I1 核心表，因此远端尚无这些表时不能据页面/API 500 推断页面缺陷。
- S6 仅操作隔离的 `datara_rebuild_i0`，迁移版本为 `r3_0001_governance_catalog`，由 `MigrationRunner` 的 MySQL `GET_LOCK` 序列化后创建版本表与 12 张治理表。DDL 为 `CREATE TABLE IF NOT EXISTS`/`create_all(checkfirst=True)`，不含 DROP、TRUNCATE、DELETE、改名或旧业务表写入。
- S6 只读盘点证实：容器 DB 配置解析为 `mysql-meta/datara_rebuild_i0`；schema 目前仅有 3 张 I1 核心表，R3 governance 表数为 0；API 容器与 MySQL healthy、API 最近 10 分钟错误标记为 0。远端挂载 `/lei/datara/rebuild-source/rebuild:/app/rebuild`，S4 governance 模块和路由在该运行包中缺失。共享的 `common/db.py`、identity/project 模型哈希与本地相同；`api/app.py` 需增加治理 router 导入/注册。
- 为满足迁移前 dry-run，已新增只读 `migration_preflight.py`（只用 Inspector/SELECT，不创建版本表）及必须显式选择 `--dry-run` 或 `--apply` 的 `migration_apply.py`。`--apply` 强制 MySQL 且 database 精确等于 `datara_rebuild_i0`，先做预检，后应用唯一路径 revision 并检查 migration/postflight；错误/冲突 fail closed。
- 此版迁移只建表，不执行 I18-I23 历史数据导入；导入映射与迁移批次后续另行验证，不以空表创建冒充资产承接完成。
- S6 失败恢复证据必须区分 migration tracking 的 failed/running 状态与 MySQL DDL 的非事务性：不能声称普通事务 rollback 能撤销已提交 DDL。修复/重试只允许基于 schema 对比和原 revision/checksum；任何表结构冲突先停止，不覆盖人工或第三方对象。

## 目标与非目标

目标：在 192.168.1.9 的专用隔离 schema 完成只读前置快照、dry-run 计划、授权范围内的 additive migration、重复执行幂等检查、表/列/索引/外键/时间戳检查、后端健康与日志核对，并保留能安全恢复的证据。通过后方可启动 S7 页面部署与控制级验收。

非目标：不改 `datara_meta`、`datara_dw`、`ec_retail`，不迁移/回写 I18-I23 数据，不部署新业务版本（除非远端现行 API 未含已批准 S4 代码且需单独先做影响分析），不删除治理表，不重建 Web 容器，不改变 18091 端口，不以 curl/API-only 替代 S7 UI 验收。

## 细化执行步骤与停止门

1. 只读确认服务、API health、挂载、解析后的目标 schema、版本表和治理表状态；若 schema/账号无法唯一确定或发现非预期对象，停止。初次盘点见 `evidence/R3/s6-remote-readonly.txt`。
2. 本地 `--dry-run` 已用 SQLite 验证只读、不写版本表、不写业务表、检测不兼容同名表及 completed revision 缺表。远端必须执行同一已验证版本的 `python -m rebuild.governance.migration_apply --dry-run`；报告新增/现存对象、冲突数和目标必须唯一。
3. 由于远端 I1 API 运行包缺少已完成的 S4 router 与 migration CLI，先对隔离挂载中的唯一 `api/app.py` 做远端只读/本地候选 diff；迁移前备份现有 `api/app.py` 到受控唯一目录。将 S4 governance package 与两个 migration CLI 经临时 staging 目录同步、校验 sha256 后原子移入；用同版本预检器 `--dry-run`，未通过则不 restart、不执行 DDL。
4. 在治理 schema 完全为空、目标唯一、dry-run 无冲突且迁移前 schema-only 备份/恢复路径已确认后，显式执行 `python -m rebuild.governance.migration_apply --apply`。禁止应用整个 Base；migration runner 只创建 `GOVERNANCE_TABLES` 与其独立版本表。
5. 核对 12 张治理表 + 1 张版本表、列/default/index/FK/unique、checksum、completed/attempt_count；第二次 `--apply` 应报告 applied 空且 skipped 含唯一 revision；核对后端日志和 health。之后原子切换 `api/app.py` 候选并仅重启 `datara-rebuild-api`，health 必须恢复。若代码发布失败，将备份 `app.py` 原子恢复并重启；新增治理代码留存但不被旧入口加载。DB rollback 不做 DROP，保留失败后置并记录。
6. 记录迁移前后 schema 指纹、预检/执行器输出、实际 restart/health 与日志摘要到 `docs/increments/evidence/R3/s6-remote-migration.txt`。S7 才部署/使用 S5 页跑真实控件闭环。
