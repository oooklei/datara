# I13 统一基础设施硬化设计

日期：2026-10-01  
状态：实施中

## 1. 设计目标与边界

本增量以 I12 和 2026-10-01 最新血缘实现为基线，不重做组件目录、基线工作台和血缘模型。目标是让三个重点域形成同一条真实闭环，并清理会误导用户的演示数据。

硬边界：数据开发 IDE 前后端功能不改；V3 需求规格仅参考；本机不承担运行验证；生产目录不直接覆盖。

## 2. 最终方案

### 2.1 组件目录与基线化工作台

- `components/catalog.py` 是执行类型集合的唯一代码源；`common/dag_catalog.json` 是前后端消费快照，不另建平行目录。
- 内置组件走基线进度、底稿、体检、认可发布；用户组件走草稿、冻结版本、发布、下线、回滚和影响面。
- 画布以 `componentRef` 固定发布版本；保存宽松兼容存量，发布严格拒绝缺失或漂移引用。
- 目录一致性、执行器覆盖、表单契约、基线闸门继续由现有测试守护。本轮只验证，不改业务模型。

### 2.2 血缘分析

- 保持设计态与运行态双源，按 `src_type` 汇总；表级、字段级、转换表达式和实例追溯分层呈现。
- `/lineage/graph` 提供方向、深度、来源、中心资产和上限参数；结果确定性聚合并显式报告截断。
- 工作流保存/发布/删除/回滚触发设计态重算；运行完成回写运行态证据。
- 本轮执行最新全量回归与 1.9 接口探针，不再引入第三套声明级血缘存储。

### 2.3 运行时节点与集群监控

- ZooKeeper 是 master/worker 在线性真源；Redis 保存短期资源指标，并以 7 天已知节点索引呈现离线节点；SSH 节点以注册表探活为真源。
- 页面只展示后端能证明的节点、指标和时间，不展示虚构的 Prometheus、Flink、Doris、DolphinScheduler 服务状态或随机趋势。
- 30 秒轮询维持单一定时器；失败保留上次成功数据并显示错误，避免空白和定时器膨胀。
- Kafka 纳入默认 Compose，使用远端已验证的 `bitnami/kafka:3.7`，worker 等待健康后启动。

### 2.4 告警闭环

- `system` 代表数据库持久化站内消息；webhook/邮件必须显式配置并由适配器确认成功。
- 未配置、不支持或投递失败进入 `fail`，禁止误记 `sent`。
- 真实模式顶部消息中心读取持久化告警 API，mock 仅保留在显式 mock 模式。

## 3. 验收门

- 本机：Python compile/ruff、TypeScript 类型检查、`git diff --check`、目录/IDE 保护审计。
- 1.9 隔离目录：后端全量 pytest、前端 vitest/vue-tsc/build、`docker compose config --quiet`。
- 1.9 运行探针：Kafka health、`/health`、`/components/stats`、`/components/baseline/progress`、`/lineage/stats`、`/lineage/graph`、`/monitor/nodes`、`/alerts`。
- IDE 保护：本增量差异中不得包含 `api/ide.py`、`views/ide/**` 或 IDE 服务契约文件。

## 4. 回滚与发布

所有验证先在隔离目录执行。代码合并与生产部署分离；任何运行验证失败先记录证据、修复并重跑，不以“服务能启动”替代功能验证。
