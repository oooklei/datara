## 2. 演进脉络（由远及近）

1. **早期规格与讲解稿**：提出一站式集成、开发、治理、安全、开放服务、运维的完整平台愿景；覆盖面大，但大量模块停留在原型或演示数据。
2. **重置方案与组件清单**：收敛到单一 DAG 工作台，取消独立 ETL 画布，以 SQL/同步/流组件组合业务流程，形成 C1～C23 组件边界。
3. **I1～I3 平台基座**：落地五后端模块、MySQL/Redis/ZK、认证、定义/实例/调度、worker 执行和容错基础。
4. **I4～I6 数据能力**：落地数据源、文件、临时数据、SQL 血缘、动态 Schema、多源同步和分批处理。
5. **I7～I8 稳定性与实时能力**：落地运行节点、变量、SSH、多 worker 竞争、自愈、Kafka/CDC/HTTP/文件流源和流任务常驻状态。
6. **I9 产品化**：区分真实与演示模块，收敛信息架构和画布交互，补发布包；但根编排、真实消息中心与扩容方式仍存在历史割裂。
7. **I10 IDE 收口**：Monaco、懒加载资源树、异步执行/SSE、取消、历史、脚本、表数据操作等闭环。该模块从 I11 起冻结。
8. **I11 当前任务**：不再横向铺设大而全的 mock 页面，转为打通真实链路、补齐部署依赖和自动验证，并让每个常驻组件有清晰、可观察的职责。

## 3. 最终需求目标

### 3.1 大目标

Datara 是面向内部数据团队的一体化数据处理工作台：用户从数据源接入开始，以统一 DAG 和 SQL IDE 完成批处理、同步与实时任务，系统自动承担调度、容错、血缘、日志、告警和运行监控；产出遵循 ODS→DWD→DWS→DIM/ADS 的分层规范，TMP 只承载可清理的运行中间数据。

### 3.2 最新细项目标

- **接入**：MySQL/GreatDB/文件为注册数据源；Kafka/CDC/HTTP/文件尾随作为流输入；连接测试、最小权限和错误可读。
- **开发**：DAG 是批处理、同步、流处理的统一编排入口；IDE 维持 I10 终态，不再改功能。
- **执行**：定义、版本、调度、实例、任务、日志、变量快照和血缘能够闭环；失败可停止、重跑或自动恢复。
- **分层**：同步默认进入 ODS，清洗进入 DWD，汇总进入 DWS，再输出 DIM/ADS；系统以模板、命名校验和运行提示引导，而不是另建一套画布。
- **实时**：流任务具备持久化位点、断流重连、宿主失联接管、真实指标与日志；Kafka 是标准部署依赖而不是手工外挂。
- **告警**：system 通道形成站内消息；webhook/邮件仅在配置完整且投递成功后标记 sent，失败必须留为 fail 并可观察，禁止“打印即成功”。
- **运维**：根编排可一键启动完整依赖；健康检查反映真实依赖；worker 能按标准 compose 方式扩容；服务、日志、告警和流任务均可观测。
- **产品边界**：未接真实后端的功能只放在“扩展（演示）”，真实菜单不得混入 mock；废弃入口重定向但不继续扩建。
- **质量**：后端单测、前端单测/类型检查/构建、compose 静态校验和核心 API 冒烟成为提交门禁；验证单只记录可重放证据。

## 4. 最终架构与职责

```text
Web
 ├─ 真实域：任务中心 / 数据源 / 同步 / IDE(冻结) / 血缘 / 流任务 / 运行节点
 └─ 扩展域：明确标识的演示页面
          │ REST / SSE / WS
API ──────┼─ 认证、定义、实例、数据源、血缘、流任务、站内告警查询
          │
Master ─ Redis Stream ─ Worker(n)
  │                       ├─ 批任务/同步/脚本/SSH
  │                       └─ 轻量流引擎 ─ Kafka/CDC/HTTP/File → Sink
  ├─ MySQL(meta)          
  ├─ ZooKeeper（注册发现）
  └─ Redis（队列、会话、指标、实时缓存）

Alert：消费 t_alert_record → system/webhook/email 适配器 → 明确 sent/fail
Logger：共享日志卷的受控查询服务；API 网关复用同一查询逻辑
```

组件原则：API 不执行长任务；Master 只编排；Worker 执行且可横向扩容；Alert 不伪造成功；Logger 只读取受控日志目录；Kafka、Redis、ZK、MySQL 都必须在部署与健康门中体现其真实角色。

## 5. 当前实现差距

| 优先级 | 差距 | 影响 | I11 处置 |
|---|---|---|---|
| P0 | 根 `docker-compose.yml` 缺 Kafka，而流引擎已把 Kafka 作为核心输入/输出 | 一键部署无法复现 I8/I9 能力 | 纳入 Kafka KRaft、持久卷、健康检查和 worker 依赖 |
| P0 | alert 将占位日志直接置 `sent` | 产生虚假成功 | 引入投递适配器与逐条状态收口，补单测 |
| P0 | real 模式顶栏消息仍读 mock dataStore | 用户看到非真实运行状态 | 增加只读告警 API 与前端真实消息服务 |
| P1 | worker 固定 `container_name`，标准 `--scale` 不可用 | HA 验证只能手工起容器 | 本轮先形成迁移方案；脚本仍大量依赖固定名，待脚本服务名化后一并切换，避免半迁移 |
| P1 | 流列表是真实 API，但详情仍夹杂 Flink/Checkpoint 演示语义，路由整体标 demo | 能力和展示不一致 | 列表按真实能力保留；详情明确“引擎实际能力/未提供”，不宣称外部 Flink 能力 |
| P1 | 根 README 缺失、web README 为模板 | 无法可靠交付与复现 | 建立根运行手册，替换模板说明 |
| P1 | 后端仅 4 个自动化测试，前端依赖未安装时门禁不可运行 | 回归风险高 | 增加告警、API、compose 契约测试；恢复前端依赖后执行全门禁 |
| P2 | 大量一次性诊断脚本与过时范围文档混在主资料中 | 干扰判断 | 建立权威索引；先标记归档，不直接删除追溯证据 |

## 6. I11 实施分期

### 6.0 三项重点目标（用户 2026-10-01 追加，优先于一般优化）

#### A. 组件目录与基线化 DAG 工作台

- 组件目录是 C1～C23 的唯一纲目，必须同时描述：组件编号、前端节点类型、表单契约、运行形态、后端处理器、是否可运行、验证状态。
- 基线工作台统一承载拖拽、连线、校验、表单、版本、变量、运行、日志、血缘与流指标；业务模块不得复制第二套不一致的组件定义。
- 建立前后端组件契约清单与自动测试，防止 `dag.ts`、master 派发白名单、failover/scheduler 白名单、worker 执行器再次漂移。
- 模板节点只在设计时展开，不进入后端运行态；流组件走独立常驻流引擎，不伪装成批任务执行器。

#### B. 血缘分析新增量

- 运行时成功 SQL 与 C17 同步是当前真实采集源；解析或落库失败旁路任务，但必须日志可见。
- 表级、字段级、实例追溯、上/下游深度、影响分析、转换表达式必须共用同一组真实边，不引入前端虚构影响对象。
- 新增量重点补齐：分页/规模保护、循环与孤点容错、按实例/工作流/表过滤的一致性、字段溯源选择最新边、采集与查询契约测试。

#### C. 运行时节点与集群监控

- `t_ssh_node` 是远程运行节点权威来源；ZK 临时节点是 master/worker 在线性的权威来源；Redis 指标仅用于资源数据，三者不得互相冒充。
- 运行时节点页负责注册、探活、标签路由与资源状态；集群监控页必须以真实注册节点/指标为主体，静态服务器、Prometheus、DolphinScheduler、Flink/Doris 等演示数据不得出现在真实主视图。
- 明确 `online/offline/unknown/stale` 语义、指标时间戳和 ZK 降级状态；故障时保留上次数据但必须显示过期，不得静默假装正常。
- worker 标准扩容、任务分摊与失联接管是基础设施终验，安排在固定容器名脚本迁移之后。

### I11-A：真实性与可部署性（本轮执行）

1. Kafka 进入根编排并有健康检查、持久卷；更新部署说明。
2. 告警投递从占位改为 system/webhook/email 适配器，失败不冒充成功。
3. 新增告警查询 API，真实模式顶栏读取真实告警；mock 模式保持原演示数据。
4. 流处理页面去除与实际引擎不符的宣称；主菜单只展示已接真能力。
5. 增加契约测试、README、过程记录和验证单。
6. 建立 C1～C23 组件运行契约并修复 master/worker 白名单漂移。
7. 对血缘新增量做契约与边界测试；将集群监控主视图从混合 mock 收敛为真实节点数据。

### I11-B：可伸缩部署（后续连续任务）

1. 将运维脚本从固定容器名迁移到 compose 服务名与 project label。
2. 移除 worker `container_name`，验证 `docker compose up --scale datara-worker=2`、任务分摊和故障接管。
3. 清理/归档只适用于旧固定容器名的诊断脚本。

### I11-C：数仓分层产品化

1. 在 C23 模板中提供 ODS→DWD→DWS→DIM/ADS 标准模板。
2. 对目标表名提供可关闭的分层提示和 TMP 生命周期提示。
3. 用端到端样例验证同步、清洗、汇总、维度、应用输出及血缘。

### I11-D：治理真实化

只按真实后端逐项启用质量、标准、指标、安全和开放 API；每启用一项即从“扩展（演示）”移出，禁止仅靠页面 mock 宣称完成。
