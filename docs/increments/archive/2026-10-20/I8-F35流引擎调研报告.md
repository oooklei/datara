## 1. 海豚流任务机制现状结论：**无原生流任务框架，仅"外部引擎提交器"级插件**

| 核查点 | 结论 | 证据 |
|---|---|---|
| dev 分支任务插件全目录（34 个） | 流相关仅 `flink-stream`、`seatunnel` 两个**外部引擎提交器**；**无** Kafka 生产/消费插件、**无** binlog/CDC 插件、**无**通用流任务框架 | [task-plugin 目录](https://github.com/apache/dolphinscheduler/tree/dev/dolphinscheduler-task-plugin) |
| FLINK_STREAM 本质 | Flink 作业客户端封装（把 Flink 流作业提交到外部 Flink 集群/YARN），平台本身无流执行能力；3.x 任务类型文档亦无 STREAM_TASK/KafkaTask | [3.x 任务架构对比](https://cloud.tencent.com/developer/article/2717964) |
| DSIP-16「Support stream task」提案（#11352，2022 发起） | **2024-07 关闭，仅 4 条评论，零落地**；所列能力（flink cluster manager、checkpoint/savepoint 管理、断流续跑、failover、事件调度）全部停留愿望清单 | [DSIP-16](https://github.com/apache/dolphinscheduler/issues/11352) |
| 实证痛点 | 用户跑 SeaTunnel/Flink streaming 时，DS 按批模型把任务实例"跑一次即结束"，无法正确反映**常驻流作业**状态（社区 issue 未解）；StreamPark 集成被 wontfix | [stream task issues](https://github.com/apache/dolphinscheduler/issues?q=stream+task) |
| 官方演进方向 | DSIP-16 关闭后 RoadMap 无流任务项，转向"事件触发工作流"（DSIP-22 Trigger Plugin，仍 Open）；2026 官方博客定调=时间驱动→**事件驱动+云原生+智能化**，不自建流引擎；最新版 3.4.3（2026-09-08）未改变 | [RoadMap #13459](https://github.com/apache/dolphinscheduler/issues/13459) / [官方博客](https://www.cnblogs.com/DolphinScheduler/p/20053973) / [dev 邮件列表](https://www.mail-archive.com/dev@dolphinscheduler.apache.org/maillist.html) |

**F35 第一问结论：海豚无可直接参考/复用的流任务机制**——02 清单 C18~C20"海豚无 → 依 F35 结论"成立，进入自研轻量 vs Flink 对比裁定。

## 2. 可借鉴的机制要点（DSIP-16 设计意图，未落地）与反面教训

1. 流任务=工作流 DAG 中一种节点，提供 **start/stop/savepoint/status/monitor** 生命周期操作——对齐 02 清单 C18~C20"常驻运行（Running 持续）"语义。
2. 基于上游变更做**影响分析**（主动通知流任务）——远期项，本期不做。
3. **反面教训（重要）**：DS 流任务无法 GA 的根因=**批调度内核（短生命周期任务实例状态机）与常驻流进程语义不匹配**。启示：自研路线必须为流任务建立独立于批实例的**常驻运行态**（进程/线程常驻 + 独立状态机 + 位点持久化），不能复用"跑一次即结束"的批实例模型硬套。

## 3. 自研轻量 vs Flink 对比（七个维度）

| 维度 | A 自研轻量流引擎（worker 内常驻流线程） | B Flink（平台只做提交外壳，对齐海豚 FLINK_STREAM） |
|---|---|---|
| 任务模型 | 流任务=worker 内常驻线程/子进程，独立状态机（running/stopped/failed），与 DAG 编排松耦合；C18 输入→C19 融合→C20 输出映射为一条流线程内的管道段 | Flink 作业常驻于独立 Flink 集群；Datara 只保存作业与生命周期操作；C18~C20 需翻译为 Flink SQL/DataStream 作业再提交 |
| 容错与断流恢复 | 位点自管：Kafka offset / binlog file:pos / HTTP 游标 / 文件偏移持久化（meta 库），断流自动重连+断点续跑，at-least-once | Flink checkpoint 完整 exactly-once（含状态算子快照） |
| 连接器 | Kafka 消费（kafka-python）；MySQL/GreatDB binlog CDC（python-mysql-replication，MySQL 协议兼容驱动同构）；HTTP 轮询、文件尾随均为轻实现 | Flink CDC 连接器成熟（Debezium 内核），Kafka/HTTP 生态全 |
| 性能 | 中低吞吐足够（数据治理/融合/大屏 API 场景，非亿级/秒）；python 管道单机万行级/秒 | 高吞吐低延迟、反压/窗口算子工业级 |
| 资源与运维 | **零新增集群**：复用现有 worker 容器与 Redis；1.9 单机友好 | 需部署 Flink 集群（JVM 栈，JobManager+TaskManager），1.9 单机负担大，运维复杂度+1 |
| 平台集成 | 与 DAG 编排/日志/告警/血缘/临时数据体系**同进程原生一体**；C19 转换表达式可直接复用 C11 血缘转换细节同构落库 | 需外壳适配层（提交/状态回查/日志转发/告警挂钩），血缘与转换细节需另行桥接 |
| 维护成本 | 自研代码自担（管道算子面窄：union/join/窗口聚合/过滤/映射，边界可控） | 引入外部引擎版本升级/兼容性负担，但算子能力由社区承担 |

## 4. 建议口径（待用户裁定）

**裁定建议：A 自研轻量流引擎**，理由：
1. 海豚无现成机制可参考（F35 第一问结论），而 Datara 的流场景（模拟订单流+src binlog CDC → 融合 → 大屏 API 消费，I8 实测门原文）吞吐要求中低，Flink 性能优势用不上；
2. 02 清单 C18~C20 的组件化形态（分型表单+页面化实时展示+临时数据/血缘一体化）与 worker 体系同构，自研集成成本最低；
3. 1.9 单机部署环境不适合再引入 Flink 集群；
4. 断流恢复按"位点持久化+自动重连+断点续跑"实现（02 清单 C18 已预置"断点策略（位点/偏移持久化）"表单项），满足实测门"断流恢复与容错"。

**保留备注**：若后续出现高吞吐/复杂窗口场景，可演进为 B 路线（C18 表单增加"执行引擎=Flink"分型，平台转提交外壳）——组件化设计天然预留该演进位，本期不实现。
