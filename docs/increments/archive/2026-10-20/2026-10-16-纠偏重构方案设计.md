# Datara 重建纠偏方案设计

> 日期：2026-10-16（Asia/Shanghai）  
> 状态：执行方案设计稿  
> 适用范围：Datara 重建项目的恢复盘点、客户优先交付切片和后续增量安排  
> 权威关系：本文是补充执行设计，不替代或改写《Datara 平台重建设计文档》和《Datara Platform Rebuild Implementation Plan》。产品目标以两份原始正本为准；已做工作和门禁状态以执行附录、交接记录和可复核证据为准。

## 1. 目的

本方案处理一次重建过程中的目标漂移：原始设计与计划由用户逐字研究讨论形成，后续评审文档又重排范围和执行顺序，造成目标、优先级和当前实现状态混在一起。方案的目的，是恢复原始目标的约束力，保存可复用的代码和证据，按客户现在明确提出的九项要求组织验收。

本文不授权删除历史数据、重跑已完成导入、批量回滚已有代码、绕开人工验收闸，也不把评审稿中的新增范围自动转为产品要求。

### 2.2 客户当前验收范围

客户明确提出以下要求，本文按这些要求组织首批验收：

1. 数据开发 IDE 参考 DBX，编辑存储过程、函数等对象，表、视图等对象支持跨 schema 查询。
2. 重做同步工作流组件表单，支持探查源/目标映射和用户调整。
3. 统一全局变量和工作流变量的规范；变量输入和引用都校验并显示现时值；变量编辑提供类似 SQL IDE 的补全选择。
4. SQL 组件支持上传 SQL 文件；Python 和 Shell 组件支持上传脚本文件。
5. 依赖组件表单参考 DolphinScheduler。
6. 去掉 ETL 工作流分类，将其作为普通 DAG 工作流处理。
7. 建立持续生产实时数据的工作流，供流处理结果观摩和验收。
8. 收敛 DAG 组件栏；优先同步、流、SQL、Python、Shell、依赖组件及必要控制节点。
9. 新增工作流运行结果统计后台表，除日志外记录运行成功数和失败数。

### 2.3 外部参考的使用边界

- DBX 只作为 IDE 对象浏览和编辑交互的参考，不作为新系统架构或执行引擎的依赖。本轮检索到的 [DBX Schema Browser 文档](https://dbxio.com/en/docs/schema-browser) 展示了 connection → database/catalog → schema → table/view/routine 的对象树、搜索过滤和对象上下文操作。原始设计未注明 DBX 产品 URL 或版本，因此进入 UI 验收前应记录客户指定的版本或示例截图；在此之前以客户提出的对象能力为准。
- DolphinScheduler 只用于对照依赖表单的任务、周期、日期和 AND/OR 条件组织方式，见 [Dependent Task 文档](https://dolphinscheduler.apache.org/python/tasks/dependent.html)。Datara 的状态、变量、权限和执行契约仍以原始设计为准。

## 3. 纠偏原则

1. **目标锚定原稿。** 不按评审稿的改写目标扩大系统边界，也不以其执行顺序覆盖原计划。
2. **先盘点、后取舍。** 所有分支、worktree、未提交改动、测试、远程状态和已导入数据先做只读登记，再判定保留、修正、仅作参考或待用户决定。
3. **保留可用投入。** 页面骨架、契约、测试、数据映射和执行器都按证据评价；不因文档漂移而一概丢弃，也不因投入过时间就默认接收。
4. **新 Backend 独立运行。** 旧 Backend 可作为行为参照和迁移来源，不作为重建系统运行时依赖；旧变量语法和旧接口不恢复。
5. **先闭合客户场景。** 每个切片从真实用户操作到后端执行、结果和数据记录完整贯通。接口数量和页面数量不能替代闭环。
6. **组件少而完整。** 先交付客户点名的组件，不把组件目录或历史分类直接变成用户画布。
7. **正式前端最后融合。** 先用原设计要求的独立验证页完成 Backend、接口、数据模型和执行协议验收；冻结后再做正式前端融合。
8. **不重复消费一次性闸门。** 已完成的导入、部署、审批或人工确认必须按当前证据闭环复核，不以重放代替取证。

## 5. 目标架构与跨切片契约

### 5.1 运行边界

- 新 Backend 是身份、项目、数据源、工作流定义、变量、IDE 执行、调度、运行实例、统计和流处理的运行事实源。
- 草稿只用于试运行；正式运行绑定已发布的不可变工作流版本。
- SQL IDE、工作流节点和后续 AI 助手共享数据源、变量解析、执行、日志和统计服务；不建立互不兼容的专用执行引擎。
- 第一阶段用独立验证页面驱动 Backend 验收；不提前改造正式前端菜单和主工作台。
- 数据库身份、schema、表、视图、存储过程和函数必须使用类型化对象标识；SQL 对象限定符和标识符引用按具体数据库方言生成。

### 5.2 统一变量服务

变量能力应由一个服务和一套前端控件共同实现：

- 支持原设计定义的全局、项目、工作流、任务、环境、运行和临时变量作用域；具体语法、优先级和类型以权威设计为准。
- 编辑变量时提供可搜索补全；所有组件配置中引用变量时校验变量是否存在、作用域是否可见、类型是否兼容，并显示当前可解析值或明确说明当前值不可用的原因。
- 保存草稿和启动试运行/正式运行前执行一致的校验；运行实例保存不可变解析快照，避免运行期间值漂移。
- 敏感值按原设计范围处理；本方案不引入从数据中推断敏感值或额外秘密管理产品范围。

### 5.3 工作流配置与文件资源

- 组件的表单定义、字段类型、默认值、变量引用支持和后端校验来自一份契约，不允许 UI、API 和执行器各自维护不一致字段。
- 上传文件成为有身份、有版本、有大小/类型限制和工作流/项目权限边界的资源；工作流版本引用确定的资源版本，运行时不得悄悄改用“最新文件”。
- 依赖配置以被依赖对象、时间窗口/周期和逻辑条件为核心，支持可读的 AND/OR 组合；执行前显示最终依赖表达式和解析结果。

### 5.4 运行统计表

建议新增 `workflow_result_stat`（最终命名服从项目数据库命名规范），与日志表分离。最低字段：

| 字段 | 用途 |
|---|---|
| `id` | 主键 |
| `workflow_id`、`workflow_version_id`、`workflow_instance_id` | 工作流和不可变运行版本身份 |
| `task_instance_id`（可空） | 可选任务粒度；工作流总计由同一运行结果口径汇总 |
| `attempt_no` | 区分重试尝试 |
| `success_count`、`failed_count` | 客户要求的成功、失败数量；不得从日志文本推算 |
| `skipped_count` | 原设计要求的跳过统计 |
| `read_count`、`write_count`（可空） | 执行器能可靠提供时写入；未知不能伪报为 0 |
| `result_status` | 本次汇总所属运行状态 |
| `created_at`、`updated_at` | 由数据库生成的时间戳 |

同一实例/任务/尝试的统计写入须幂等；重试信息可追溯，最终工作流汇总定义清楚是否包括已失败的历史尝试。所有执行器通过统一结果契约上报数量，日志仍用于诊断，不承担统计事实源职责。精确索引、唯一约束和聚合口径在对应数据库影响分析与迁移设计中冻结。

## 6. 客户交付切片与验收标准

### 切片 0：状态与依赖恢复

**产出**：工作树/分支清单、实现与证据矩阵、S9 状态对账结论、客户九项基线和目标映射、首批实现前影响分析。

**验收**：

- 每条现存分支和 worktree 都能定位到基线和差异；未提交用户工作被单独保全。
- S9 的一次性导入、用户复合验收和只读复核记录互相对应；不再次触发导入。
- R0–R3 等已通过或待通过的原计划门禁分别列出真实证据；没有把“S9 完成”扩大解释为“全新工作流、IDE 已完成”。
- 对每个可复用产物作出可追溯的处理决定。

### 切片 1：DBX 参考的数据开发 IDE

**用户流程**：选择项目和数据源 → 浏览多个 schema 的对象 → 搜索表/视图/存储过程/函数 → 打开编辑器 → 编辑/校验查询或例程定义 → 查看结果或变更影响 → 依授权确认写入并查看执行历史。

**范围**：跨 schema 对象树和 SQL 名称解析、SQL 补全、查询执行/结果、例程定义编辑、明确区分只读查询与 DDL 写路径、执行权限和审计；实现依赖于原设计规定的数据源能力和运行环境。

**验收**：至少覆盖两个 schema 的同名/异名对象、表/视图/例程浏览、例程语法和方言、权限拒绝、查询失败、DDL 影响预览及未确认时不写入；运行记录可追溯到用户、项目、数据源和版本。DBX 对照产品及版本作为验收证据记录。

**交付次序**：R0/R1 数据源与项目身份门禁满足后优先形成 IDE 可演示闭环。SQL IDE 与核心工作流节点在原设计中可以并行推进，但共用的变量、执行、日志和统计契约必须一致。

### 切片 2：工作流变量、同步表单与重点组件

按依赖先后交付：

1. **变量服务**：统一语法、作用域、优先级、类型、补全、现时值、校验和运行快照。
2. **同步组件**：依据源和目标连接探查对象/字段，生成初始映射；允许修改字段映射、转换和目标属性；保存后可预览并运行。映射结果随工作流版本保存。
3. **SQL / Python / Shell**：SQL 组件支持 SQL 文本和上传 SQL 文件；Python、Shell 支持上传脚本并引用明确版本。所有配置字段接入变量控件和同一校验服务。
4. **依赖组件**：按 DolphinScheduler 的表单组织方式选择依赖工作流/任务、周期/日期范围和逻辑条件；不复制其底层实现。
5. **DAG 分类和画布**：ETL 迁移为普通 DAG 展示；保留原定义、运行历史和链接。默认 palette 只显示客户重点组件和必要控制节点；额外组件放在经过审核的扩展入口，直至客户验收范围需要它们。

**验收**：同一变量在 IDE、工作流变量编辑和各组件配置中的补全、校验、现值展示及运行快照一致；同步映射可探查、人工调整和重复运行；上传资源版本固定；依赖表达式预览无歧义；ETL 历史工作流能以通用 DAG 打开，历史记录不丢失。

### 切片 3：运行统计和后台监控

**用户流程**：启动一个工作流 → 在运行中查看实例和任务 → 结束后在监控页按工作流、版本、时间和状态检索 → 查看成功、失败、跳过数量及可用的读写量 → 从统计跳到实例明细和日志。

**验收**：SQL、同步、Python、Shell、依赖和流处理至少各有成功与失败用例；每个用例的执行结果数与统计表一致；重试不会重复累计；日志删除/裁剪不改变统计结果；时间戳由数据库生成；权限按项目隔离。

统计契约先于各执行器冻结并贯穿实现，不能等到项目末尾再从日志补算。

### 切片 4：实时生产流与观摩

**用户流程**：启动生产流工作流 → 持续产生带时间戳和唯一事件号的测试事件 → 消息接入 → 聚合/融合处理 → 结果落地 → 页面实时观测生产、消费、积压/位点、窗口结果和错误样本。

**验收**：生产与消费速率、积压/位点、处理/落地数量及窗口结果来自真实运行数据；支持注入无效事件、重复和乱序记录，演示失败、重启或恢复后的行为；用相同输入能核对输出正确性。观摩页不能使用只在前端生成的静态结果代替执行。

### 切片 5：原设计其余能力与正式前端融合

在客户重点闭环和原计划前置门禁满足后，按原始设计/计划继续调度、治理、质量、血缘、AI 等能力。Backend API、数据模型、运行协议和独立验证证据全部达到冻结条件后，才启动正式前端融合。

## 7. 增量实施与阶段门禁

每个切片沿用原计划固定流程：

1. 对照原设计和客户范围，写开始前影响分析，确定代码/数据/接口影响与隔离环境。
2. 冻结前后端契约、数据模型和真实用户验收步骤；先建立能失败的契约验证。
3. 实现 Backend、数据库变更和执行器；应用迁移前按约法做快照、预检与明确批准。
4. 建立独立验证页面，使用真实服务、数据、执行器和环境完成浏览器端闭环。
5. 运行项目要求的测试、静态检查、浏览器/远端检查，并保存命令、结果、截图和日志链接。
6. 对照本切片验收项逐条复核；证据不足时保持 RED/PARTIAL，不提前报 PASS。
7. 更新唯一责任人维护的执行状态和台账；所有共享文档按 handoff 单写者声明执行。

每个客户要求都必须能追踪到：`原始设计条款 → 接口/表/页面 → 运行行为 → 验收证据`。缺少任一环节即为未完成。

## 8. 防止再次漂移的硬约束

- 不以“评审建议”“后续扩展”“组件目录已经存在”为理由自动增加新产品范围。
- 不恢复旧变量语法，不复用旧 Backend 作为新执行器，不把旧系统表现误报为新系统交付。
- 不让 SQL IDE、SYNC、STREAM、Python、Shell 各自建立变量、运行、日志和统计口径。
- 不把 ETL 留作并列工作流分类，也不通过删除 ETL 数据实现分类收敛。
- 不把 70+ 项历史组件全部暴露在默认画布；默认优先集合只含本轮重点组件和必要控制流。
- 不用 mock 流数据、静态截图、API 按钮面板或孤立页面替代真实端到端验证。
- 不把开发 GREEN、页面骨架完成、单元测试通过等同于客户验收通过。
- 原设计发生变更时，先由用户裁定并更新权威设计/计划，再更新接口、迁移和验收契约；执行者不得自行降级目标。

## 9. 主要风险与处置

| 风险 | 后果 | 处置 |
|---|---|---|
| 分支和工作树不是同一基线 | 漏代码、冲突或误报完成 | 切片 0 建立 SHA 与差异清单；集成前逐分支审阅 |
| 主目录存在未提交用户工作 | 覆盖或丢失已有工作 | 本方案在隔离工作区编写；主目录改动只读保全 |
| 原计划状态和 handoff 不一致 | 门禁重复或越级 | 以用户裁定、原始证据和单写者状态台账联合对账；不重放一次性操作 |
| Legacy 能力看似成熟 | 直接依赖导致新系统目标失效 | 仅抽取领域行为和验证用例；新 Backend 另行实现并独立运行 |
| 组件字段与变量规范各自演进 | 表单能保存但运行失败 | 共享 Schema、VariableService 和运行前校验；同一组跨组件契约用例 |
| 统计由日志推算 | 日志轮转后结果不可靠 | 执行结果结构化写入独立统计表并做幂等约束 |
| DBX 参考版本不明确 | UI 评审争议、重复返工 | 原型评审前补充客户给定的产品版本、链接或截图 |
| 正式前端过早融合 | 旧界面结构牵制后端契约 | 按原设计冻结节点设门；本轮先用独立验证页面 |

## 10. 方案交付物

批准进入执行后，按项目约法形成以下材料：

1. 快照清单和“客户要求—原设计—代码—证据”追踪矩阵。
2. 对 R3-S9、R4-SYNC、R5 IDE、I7–I9 等现有工作逐项作出的保留/修正/参考/待裁定决定。
3. 对每个客户切片独立的影响分析、接口/数据库契约、验证页和验收记录。
4. 经单写者审核更新的执行附录与状态台账；不得重写原始设计目标。
5. 所有新建和变更的 AOCI 资产在专门维护会话的授权窗口内统一收口。

## 11. 完成定义

本次纠偏完成需同时满足：

- 原始设计与计划仍是唯一产品目标真源，新增决策全部有用户裁定记录。
- 分散工作已按证据判定去向，未提交用户工作和已完成的一次性导入均未被破坏或重放。
- 客户九项要求均有状态、责任人、对应切片和可复核验收证据；客户确认的首发闭环通过真实环境验收。
- 成功/失败统计、变量解析、数据源权限、工作流版本和正式运行边界一致贯通。
- 实时生产流、处理结果和观测指标构成可重复演示的真闭环。
- 正式前端只在 Backend 与运行契约冻结后融合；AOCI/文档状态按当前项目约法完成一致性收口。
