# P-OPT-1：STATE 分层快照机制设计

**状态：设计稿，仅定义规范；本稿不修改 STATE、循环程序或其他实现。** 目标是在冷启动时先恢复当前授权事实，再按需读取详细材料，避免每次扫描冻结历史和重复展开证据。

## 1. 目标与边界

- `docs/handoff/STATE.md` 是监督线现状基线，也是所有线冷启动的共同入口；它保留当前状态、有效裁定指针、在飞任务、已知工作区差异和活动心跳。
- 详细规范、裁定原文、实现证据仍以其各自增量文档为准。STATE 只保留结论摘要、定位链接和提交锚，不复制长论证或测试日志。
- 历史台账已冻结的内容只按明确引用回查；不得把旧台账扫描结果当作当前任务或新裁定。
- AOCI 仍归监督线治理。Trae、Codex、Claude 实施线按 #85 豁免，不调用 AOCI 工具；STATE 快照不得改变该职责边界。
- 继续执行 STATE ≤60 行、活动心跳 S# 单调递增且每条 ≤8 行、历史台账只读、pathspec 单文件提交、无 push 的现行约束。

## 2. 信息分层与载体

| 层 | 载体 | 保存内容 | 读取条件 |
|---|---|---|---|
| L0 当前快照 | `docs/handoff/STATE.md` 前半部 | 当前权威、现状、在飞/待裁任务、有效门禁、已知脏项、刷新锚点 | 每次冷启动完整读取 |
| L1 活动心跳 | `STATE.md` 活动区 S# | 到岗/领单、关键交付、测试命令和输出定位、提交号、下一单 | 每次冷启动读取当前活动区；追任务时按 S# 链接定位 |
| L2 增量材料 | `docs/increments/`、`docs/increments/evidence/`、`docs/adr/` | 设计、裁定索引、交付复核、机器可读证据及原始日志 | 只读任务所需文件，不递归扫描整个目录 |
| L3 冻结历史 | `docs/handoff/2026-10-16-并行协作分工.md` 与归档区 | 已冻结旧心跳和历史上下文 | 仅当当前快照/裁定索引引用旧锚，或核实历史争议时读取相关段落 |

STATE 快照头部建议记录 `snapshot_date`、`covered_through`（最新核实的 S#）、`git_anchor`（核对时的 HEAD）、`refresh_reason`。这些字段描述快照覆盖范围，不替代提交记录、裁定索引或证据文件。

## 3. 各线冷启动读取顺序

共享首段严格按序：

1. 读取仓库 `AGENTS.md`，识别仓库规则、当前活动交接、角色权限和明确豁免。
2. 读取 `docs/handoff/STATE.md` 全文，对齐快照、在飞任务、活动区和链接指针。
3. 执行 `git log --oneline -5` 并与快照的 `git_anchor`、最近心跳/提交锚比对；发现不一致时先查清分支或工作区来源，不用旧快照覆盖实锚。
4. 启动本线循环实体 `python agents/mailbox_loop.py --role <line> --agent-cmd "<CLI command>"`，核对没有重复进程并记下 PID。循环实体只消费本线收件箱，不替代当前会话履行领单。
5. 追加到岗/领单/留守心跳 S#（≤8 行），随后只对 `docs/handoff/STATE.md` 做 pathspec 单文件提交，不 push。
6. 再按角色读取主标准 §15、裁定索引 §一以及领单所指向的增量材料；不因“完整了解项目”而遍历冻结台账或所有证据目录。

角色追加步骤：

- **监督线**：完成共享首段后读取主标准 §15、裁定索引 §一、任务池；只有其治理职责触发时才按 AOCI 规则执行机读。
- **Codex 线**：完成共享首段后读取设计/复评对应的规范和证据。独立复评先锁定裁定锚与验收边界，再查看被评交付及其原始输出。
- **Claude 线**：完成共享首段后读取实施派单、冻结契约和定向测试；仅实施范围内文件。回报需带提交、命令与输出路径，供 Codex 独立复评。
- **Trae 线**：完成共享首段后读取本线派单及对应冻结契约/验收清单；按派单边界实施并交付可机读证据。

用户明确指定的新冷启动顺序高于旧启动提示中的差异顺序；本节实施后应同步主标准 §15 和各线提示，避免两套入口并存。

## 4. 快照刷新规约

### 4.1 触发

监督线在以下任一事件发生时刷新快照：新监督窗接手；领单、交付、裁定、任务状态或门禁改变；新提交改变现状基线；工作区脏项披露有变化；快照覆盖锚已落后于活动区且可能误导冷启动。无状态变化时可只追加必要的监督心跳，不重复重写相同快照。

### 4.2 生成与核验

1. 从当前工作区核验 `git log --oneline -5`、`git status --short`、相关 S# 与任务证据；以可验证事实更新快照，不从过期摘要推断状态。
2. 快照只写变化后的当前值，并更新 `snapshot_date`、`covered_through`、`git_anchor`、`refresh_reason`。保留未关闭任务及其阻塞条件；已完成项移出任务池前须有交付/验收锚。
3. 同一监督窗把快照更新与对应活动心跳放在一次 `STATE.md` 单文件提交中。提交前确认行数 ≤60、活动心跳编号无冲突、单条 ≤8 行、所有路径存在且未误改冻结历史。
4. 任何线收到新事实时先通过信箱/心跳报监督线；由监督线核实并刷新当前快照。实施线不得互相改写对方状态，也不得把监督线快照编辑职责转给循环实体。

### 4.3 行数与历史保全

在达到 60 行上限前，按以下两阶段轮转活动区；不得静默删行、覆盖旧 S# 或直接突破上限：

1. **归档提交**：选取连续且已完成/已裁定的最早 S# 区间，把原始心跳文本、S#、原提交号和其间断点说明原样追加到 `docs/handoff/archive/STATE-<日期>-S<起>-S<止>.md`，单文件提交。归档文件只追加，不改写既有归档段。
2. **快照提交**：确认归档文本和锚点可读后，在另一个仅含 `STATE.md` 的提交中，把该连续旧区间替换成一条归档索引，并同步刷新快照字段；新增活动心跳仍按 S# 递增追加。归档与当前视图短暂重复是安全的；若第二步未完成，原 STATE 行仍在，可重试核对后再轮转。

此过程保留历史原文和 Git 提交锚，同时让当前 STATE 保持 ≤60 行。轮转不得跨越未完成任务最近一次必要上下文；未关闭任务的当前状态留在快照，原始历史可经归档索引读取。具体归档日期格式需实现时按仓库命名约定落地。

## 5. 一致性与失败处理

- **快照与 HEAD 不一致**：以当前分支和工作区实锚为准，检查快照之后的提交/心跳；必要时报告监督线刷新，不回滚或改写历史。
- **快照过期或链接缺失**：完成共享首段后只读取解决当前领单所需的源文件，并记录缺失项；禁止把旧摘要当成证明。
- **证据与摘要冲突**：复评按既有裁定基线核对原始证据，STATE 仅作为导航和状态快照。
- **循环实体异常**：不得由循环实体自行重写 STATE；保留日志、由当前人工会话核查 PID/信箱和 git 锚后恢复。
- **提交范围**：每次快照或心跳提交仅包含 `docs/handoff/STATE.md`，不 push；文档、原始测试输出等其他文件分别按单文件 pathspec 提交。

## 6. 预期冷启动成本与验收条件

每线固定读取两个小型交接文件（AGENTS、STATE）和五条 Git 提交摘要；后续材料由领单定向加载。以冷启动期间实际读取的文件数/字节数、是否发现过期任务或缺失锚、是否能从测试输出定位复现结果作为验证记录，不预设 token 节省比例。

实施前需验证：共享首段顺序一致；任一活动任务可从 STATE 跳转到裁定/增量/原始输出；刷新不覆盖历史且单文件提交；60 行轮转方案与 append-only 契约相容；AOCI 豁免、各线职责和现有门禁不变。通过评审后另开实现单，本稿不包含实现步骤或代码变更。
