## Problem Statement

多终端多智能体协作的规则目前散落在五处，彼此独立演化：协作范式文档（角色/循环/案例库）、监督线交接就任令（在案常设裁定 11 条）、重建执行约法（六条约法）、AGENTS.md 集成段（AOCI 豁免与信道指针）、以及 3600+ 行分工台账内嵌的 340+ 条心跳与裁定编号。结果是：

1. 新会话/新角色上手必须自行读五处并拼接，没有一份"项目管理标准规范"可作为唯一对标基线；
2. 过期描述与现行状态并存且互相矛盾（台账仍以 Trae 线为执行者之一、watchdog 已按用户令停机而范式与仍描述其常驻运行），读者无法区分"现行规则"与"历史事实"；
3. 裁定编号内嵌于台账长文，检索成本高，出现过复评基线滚动漂移、收敛闸失守等流程缺陷；
4. 规则变更没有统一的版本与生效通道，只能靠回写范式文档零散补丁。

用户要求：对既有协作范式进行重构、优化与完善，形成一份有机一体的项目管理标准规范。

## Solution

产出一份唯一权威的《多终端多智能体项目管理标准规范》，按四层权威模型有机组织而非机械拼接：

- **事实层**：分工台账（append-only 心跳与裁定原始记录，历史原文永不改写）；
- **流程层**：执行循环、约法、门禁与证据纪律；
- **角色层**：角色拓扑、权力边界、派单/领单/交付回执闭环、AOCI 职责边界；
- **技能层**：范式文档瘦身为可复用技能入口与案例库，指向标准。

同时建立裁定索引附录（编号→日期→裁定点→状态）、统一心跳模板、清理过期状态描述（以状态注记而非删除历史段落的方式处理），并在既有入口（AGENTS 同步文件、交接就任令、台账头部）各留一条指针指向标准。合规性以台账心跳为唯一判据接缝、以权威文档链指针为一致性接缝进行验证。用户从"被迫拼接五处规则"变为"读一份标准即可对标执行，历史事实可经裁定索引回溯"。

## User Stories

1. 作为新加入的执行线会话，我想只读一份标准规范就理解角色拓扑、信道、循环与纪律，以便不必自行拼接五处文档即可开工。
2. 作为新监督员，我想在就任时拿到标准与裁定索引，以便继承全部在案常设裁定而不必通读 3600 行台账。
3. 作为监督线，我想每条规则都有唯一的权威层级归属（事实/流程/角色/技能），以便发生矛盾时能机械判定以谁为准。
4. 作为执行线，我想在心跳模板中看到必填字段清单（编号/线别/时间/领单/交付/证据锚/下一单触发/Resolved），以便每条心跳一次写全、不被反复退回。
5. 作为执行线，我想派单-领单-交付-验收四跳各有明确的回执格式，以便交付即派单同窗完成、无派单真空。
6. 作为用户，我想任务池以固定字段表（编号/任务/Owner/状态/证据提交号/依赖与下一步）分 Phase 呈现，以便一眼看清全局与关键路径。
7. 作为用户，我想每条用户裁定被分配全局唯一编号并进入裁定索引，以便随时质询"某裁定现在是否仍然有效"。
8. 作为监督线，我想裁定索引带状态字段（生效/被替代/已废止/仅历史），以便区分现行规则与历史事实。
9. 作为任何角色，我想台账历史心跳原文保持不动，以便追溯原始事实不被"整理"破坏。
10. 作为任何角色，我想过期描述以显式状态注记处理（如"watchdog 已于 2026-10-18 停机""Trae 线已撤"），以便阅读现行段落时不再被误导。
11. 作为执行线，我想标准里给出明确的文件域划分与共享文件单写者规则，以便并行执行零文件重叠。
12. 作为执行线，我想 pathspec 单文件提交、禁 push、临时索引恢复等提交纪律集中成章，以便每轮提交前可对照检查。
13. 作为执行线，我想失败处理与事故披露协议（即时披露→影响评估→不回滚不改写历史→留痕→归类→纪律升级）写入标准，以便出事后按章处置而非临场决策。
14. 作为质量监督角色，我想审计清单成为标准的一节，以便每轮增量收口按同一清单执行。
15. 作为监督线，我想证据规范（JSON+PNG 成对、失败证据不覆盖、提交号实锚）进入标准，以便复核证据纪律有统一依据。
16. 作为监督线，我想"没有核实过台账/git 实锚的结论不许报"作为硬纪律写入标准，以便杜绝未核实完成声称。
17. 作为 AOCI 职责方，我想 AOCI 调用边界（谁可调用、谁禁止、豁免条款与裁定来源）在标准中唯一成文，以便职责争议有据可依。
18. 作为运维角色，我想看护类基础设施（watchdog/自动拉起）有明确的生命周期状态登记（运行中/停机/重启决策人），以便其描述不与现实脱节。
19. 作为新项目启动者，我想标准附带启动清单，以便在新仓库直接套用本规范。
20. 作为范式维护者，我想范式文档瘦身并指向标准，以便消除双权威并保留案例库的历史价值。
21. 作为规则修订者，我想标准本身有版本号与修订通道（用户裁定→版本递增→入口指针不变），以便变更可追溯。
22. 作为执行线，我想标准明确"交付心跳以下一单：已派/待派+触发条件收尾"，以便消除掉线歧义。
23. 作为监督线，我想标准固化收敛闸与轮次上限（复评只对照既有基线、超轮强制互换），以便复评漂移不再复发。
24. 作为执行线，我想并行度规则（可并行任务必须并行、串行须写依赖依据）进入标准，以便强制并行有判定标准。
25. 作为执行线，我想用户专属闸的委托授权与证据留痕规则唯一成文，以便"经用户委托"标注有据可依。
26. 作为验证方，我想页面自驱动验证与预置输入规则保留在标准中，以便验收不回退用户做页面操作员。
27. 作为任何角色，我想心跳编号规则（全局递增、取台账实锚最大号+1、撞号后落库改号）成文，以便并发占号有章可循。
28. 作为审阅者，我想标准的每条规则都可在心跳上机械判定合规/违规，以便用台账抽样即可验证标准的可执行性。
29. 作为维护者，我想旧入口的引用全部改为指向标准的单指针，以便全仓不再存在两份互相独立的权威表述。
30. 作为监督线，我想标准区分"派单心跳唯一载体"（口头派单作废）与日常沟通，以便争议时以台账为唯一依据。
31. 作为执行线，我想标准给出工作区脏项与他线产物的处置规则（不触碰、先报备），以便多线并行互不破坏。
32. 作为新会话，我想标准开篇给出 15 分钟上手行动清单，以便冷启动即可对齐状态。
33. 作为用户，我想标准保留"认错直接认、先修后解释、不找借口"的沟通纪律，以便汇报质量稳定。
34. 作为维护者，我想事故案例库在标准中有回写入口（新事故→案例→纪律条款），以便案例持续沉淀而非一次性文档。
35. 作为审阅者，我想标准不复制台账内容而只引用，以便标准体量可控、不与事实层双写。
36. 作为监督线，我想 AOCI 语义批次与传输的分窗规则引用在案裁定而不重新发明，以便裁定链完整连续。

## Implementation Decisions

- **分层权威模型（核心架构决策）**：标准按四层组织——事实层（台账心跳，append-only，历史原文永不改写）、流程层（执行循环/约法/门禁/证据）、角色层（拓扑/权力边界/派单闭环/AOCI 边界）、技能层（范式文档=可复用入口+案例库）。同一条规则只允许在一层完整表述，其余层只留指针；矛盾时低层（事实）优先于高层（规范）作为事实依据，规范优先作为行为依据。
- **单一新权威 + 旧入口指针**：新建标准文档为唯一行为权威；协作范式文档瘦身为"技能入口+案例库+审计清单"并指向标准；AGENTS 集成段、交接就任令、台账头部各加一条指针。不再维护第二份独立权威表述。
- **裁定索引附录**：从台账全部心跳提取裁定编号，形成"编号→日期→裁定点摘要→状态（生效/被替代/已废止/仅历史）"索引表，作为标准附录；台账原文不改写，索引只引用。
- **过期内容处置策略**：以状态注记方式在现行段落标注（watchdog 停机、Trae 线已撤、cron 机制失效历史等），历史心跳段落一律不删不改；分工台账中已失效的角色描述在文件头部以"现行三线"注记覆盖。
- **心跳模板标准化**：规定心跳必填字段与可选字段、编号规则（全局递增、取 git log 与文件内实锚最大号+1、撞号后落库方改号）、交付心跳尾部"下一单"自解释条款。
- **任务池表结构**：固定字段（编号/任务/Owner/状态/证据提交号/依赖与下一步）分 Phase 呈现，临时任务单列；状态枚举沿用现有在案用法。
- **变更通道**：标准修订必须经用户裁定并递增版本号；入口指针路径保持稳定；范式回写条款（新裁定/新事故）保留并改为"回写标准"。
- **规则可判定性要求**：每条规则必须能在心跳（文本）上机械判定；无法判定的表述在评审中改写为"触发条件→判定→处置"三段式。
- **看护基础设施生命周期**：任何常驻机制（watchdog、cron、自动拉起）在标准中必须有运行状态登记节，状态变更由用户裁定并注记日期。
- **不做**：不重排历史编号、不引入新工具链、不新增自动化测试框架（见测试决策）。

## Testing Decisions

- 好的测试只测外部可观察行为：本规范的"外部行为"=①在台账心跳上的合规可判定性、②入口指针的一致性；不测文档内部措辞或结构偏好。
- **接缝 A（主接缝，既有）：台账心跳合规抽样**——取台账最近约 100 行心跳，逐条按标准规则判定（编号是否连续实锚、是否含必填字段、交付心跳是否有"下一单"、证据是否带提交号、派单是否落台账）。通过标准=全部条目可给出"合规/违规/标准未覆盖"三态结论且无两条规则互相矛盾。
- **接缝 B（既有）：权威文档链指针一致性**——全仓引用扫描，断言：标准被入口文件引用、旧入口不再保留独立权威表述、无断链（被引用文档存在）。
- **裁定索引回溯抽样**——从索引随机取若干裁定编号，回台账原文核对日期与裁定点一致、状态标注正确。
- **过期描述零残留扫描**——以关键词扫描现行段落（非历史心跳段），断言不存在把已停机/已撤对象描述为运行中的句子。
- Prior art：范式第 8 章质量监督审计清单（基线实测复现、三方一致性）、交接就任令"就任后第一个 15 分钟"行动清单、台账既有 Resolved 行惯例——均为人工可执行的核对式验证，与本规范验证方式同构。
- 文档型规范不引入代码测试框架；两接缝均在既有最高层（台账文件与全仓引用），不新增脚本接缝。

## Out of Scope

- 台账历史心跳的改写、重排或归档压缩（append-only 原则）。
- 历史裁定编号的重新分配或合并。
- 业务代码、AOCI 索引内容本身、语义批次撰写（另有裁定链管辖）。
- watchdog/看护机制的重启与否（由用户按当时需要另行裁定，标准只登记状态与决策人）。
- 新通信信道或新工具链的引入（标准只整合现有信道与工具）。
- 项目记忆文件（project_memory.md）的迁移或合并。
