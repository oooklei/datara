## §3 逐差异明细

### P1（阻塞契约冻结或接线）

**D1. DEPENDENCY 域整体无 HTTP 面（FE #1-#5，5/5 缺失）**
- `rebuild/dependency/` 8 文件（`__init__/domain/persistence/dispatch_persistence/poller/scheduler/worker/gate`）为纯库级：全目录无 `api.py`、grep 无 `APIRouter`；`rebuild/api/app.py` import（:32-54）与装配（:590-768）均无 dependency 项。
- 库级语义与 FE 契约高度同源——`preview_dependency`（domain.py:420，"Render a human-readable expression and its concrete calendar windows"）↔ FE `previewExpression`；`evaluate_dependency_result`（:374，"pending/wait and fail-closed error rules"）+ `gate.py`（"only SATISFIED permits"）↔ FE `evaluateDependency`/`DependencyVerdict`；`ConditionGroup`（:264，AND/OR **可嵌套**）↔ FE `DependencyGroup`（组内 join+**组间固定 AND**，:33）。嵌套组是 BE 超集，FE 组间 AND 是否仍为约定（B2 :65 悬空点）需在冻结时对齐。
- `persistence.py`/`dispatch_persistence.py` 是 **poll 决策与派发 token** 持久化（运行时面），不是 FE `saveDependency` 的「依赖配置随工作流版本保存」（客户 #2/#5 语义）——配置保存面完全无落点。
- **B2 缺口 #2 部分修正**：DEP 侧「无 Codex 草案」的表述在 HTTP 面意义下成立，但「无草案文件」需改为「纯库级 8 文件在飞（域模型/求值/持久化齐备，无 api 层）」。见 Q2/Q3。

**D2. RESOURCE 上传编码与上限双向偏差（FE #6）——B2 缺口 #3 编入**
- FE 契约注释（resourceApi.ts:39）："真实实现为 multipart 正文；契约层仅承载元数据描述"；BE 实态为 **JSON body `content: str`**（api.py:27-31）——multipart 口径在 BE 侧同样未采用，B2 缺口 #3「multipart 编码与分片口径待定」的答案方向变为「BE 目前收 JSON 文本」，需 Codex 裁定终态（JSON base64 / multipart / 其他）。
- 大小上限：FE 草案 20MB（resourceApi.ts:56，测试 ：65 冻结断言）vs BE 默认 5MB（app.py:100 `resource_max_content_bytes: int = 5 * 1024 * 1024`，经 ：712 注入 api.py）。设计 §5.3 仅要求「有大小限制」（B2 :87），数值需冻结；若定 20MB 则 BE 默认值需调整或确认装配处覆盖。

- association 两端点与 FE 两方法语义对位良好（质量结果关联/血缘结果关联，执行 attempt 级证据链 evidence_kind/evidence_ref），分页与 attempt 过滤齐备。
