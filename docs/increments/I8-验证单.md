## 二、实测发现并修复的缺陷（均已部署 1.9 复测通过）

### 1. C20 轮询响应未走统一信封（门 1 复测抓出）

- 现象：poll 返回裸数据，前端解析失败。
- 根因：[api/streamdata.py](../../datara-backend/api/streamdata.py) 缺 `from common.resp import ok` 导入，poll 分支直接返回 `_snapshot(...)` 未包信封。
- 修复：poll 分支改 `return ok(_snapshot(job, client, limit))`。

### 2. consumer group 竞争致消费空转（门 1/门 3 抓出）

- 现象：totalIn=0 持续空转，同 group 的遗留旧任务消费者抢单分区。
- 根因：门脚本多画布共用固定 `group='i8-flink'`，kafka 组内分区被旧 member 占用。
- 修复：i8_gate.py `_mk_doc` 改 `group=f"i8-{kind}-{int(time.time())}"`（每画布独立组）。

### 3. CDC 列名 UNKNOWN_COL0~3（门 2 抓出）

- 现象：CDC 行事件列名为 `UNKNOWN_COL0~3`，无业务列名。
- 根因：datara-mysql-src `binlog_row_metadata=MINIMAL`，binlog 行事件不携带列名元数据（mysql-replication 1.0.17 支持读 FULL optional metadata）。
- 修复：`SET PERSIST binlog_row_metadata='FULL'`，重启后 CDC 行携带真列名 + before 镜像。

### 4. kafka-python 掉线静默空转（门 5 抓出）

- 现象：docker stop kafka 后任务无任何异常、poll 持续返回空，永不重连。
- 根因：kafka-python `poll()` 在 broker 掉线时静默返回空 dict（不抛错），引擎无从感知。
- 修复：[worker/stream/sources.py](../../datara-backend/worker/stream/sources.py) KafkaSource.poll 空闲计数（idle≥25 次）触发应用层 TCP 探测，全失败抛 `SourceError` 进引擎重连。

### 5. 探测层两轮误报修正（门 5 修复过程）

- **bootstrap_connected() 误报**：正常空闲时也返回 False，作为探测依据导致无限重连循环 → 弃用，改 TCP 层探测（`socket.create_connection`）。
- **Docker DNS 别名恢复延迟**：容器 stop 后 embedded DNS（127.0.0.11）移除别名（`gaierror [Errno -5]`），start 后恢复有延迟 → open() 成功时缓存 broker IP（`_resolved_ip`），探测时主机名解析失败用缓存 IP/重新解析直连兜底。
- **探测超时 3s→10s**：KRaft 半就绪窗口 9092 SYN 排队 accept 抖动，KafkaConsumer 宽超时能连上而 3s 短超时必失败；真断流是 refused/gaierror 秒失败，感知不受影响。
- **MAX_RETRIES 10→30**（[worker/stream/engine.py](../../datara-backend/worker/stream/engine.py)）：实测 KRaft 冷启动恢复 >180s，原 10 次/190s 上限会在恢复期耗尽误转 failed。

### 6. fail_event 残留致重试开局秒败（门 5 真根因，决定性）

- 现象：恢复期每轮重试 open 成功后 2~3s 即报「管道异常」，无探测 warning，kafka 完全正常也永不自愈，直至 MAX_RETRIES 耗尽转 failed；DB 状态每轮 running→reconnecting 抖动。
- 根因：[worker/stream/engine.py](../../datara-backend/worker/stream/engine.py) `_pipeline_once` 主循环以 `fail_event` 未 set 为运行条件，但 `_job_main` 重试循环从不清除上轮残留的 fail_event/fail_msg——首次失败后每轮重试装配完成即 raise 旧 fail_msg，**poll 从未执行**；每轮装配先置 running（424 行）再秒败，解释了状态抖动假象。
- 修复：`_pipeline_once` 开头 `rt.fail_event.clear(); rt.fail_msg = ""`（每次装配=全新尝试）。
- 复测：修复后 job5 立即恢复消费积压（offset 160→165），复投 5 条 10s 内到账；门 5 终验 v3 全流程 PASS。

### 7. 过程性排查修正（非缺陷）

- 1.9 部署路径：worker 代码需 `docker cp` 进容器 + kill/start 重载才生效（scp 到宿主挂载目录不自动生效）；`__pycache__` 因 mtime 变化自动失效，无需手清。
- PowerShell 5.1 不支持 `&&`，ssh 内嵌双引号/内嵌 python -c 会被剥离 → 统一「scp 脚本 + `sed -i 's/\r$//'` + bash」模式。

## 三、遗留观察项（未修，如实记录）

1. **open() seek 时机 bug**：KafkaSource.open 在 `poll(timeout_ms=200)` 触发分配后立即 seek，组 join/assignment 未就绪时 seek 被跳过 → 重启后按 auto_offset_reset=earliest 重放（totalIn 计数虚高、窗口行重复产出）。**位点提交不回退**、下游按窗口幂等聚合，属 at-least-once 语义内；后续可在 poll 首次返回 assignment 后再 seek 修复。
2. **KRaft 恢复时长**：docker stop→start 冷启动实测 >180s（bitnami/kafka KRaft 恢复），期间任务 reconnecting 如实留痕、恢复后续跑；短暂 stop（~50s）热重启场景 ~10s 恢复。1.9 演示环境可接受，生产建议持久化卷 + 监控恢复窗口。
3. **历史画布 group**：job5 等 I8 早期画布 spec 的 group 仍为固定 `i8-flink`（旧版 gate 脚本产物）；新画布已用独立 group。多画布复用历史画布时注意 group 冲突。
