## 一、调查确证：五系统事实

### 1.1 DBX（SQL IDE 参照）

- **三形态并存**：Tauri 桌面（`src-tauri/tauri.conf.json`；`src-tauri/src/main.rs` 仅 `dbx_lib::run()`）；**dbx-web HTTP 服务**（`crates/dbx-web/`，Axum 框架，55+ 路由模块含 query/connection/schema/history/ai/agents/SSE，utoipa OpenAPI）；CLI/MCP 包（`package.json` 中 `@dbx-app/cli`、`@dbx-app/mcp-server`）。
- SQL 核心 = Rust crate 进程内执行（`crates/dbx-core/src/query/mod.rs`；桌面经 `#[tauri::command]` 直连，`src-tauri/src/commands/query.rs:L33-L51`）。
- dbx-web 认证 = **单密码 + 内存 session cookie**（`crates/dbx-web/src/auth.rs:L16-L49`：argon2 单口令 + uuid token HashMap）——**单用户模型，无多租户/多用户/项目权限**。
- **服务化结论：可容器化（dbx-web 现成载体），但为单用户级服务**；接入平台需网关身份桥接 + 连接/历史/保存 SQL 等数据模型映射；UI 为 Vue3（apps/desktop）。

### 1.2 DolphinScheduler（DS，调度参照）

- Java 多模块 **29 个**（api/master/worker/alert/standalone-server/ui/dao/task-plugin/datasource-plugin/registry/scheduler-plugin 等，pom 实锚）；多进程架构，官方 standalone/docker/k8s 部署成熟。
- 引擎成熟度（重试/容错/补数/优先级队列/失败策略）是五系统中**最难以短期自研达到**的部分。
- 集成面成本：自有用户/租户/项目模型、工作流定义 JSON 协议下发、日志与状态回收，以及**变量体系冲突——DS parameterPassing vs Datara 七级作用域+run-snapshot（系统灵魂，S3/R2 已冻结）**。

### 1.3 OpenMetadata（OM）/ 1.4 DataHub（DH）（元数据参照）

- OM：Dropwizard Java server + Python ingestion + Elasticsearch + MySQL；OIDC/JWT 对接支持（`openmetadata-service/pom.xml` pac4j 依赖）；本地一键容器化（`docker/run_local_docker.sh`）。运行栈约 4-6 容器。
- DH：GMS(Spring)+frontend React+Kafka+ES+图库+actions/upgrade 作业（`docs/components.md:L13-L45`、`docker/README.md:L37-L44`）；GraphQL/REST 面；**组件比 OM 更重**。
- 两者功能高度重叠（现行 U4 择一待裁定）；设计 §11 本就定位为「可选外部目录和 AI 上下文投影，不作为 Datara 执行真源」。

### 1.5 Vanna（AI 助手）

- **pip 可安装 Python 库**（`pyproject.toml:L20-L43`，可选 FastAPI/Flask server extras）；v2 ChatHandler（chat_sse/chat_poll，`servers/flask/routes.py`）。
- 与 datara-backend **同为 Python 3.11**：可直接 import 嵌入，零容器成本。

### 1.6 Datara 当前成熟度盘点

- datara-backend：Python 3.11 **五模块（api/master/worker/alert/logger**，`pyproject.toml`）——已是 DS 式分解的自研后端骨架。
- 已冻结/大半完成：R2 变量域（系统灵魂）、R8-A 八工具契约；依赖域契约 A2 v2.1（待会签冻结）；R3 治理迁移（I18-I23 批量执行大半）；R5-A DBX DDL 精读完成（2026-10-17 迭代 56）；R0/R1 验证底座与部署工具链。
- 未完成：R4 接线（等 A2 冻结门）、R5-A 实现、R6 执行引擎、R7 收尾、R8 集成、R9-R11。

## 二、方案 2 的真实构成（拆解）

方案 2 **并非对五系统同质成立**：

| 系统 | 方案2 落位 | 真实成本 |
|---|---|---|
| DS | 容器部署 + API 桥接 | 引擎白得；但身份/租户/项目映射、工作流定义下发、日志状态回收、变量语义包裹 = 深度桥接；深度定制需 fork 跟随上游 |
| DBX | dbx-web 容器化 | 服务载体现成但**单用户**；多用户/项目权限需网关 + 数据模型映射；UI 融合 Vue3 |
| OM/DH | 容器外挂目录 | 开箱即用；但这本就是设计 §11 的既有定位（方案2 直觉与现行设计重合）；运维栈重 |
| Vanna | 库嵌入 | **两方案完全同构，无差异** |

**推论**：方案 2 ≠ 全面外包。它的实质增量只有一个真正的硬分歧点——**调度执行引擎是否用原生 DS 容器替代自研**。其余部分（OM/DH 外挂、Vanna 嵌入）现行方案 1 的混合设计已经涵盖；DBX 即便容器化，其平台化改造（多用户/契约对齐/权限桥接）工作量与「复刻语义自建服务端」处于同一量级。

## 三、对比分析

### 3.1 成功概率

- 方案 2 最大风险 = **集成语义统一**：五套身份/项目/变量/统计/时间戳协议归一，本质是分布式系统集成项目而非「粘合」；此类路线的历史失败点集中在语义一致性与端到端体验。前端还面临五套技术栈融合（Datara React + DBX Vue3 + OM React + DH React + DS UI）。
- **变量灵魂（S3）存续问题**：外部 DS 引擎天然不携带 Datara run-snapshot/七级作用域语义。要么 DS 内深度定制（fork 跟随成本 + 升级冲突），要么只在 Datara 侧包裹（依赖 DS 内部行为细节，脆弱，且难以通过 A5 全覆盖对照验收）。
- 已冻结资产折价：R2/R8-A 契约、A2 v2.1、S1-S5 验收体系均以自研复刻为前提；切换方案 2 = 标准大版本修订 + 部分返工。
- DBX 单用户模型 → 平台化改造不可回避（认证/连接密钥归属/项目隔离）。
- **判定：方案 1（含其内建的混合外挂）成功概率更大**；方案 2 的概率损失主要来自「桥接 × 前端融合 × 变量灵魂」三处不确定性叠加。

### 3.2 发版效率（按里程碑辩证）

- **M1「内部可演示」**（调度 demo + 目录外挂 + Vanna 问答）：**方案 2 更快**——DS/OM 开箱即用是真实优势。
- **M2「可交付统一产品」**（统一认证/变量/统计/审计 + 单一前端 + 可控交付物）：**方案 1 效率与概率更高**——方案 2 的桥接长期维护、五套 UI 融合、上游版本跟随（5 个上游任一升级都可能破坏桥接）、内部系统 10+ 容器的交付门槛，尾工程深不见底；TCO 持续更高。
- 内部系统语境下发版定义 = M2。故「换方案 2 最后发版效率更高」**大概率不成立**（M2 更晚、维护更重）。
- **公平记录**：方案 1 的最大技术风险必须同样点名 = **R6 执行/调度引擎成熟度**（重试/容错/补数/分布式 worker）——这是方案 2 唯一真实的王牌。因此 §四给出引擎外挂的判定准则，而非简单否定。

### 3.3 与现行标准的关系（若采纳方案 2）

- S1 复刻令、S4 DS 全链路复刻、A5 锚点验收均需用户裁定修订（「复用载体」相对「复刻语义」的例外，须走 S1「更优方案」三步判定：提前沟通 + 全覆盖对照 + 用户批准）；标准 v3→v4/v5，设计 §2/§11 经 §13.17 并回。
- R4 依赖域不受根本影响：A2 v2.1 是 Datara 侧语义契约，即便 DS 引擎外挂，依赖判定面仍需在 Datara 建模或在桥接层实现，验收口径不变。

## 四、推荐路线（供评估，未裁定）

**主干维持方案 1（其本就是混合架构），新增两项明确化 + 一项开放专项评估**：

1. **AI 助手先做 Vanna（采纳用户提议）**：R8 首个集成组件——datara-backend 内嵌 vanna 库（同栈 Python 3.11 直接 import）+ R8-A 八工具契约面 + chromadb 向量存储 + 悬浮助手测试页（R8-B 门禁）。OM/DH 择一（U4 裁定）与数仓语义层随后接入，不阻塞 Vanna 先行。
2. **OM/DH 外挂定位重申**：设计 §11 原生定位即「可选外部目录/AI 上下文投影」；容器化部署属方案 2 思路的既有组成，与方案 1 不冲突，按 U4 裁定后按需启用。
3. **唯一真正开放分歧点 = R6 调度执行引擎**：建议对 Trae/Codex 发起专项评估——自研引擎达到 DS 基线（重试/容错/补数/优先级/分布式 worker）的逐能力差距与工作量估计，对比 DS 容器外挂 + 语义包裹的桥接面与跟随成本。**若评估结论支持外挂，必须走 S1 例外三步判定（提前沟通 + 全覆盖对照表 + 用户批准）**，且变量 run-snapshot 语义必须在 Datara 侧强制包裹并纳入验收。
