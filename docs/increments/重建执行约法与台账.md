## 一、六条执行约法

### 第 1 条：设计冲突必须即时裁定并刷新

执行过程中发现实现、现有代码、原版交互、运行环境或中间件行为与总体设计冲突时：

1. 暂停受影响的当前步骤；
2. 记录冲突事实、影响范围、候选方案和建议方案；
3. 取得用户批准后才能继续；
4. 批准后的设计必须立即更新并覆盖设计文档；
5. 同步更新增量计划、受影响任务和验收标准；
6. 未批准的方案不得进入代码。

设计文档刷新不是事后补记，而是继续执行的前置条件。

### 第 2 条：用户要求和命令必须留痕

用户在执行过程中提出的每条要求、命令、修改意见和验收结论都必须记录到本台账，至少包括：

```text
编号
时间
用户原始要求或命令
对应增量
影响模块
是否已实现
验证证据
未完成任务
```

不得只依靠聊天上下文记忆。每个增量结束时，必须从台账反向生成“已完成 / 未完成 / 延后 / 阻塞”清单。

### 第 3 条：每次增量必须完成整体验证

每个增量通过前，必须从前端开始牵引验证，并使用 browser-use 操作真实测试页面：

```text
前端测试页面
→ API 请求
→ Backend
→ 中间件
→ 数据源/资源
→ 执行任务
→ 后台日志
→ 页面结果
```

验证至少覆盖：

- 前端页面和交互；
- 浏览器实际请求；
- Backend 接口；
- 数据库迁移和数据写入；
- 消息队列、缓存、对象存储或其他中间件；
- 文件、脚本、资源和权限；
- 执行器和 Worker；
- 后台日志、错误日志和时间戳；
- 页面最终状态和结果统计。

只通过单元测试、接口 curl 或静态检查，不得标记增量完成。

### 第 4 条：增量开始前必须做影响分析

开启新增长量前，必须先完成上一增量对本增量的影响分析：

1. 检查上一增量修改的接口、表、事件、执行器、页面和中间件；
2. 分析对当前增量的直接依赖、反向影响和兼容风险；
3. 必要时调整设计文档和计划文档；
4. 将当前增量拆成可逐步验证的细步骤；
5. 按步骤执行、验证、记录；
6. 当前增量完成后再允许开启下一个增量。

没有影响分析、细化步骤和上一增量验收证据，不得开始新的增量。

### 第 5 条：项目主目录是唯一权威落点

设计文档、增量计划、执行约法、用户要求台账、命令记录、验证证据、运行日志摘要和未完成任务清单，必须写入项目主目录：

```text
D:\需求\数据治理工具\Datara
```

具体规则：

1. 不得把唯一文档留在 `C:\Users\Administrator\.codex\worktrees\...` 等 Agent 临时 worktree；
2. 不得把协作状态只留在聊天上下文或本机记忆中；
3. 多 Agent 读取和写入必须以项目主目录中的文档为准；
4. worktree 可以用于代码隔离，但不能成为设计、台账和验证证据的唯一存放位置；
5. 任何临时副本、导出物或 Agent 本地缓存都必须标记为非权威；
6. 发生文档路径迁移时，必须在台账记录原路径、目标路径、迁移时间和校验结果。

本条优先于工具默认工作目录。所有后续工具调用、文档链接和多 Agent 协作均以项目主目录为准。

### 第 6 条：本机检查与远程运行环境分离

验证环境沿用项目既有约定：

```text
本机：代码检测、静态检查、类型检查、单元级业务逻辑稽核
192.168.1.9：部署、容器服务、中间件、运行资源、接口联调、浏览器端到端验证
```

具体规则：

1. 本机不作为容器服务、消息队列、数据库、Worker 或完整运行环境的验收环境；
2. 本机只执行代码质量检查、契约检查、业务逻辑检查和不依赖运行资源的测试；
3. 需要部署和运行资源的验证必须在 `192.168.1.9` 的隔离工作目录完成；
4. 远程验证必须记录容器状态、服务日志、接口结果、浏览器操作结果和后台运行日志；
5. 未在 `192.168.1.9` 完成的部署或端到端验证，不得标记增量通过；
6. 远程生产目录未经明确批准不得覆盖，验证使用项目既有隔离目录。

## 三、设计刷新规则

设计发生批准变更时，必须同步更新：

```text
总体设计文档
增量开发计划
当前增量台账
接口或数据库契约
验收标准
```

文档中不得同时保留两个未裁定的规范版本。
