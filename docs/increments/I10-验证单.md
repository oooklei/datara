## 二、实测发现并修复的缺陷（已部署 1.9 复测通过）

### 1. `ide_execute` 全局变量 `_ACTIVE` 未声明 global → UnboundLocalError（门 5 抓出）

- 现象：`POST /ide/execute` 返回 500，api 日志 `UnboundLocalError: cannot access local variable '_ACTIVE'`。
- 根因：[ide.py](../../datara-backend/api/ide.py) `ide_execute` 函数内有 `_ACTIVE += 1`，Python 将 `_ACTIVE` 视为局部变量，赋值前读取即报错。`_exec_worker` 已声明 `global _ACTIVE` 但 `ide_execute` 遗漏。
- 修复：`ide_execute` 函数体首行加 `global _ACTIVE`。重建部署后 execute 正常返回 taskId。
- 教训：**模块级计数器在函数内 `+=` 必须显式 `global`**；本机语法检查（py_compile/ruff）无法发现此类运行时绑定错误，需运行时实测覆盖。

### 2. `meta_ops.py` import-csv 用 File/Form 但缺 `python-multipart`（i10-1 隐患，部署首轮抓出）

- 现象：api 容器启动后重启循环，`docker logs` 显示 `ImportError: python-multipart` 依赖缺失（FastAPI File/Form 必需）。
- 根因：[requirements.txt](../../datara-backend/requirements.txt) 未声明 `python-multipart`。
- 修复：requirements.txt I10 段加 `python-multipart>=0.0.9`；容器内验证 `python-multipart 0.0.32`。

### 3. 部署脚本自检方法误用 `app.routes`（部署首轮抓出，非代码缺陷）

- 现象：自检 `IDE_ROUTES 0 PARAM_ROUTES 0` 断言失败，但容器内代码正确（ide.py 13 路由、main.py 含 params 注册），HTTP 探测 `/ide/history` 返回 401（路由命中）。
- 根因：新版 FastAPI 的 `app.routes` 为 `_IncludedRouter` 聚合结构，不平铺 `path` 属性，`'/ide' in p` 永远 False。
- 修复：自检改为 HTTP 探测法（存在的路由未带 token → 401；不存在 → 404），判定 `hist=401 params=401 meta=401` 即通过。

## 五、实测发现并修复的缺陷（第二轮 UI 实测阶段，已部署 1.9 复测通过）

### 4. 部署缺陷：web tgz 带 dist/ 前缀 + bind mount 绑旧 inode（用户实测「页面没变」根因）

- 现象：8090/#/ide 仍是旧版布局；远端 `dist/` 下只有 `dist/dist/index.html`（嵌套）。
- 根因：①首轮 `tar -czf web.tgz -C datara-web dist` 打包带 `dist/` 前缀，解包后成 `dist/dist/` 嵌套；②部署脚本 `mv dist dist.bak; mkdir dist` 后，datara-web 容器的 bind mount 仍绑定**旧目录 inode**（=dist.bak 旧版前端），导致 nginx 一直服务旧页面；③重跑时 tgz 已被删除，脚本按「重跑场景」跳过前端覆盖，陈旧状态固化。
- 修复：正确打包（`tar -czf web.tgz -C datara-web\dist .`，顶层=index.html/assets）→ 重建 dist → `docker compose up -d --force-recreate datara-web` 重绑新 inode → md5 对比（本地=远端=HTTP 响应 37e7cb1a…）+ worker 资产 200。
- 教训：**容器 bind mount 绑定 inode 而非路径，目录级替换必须 force-recreate 容器**；tgz 打包后必须 `tar -tzf` 验证顶层结构再上传。

### 5. 后端缺陷：`quote_ident` 标识符正则不含连字符 → I4/I8 同步表名全端点阻断（U6 抓出）

- 现象：浮层菜单点「结构（DDL）」toast「不合法的标识名: 20260101000000-9999-i3t_x」，DDL 未填充。
- 根因：[dsconn.py](../../datara-backend/common/dsconn.py) `_IDENT_RE = ^[\w$]+$` 不含 `-`，而 I4/I8 同步管道生成的表名规范即含连字符（`20260101-9999-i3t_x`）；DDL/count/rows/audit 等所有走 quote_ident 的元数据端点对该类表全部 400。
- 修复：`_IDENT_RE = ^[\w$-]+$`（反引号包裹后连字符无注入面）；容器内回归 `quote_ident('20260101000000-9999-i3t_x')` → `` `20260101000000-9999-i3t_x` `` 通过；ruff/py_compile 全绿。

### 6. 前端缺陷：单元格复制在 HTTP 非安全源静默失败（U4 抓出）

- 现象：点结果单元格无任何提示（预期「已复制单元格」toast）。
- 根因：用户经 `http://192.168.1.9:8090` 访问属非安全上下文，`navigator.clipboard` 为 undefined，`navigator.clipboard.writeText(val)` 同步抛 TypeError，无降级无提示。
- 修复：[ResultPanel.vue](../../datara-web/src/views/ide/components/ResultPanel.vue) onCellClick 加可选链判断 + `document.execCommand('copy')` 降级 + 失败提示兜底；复测 toast「已复制单元格：1」。
- 教训：**依赖浏览器安全上下文的 API（clipboard/通知等）必须做可用性判断与降级**，内网 HTTP 部署是常态。
