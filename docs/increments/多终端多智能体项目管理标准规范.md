## 2. 事实层：分工台账

台账文件：`docs/handoff/2026-10-16-并行协作分工.md`。

### 2.1 append-only 原则

- **触发条件**：任何角色需要回写台账（心跳、裁定、状态注记）。
- **判定**：仅允许在文件尾部追加；改写、重排、删除历史心跳原文即违规。
- **处置**：过期描述以显式状态注记方式覆盖（如"watchdog 已于 2026-10-18 停机"），注记写在现行段落或文件头部，历史段落一律不删不改（spec：过期内容处置策略）。

### 2.2 心跳编号规则

- **触发条件**：任何角色落台账心跳（含 watchdog 程序告警心跳，占号）。
- **判定**：编号=全局递增；取 git log 提交实锚与台账文件内实锚最大号+1；撞号时先落库者保留、后落库方改号（#136/#44 惯例）。
- **处置**：落库方在心跳内写明"编号实锚：git log 与台账正文最大号 #N；本条占 #N+1"；撞号时改号并在心跳内披露（样例见台账 #343 心跳实锚声明）。

### 2.3 心跳模板指针

心跳模板（必填/可选字段、交付心跳尾部"下一单"自解释条款）的完整表述见 §3.3（流程层）；本层只约束其事实属性：每条心跳落库即成为事实记录，编号、时间、线别缺一不可，字段清单见 §3.3。

### 2.4 单写者原则与共享文件规则

- **触发条件**：多角色需写入同一共享文件（`docker-compose*.yml`、`AGENTS.md`、`docs/increments/` 台账类文件等）。
- **判定**：共享文件实行单写者——谁改谁先声明，另一方只读；台账权威追加按增量归属；一次写窗一个文件。
- **处置**：写窗开启在台账心跳声明；心跳编号池全局共享（watchdog 告警也占号）；实施线文件域独占划分的角色规则见 §4.6（角色层）。

### 2.5 工作区脏项与他线产物处置

- **触发条件**：会话发现工作区存在他线未提交产物、脏项或遗留文件。
- **判定**：不触碰、不清理、不代提交他线产物；涉他线产物的工作区处置须先报备（#286 纪律瑕疵记录在案；守护线携带他线遗留日志行循 #303 先例合规）。
- **处置**：心跳报备（注明文件锚与归属线），等待归属线或监督线处置；紧急自愈（如 git 锁竞争）须留痕披露（样例：台账 #343"文件级提交不可分割，特此披露"）。

## 3. 流程层：执行循环·约法·门禁·证据

### 3.1 增量执行循环与六条执行约法

增量执行循环（收纳自范式 §3）：Scope authority 对表 → RED 契约冻结 → 交叉评审 → GREEN 实现 → 回测门禁 → 证据 + pathspec-only 提交 → 心跳回报。

六条执行约法（来源：约法文件 §一，逐条编号 F1–F6，三段式）：

**F1 设计冲突必须即时裁定并刷新**
- **触发条件**：实现、现有代码、原版交互、运行环境或中间件行为与总体设计冲突。
- **判定**：未取得用户批准即继续受影响步骤=违规；批准后未立即刷新设计文档=违规。
- **处置**：暂停受影响步骤 → 记录冲突事实/影响范围/候选与建议方案 → 取得用户批准 → 立即更新设计文档并同步增量计划、受影响任务与验收标准；未批准的方案不得进入代码。设计刷新是继续执行的前置条件，不是事后补记。

**F2 用户要求和命令必须留痕**
- **触发条件**：用户在执行过程中提出任何要求、命令、修改意见或验收结论。
- **判定**：未记入台账（编号/时间/原始要求/对应增量/影响模块/是否已实现/验证证据/未完成任务）=违规；只依靠聊天上下文记忆=违规。
- **处置**：即时记入台账；每个增量结束时从台账反向生成"已完成/未完成/延后/阻塞"清单。

**F3 每次增量必须完成整体验证**
- **触发条件**：增量通过前。
- **判定**：只通过单元测试、接口 curl 或静态检查即标记完成=违规；未从前端开始牵引验证（前端测试页面 → API → Backend → 中间件 → 数据源 → 执行任务 → 后台日志 → 页面结果）=违规。
- **处置**：按约法列明的验证覆盖面逐项取证；证据规范见 §3.9。

**F4 增量开始前必须做影响分析**
- **触发条件**：开启新增长量前。
- **判定**：无上一增量影响分析（接口/表/事件/执行器/页面/中间件）、无细化步骤、无上一增量验收证据即开工=违规。
- **处置**：完成影响分析 → 必要时调整设计与计划 → 拆成可逐步验证的细步骤 → 按步骤执行/验证/记录 → 当前增量完成后再开启下一增量。

**F5 项目主目录是唯一权威落点**
- **触发条件**：任何设计文档、增量计划、台账、验证证据、日志摘要、未完成任务清单的落点选择。
- **判定**：唯一文档留在 Agent 临时 worktree（如 `C:\Users\Administrator\.codex\worktrees\...`）=违规；协作状态只留聊天上下文或本机记忆=违规；临时副本/导出物未标记"非权威"=违规。
- **处置**：权威文档根=`D:\需求\数据治理工具\Datara\docs`；worktree 可用于代码隔离但不得作权威唯一存放；文档路径迁移必须在台账记录原路径、目标路径、迁移时间和校验结果。

**F6 本机检查与远程运行环境分离**
- **触发条件**：验证环境选择。
- **判定**：本机作为容器/中间件/数据库/Worker/完整运行环境的验收环境=违规；需部署和运行资源的验证未在 `192.168.1.9` 隔离工作目录完成=违规；未在 `192.168.1.9` 完成的部署或端到端验证标记增量通过=违规。
- **处置**：本机只做代码检测、静态检查、类型检查、单元级业务逻辑稽核；远程验证必须记录容器状态、服务日志、接口结果、浏览器操作结果和后台运行日志；远程生产目录未经明确批准不得覆盖。

### 3.2 派单-领单-交付-验收四跳闭环

- **触发条件**：监督线向实施线派发任务，或实施线交付产出。
- **判定**：派单未落台账心跳=违规（会话口头派单作废，#312）；交付回执落库与下一派单未同窗完成=违规（#279，永不分窗）；任务完成立刻未派下一单=违规（派单真空）；领单无心跳回执"任务号+认领+产出承诺"=违规（#45 认领制）。
- **处置**：四跳格式——①派单心跳（监督线，唯一载体）→ ②领单回执（实施线心跳）→ ③交付心跳（实施线，含证据锚+提交号+尾部"下一单"自解释条款，模板见 §3.3）→ ④验收回执（监督线，无台账/git 实锚不放行）。各跳回执格式见 §4.3（角色层）。

### 3.3 心跳模板（完整表述层）

每条台账心跳必须包含：

**必填字段**：
1. **编号**：全局递增，实锚=git log 与台账最大号+1（规则见 §2.2）。
2. **线别**：质量监督线 / Claude 实施线 / Codex 实施线 / AOCI 守护线 / 程序 watchdog。
3. **时间**：Asia/Shanghai。
4. **领单**：所领任务号与派单心跳编号（首跳可写"无/就任"）。
5. **交付**：本跳产出（做了什么、改了什么文件域）。
6. **证据锚**：测试命令与输出定位、证据文件路径（JSON+PNG 成对）、提交号；"报告 PASS"不算独立复现（#265 复核证据纪律）。
7. **下一单触发**：触发条件或等待条件。
8. **Resolved**：闭环结论；未闭环写明卡点。

**可选字段**：阻塞项、worktree/分支/HEAD 声明、写窗声明（pathspec 单文件、零业务触碰、无 push）、编号实锚声明。

**交付心跳尾部自解释条款**（#286）：交付心跳必须以「下一单：已派/待派+触发条件」收尾；"待派"必须写明触发条件（如"监督线复验 PASS 后派 P2-3 开工单"），消除"掉线"歧义。

样例锚：完整交付心跳见台账 #337（Claude 实施线 Track A 交付：领单/交付内容/测试命令与输出定位/提交记录/Resolved+下一单触发）；任务池表见 §4.3 与台账 #343。

### 3.4 六条验收红线

来源：约法文件"提速裁定"门禁红线节 + 范式 §2 门禁。逐条三段式：

**红线 1：真实控件操作真实后端**
- **触发条件**：页面类验收。
- **判定**：以 API-only、静态断言或单元测试替代真实控件验收=违规。
- **处置**：browser-use/Playwright 操作真实测试页面、走真实 Backend 全链路；红线不因提速放宽。

**红线 2：显式人工确认闸**
- **触发条件**：确认短语、验收授权、破坏性操作。
- **判定**：agent 代写或绕过用户确认=违规（台账头部五条硬规则第 5 条）。
- **处置**：一律由用户下发；受委托执行的按 §3.11 留痕。

**红线 3：失败证据保留**
- **触发条件**：任何失败运行。
- **判定**：静默重跑覆盖失败证据=违规；同一问题不静默重跑覆盖=违规。
- **处置**：失败 JSON/截图保留并登记失败 run 编号；阻塞如实写明卡点而非降级标准。

**红线 4：诚实自评**
- **触发条件**：增量/任务状态标注。
- **判定**：接受中间态为终态（弱 PASS）=违规；隐瞒 PARTIAL/NOT CLOSED=违规。
- **处置**：2xx + 终态文案 + runtime complete 三重闸；PARTIAL/NOT CLOSED 如实标注。

**红线 5：契约/集成 TDD 红绿**
- **触发条件**：契约与集成测试。
- **判定**：未先 RED 后 GREEN=违规；契约不用 `xfail/pending-acceptance` 或独立草稿承载而破坏主套件全绿=违规（P1）。
- **处置**：TDD RED→GREEN；契约冻结前的 GREEN 硬前置不抢跑。

**红线 6：token/key 安全边界**
- **触发条件**：凭据、token、key 的读取、传递、落盘。
- **判定**：key 明文入台账/证据/心跳=违规；凭据经命令管道混入会话 transcript=违规。
- **处置**：key 明文零入库零心跳；凭据只经 `docker exec -i` 单向 stdin 传递、stdout 重定向直写文件不过 transcript；转录泄露一律立即轮换 + 审计留痕（范式案例库先例）。

### 3.5 P1–P4 提速规则

来源：约法文件"二次提速与受控流水线裁定"（2026-10-15 用户裁定 P1–P4）。**适用边界**：同一增量内适用；跨增量并行禁止（未完成上一增量验收不得滚动前进）；纯函数快车道条件=不接触 DB、网络、API、UI 的纯函数可走本地测试快车道，但必须保持 TDD RED→GREEN。

**P1 受控并行**
- **触发条件**：当前增量进入远程验证阶段。
- **判定**：下一增量的实现/GREEN/提交在当前增量验收通过前启动=违规；契约不用 `xfail/pending-acceptance` 或独立草稿承载=违规。
- **处置**：可并行准备下一增量的影响分析与契约测试 RED；下一增量 GREEN/实现必须等当前增量验收通过；执行状态须列明当前增量、下一增量及各自阶段。

**P2 范围合并（历史裁定，已入计划基线）**
- **内容**：SQL IDE 合为 `R5-IDE`（内部 `R5-A` 只读与 `R5-B` DDL 写路径两个独立子门禁）；治理 lineage/data_transfer 与治理目录/质量/标准合并为 R6；调度可靠性与任务运维合并为 R7；AI 工具契约作为贯穿各门禁的跨增量验收并在 R8 集成核验；计划改为 9 个编号交付 R0–R8。
- **判定**：与现行设计/计划正文冲突时以正本为准（见权威链声明）。
- **处置**：已入计划基线，按正本执行；本条仅作裁定留痕。

**P3 取证分级**
- **触发条件**：每增量收口。
- **判定**：同域改动分轮取证=违规（可合并一轮）；跨域改动合并取证=违规；以中间步骤留痕替代收口轮=违规。
- **处置**：同一增量内同域多个改动可合并为一轮真实浏览器控件运行，以成对 JSON+PNG 和 `remote-final` 收口；跨域改动仍分轮；认证/权限/DDL/导入/确认闸/数据破坏性高风险动作即时触发；中间步骤只需留 API 请求/响应 JSON。

**P4 第二执行者**
- **触发条件**：需要第二执行者并行。
- **判定**：R3 收口并合回 main 前启动第二执行者=违规；两边同时修改 Backend=违规；文件零重叠破坏=违规。
- **处置**：第二执行者在 R3 收口合回 main 后启动，使用项目内独立 worktree；执行者 1 负责 Backend，执行者 2 仅写 `datara-web/` 和其专属 evidence；同 schema 远程迁移串行；主台账唯一，每位执行者仅追加自己的小节。

### 3.6 收敛闸与轮次上限

- **触发条件**：文档复评 / 修订-复评循环。
- **判定**：复评引入新维度、滚动新基线=违规（#257：复评只对照既有裁定基线判 PASS/FAIL，本轮结果终局，新发现走冻结后勘误通道）；同一对象超 3 轮修订-复评未过审而未互换=违规（#261 用户令）。
- **处置**：超轮 → 修改者与评审者强制互换，报监督线心跳；拒不互换升级用户裁定。

### 3.7 并行度规则

- **触发条件**：多任务派发。
- **判定**：可并行任务（无共享可变状态 + 无依赖 + 独立文件域）未并行派发=违规；串行派单未写明依赖依据=违规（范式 R4/裁定 4；启动提示词任务池要求第 6 条同）。
- **处置**：可并行任务必须多子智能体并行；串行须在派单心跳写明依赖依据，无依据串行即违规。

### 3.8 失败处理与事故披露协议

来源：范式 §6。六步闭环，顺序不可换：

1. **即时披露**：出事即刻心跳披露，不等待、不自行消化。
2. **影响评估**：良性/有害定性，影响面与是否波及在飞循环。
3. **不回滚不改写历史**：避免与在飞循环竞态；恢复走新提交。
4. **留痕**：恢复过程与证据全量留档。
5. **归类**：根因归入事故案例库（案例库回写入口见 §5.4）。
6. **纪律升级**：同类事故重复发生则纪律条款升级（回写本标准，见 §6）。

- **判定**：以临场决策替代协议=违规；事故证据未留痕=违规。
- **处置**：按序执行；范式案例库所载三起暂存区事故为已闭环先例。

### 3.9 证据规范

- **触发条件**：任何交付/复核/验收。
- **判定**：JSON+PNG 不成对=违规；失败证据被覆盖=违规；无提交号实锚=违规；"报告 PASS"无测试命令与输出定位=违规（#265）。
- **处置**：证据目录 `docs/increments/evidence/<增量>/`；失败 run 编号登记；一切交付/复核必须附测试命令与输出定位；基线数字回写台账（允许演进，禁止多版本漂移不收敛）；复现一律用干净 detached worktree（范式 §8 审计清单第 2 条）。

### 3.10 提交纪律

- **触发条件**：任何 git 提交。
- **判定**：add-then-commit（非 pathspec 单文件）=违规；push 远端=违规；临时索引（`GIT_INDEX_FILE`）未恢复=违规；提交含非本线文件=违规。
- **处置**：一律 `git commit -m "..." -- <pathspec>`；禁 push（仓库无远端 push 纪律）；PowerShell 下 `$env:GIT_INDEX_FILE = $null` 会移除变量使后续 git 命令作用于主索引——结束临时索引前必须显式恢复或验证；一次写窗一个文件。

### 3.11 用户专属闸的委托授权与证据留痕

- **触发条件**：确认短语、验收授权、破坏性操作确认等用户专属闸需委托执行。
- **判定**：未获用户授权即代办=违规；受委托执行未在证据标注"经用户委托"=违规；伪称亲自操作=违规（范式 R2/裁定 2）。
- **处置**：用户可授权 agent 委托执行；证据如实标注"经用户委托"；授权与执行证据链留档（可回溯）。

### 3.12 页面自驱动验证与预置输入规则

- **触发条件**：页面功能验证。
- **判定**：回退用户做页面操作员=违规；无预置输入即放弃自驱动=违规（无预置输入导致 agent 无法自驱动 = 页面缺陷）；绕行输入用于生产安全闸=违规。
- **处置**：按钮/输入/浏览一律 browser-use/Playwright/TDD 自行验证；输入绕行优先用预置输入（预填值/测试凭据/演示账号/预置按钮/localStorage 预置点）；绕行仅限验证路径，生产安全闸走 §3.11 委托授权+留痕（范式 R5/裁定 5）。

### 3.13 "没有核实过台账/git 实锚的结论不许报"硬纪律

- **触发条件**：任何角色向监督线/用户报结论。
- **判定**：结论无台账/git 实锚支撑=违规；转录他线声称未亲验=违规（rc16 四次机读证伪其"完成"声称为教训样本，见裁定索引 #273）。
- **处置**：报前自查实锚（git log / 台账行号 / 证据文件）；无法核实即标"未核实"或先核实再报。

### 3.14 沟通纪律

- **触发条件**：任何角色间/对用户的沟通。
- **判定**：不认错先解释、找借口=违规；未用中文=违规；只报喜不报忧=违规；报时间估计=违规。
- **处置**：中文回复；每次回复先进度/难点/质量；认错直接认、先修后解释、不找借口；不报时间估计。

## 4. 角色层

### 4.1 角色拓扑

```
用户（唯一裁定权威）
└─ 质量监督线（派单/裁定/验收/台账/协调/看护治理；AOCI 全权；唯一通信出口）
   ├─ Claude 实施线（生产实施域，交互式长会话，用户终端）
   ├─ Codex 实施线（设计深化+评审域，交互式 + codex exec 双模式）
   └─ AOCI 守护线（仅 AOCI 传输与留痕心跳）
```

状态注记（历史段落不删改，仅注记）：**Trae 线已按 2026-10-18 用户裁定撤换**（原执行者之一，其历史心跳原文保留；见 §4.5）。

各线职责与对接结构：
- **监督线**：派单/裁定/验收/台账/协调/看护治理；唯一可调用 `aoci_*`；唯一有权用 CLI 启动实施线（含首轮，用户 2026-10-18 裁定）。主智能体只与用户通信；另起 1 个对接子智能体负责与两条实施线收发（读写台账心跳、汇总状态、监控启动进程），不代传口头派单、不形成第二信道。
- **实施线**：文件域独占执行；主智能体留守，是唯一对监督线的通信出口；内部可起 2 个并行实施子智能体（子智能体不写台账、不直接 git 提交、不与监督线/用户直接通信）；交付物经主智能体整合后 pathspec 单文件提交。
- **守护线**：仅 AOCI 传输与留痕心跳；不做业务判断。

**启动登记**（用户 2026-10-18 裁定）：监督线每次启动实施线须在台账心跳登记——所用命令、会话/进程标识（claude 会话 id、codex exec session id）、拉起时间；CLI 仅作启动器，不是通信信道；交付判定以台账心跳+提交号为准，进程退出不等于交付，续跑用 resume/同 id 续接（样例见台账 #343）。**CLI 命令模板**：实施线 A（Claude）`claude -p "<提示词>"` 或 `claude --bg "<提示词>"`；实施线 B（Codex）`codex exec "<提示词>"`，续跑 `codex exec resume <session-id>`；工作目录=仓库根，拉起前按本地权限配置核对工具可用性。

### 4.2 权力边界

- **监督线禁止**：亲自做业务验证、业务编码、业务文档（用户 2026-10-18 纠偏令 #237）；业务一律派单给实施线。
- **实施线禁止**：调用任何 `aoci_*` 工具（#85 豁免，见 §4.4）；直接 push；修改非本线文件域；越过主智能体直接与监督线/用户通信。
- **守护线禁止**：业务判断、AOCI 语义撰写（仅传输留痕）。
- **用户保留**：随时叫停与亲自启动权。
- **判定**：越界即违规；越界产出不具效力。
- **处置**：越界心跳披露（#286 先例），监督线裁定处置。

### 4.3 派单/领单/交付回执闭环（四跳格式）

四跳闭环规则见 §3.2（流程层）；本节为各跳心跳格式与任务池表：

- ① **派单心跳**（监督线，#312 唯一载体）：任务号 + 任务说明 + Owner + 证据锚要求 + 文件域声明（零重叠）+ 下一单触发条件。
- ② **领单回执**（实施线，#45）："任务号 + 认领 + 产出承诺"。
- ③ **交付心跳**（实施线，模板见 §3.3）：交付内容 + 测试命令与输出定位 + 提交号 + Resolved + 尾部"下一单：已派/待派+触发条件"（#286）。
- ④ **验收回执**（监督线）：对照证据锚核验，放行/退回；无台账/git 实锚不放行。

**任务池表**（样例见台账 #343）：固定字段=编号/任务/Owner/状态/证据提交号/依赖与下一步，分 Phase 呈现；临时任务单列一节（T 编号）；状态枚举沿用现有用法（待派/已派/已认领/进行中/阻塞/待验收/完成/关闭等），完成态只能由监督线在验收放行后置位；执行情况以该线心跳回执（进度四态：RED/GREEN/证据/提交）为准，监督线不代填、不臆测（任务变更要求第 14 条）。

### 4.4 AOCI 职责边界

来源：AGENTS.md AOCI 集成段 + #85 豁免（2026-10-17 用户裁定）。

- **谁可调用**：监督线（含 AOCI 守护会话/守护线）是唯一可调用 `aoci_*` 工具的角色，全权负责 overview/refresh/maintain/全量传输。
- **谁禁止**：Claude/Codex 实施线禁止调用任何 `aoci_*` 工具，AOCI 义务为零（#85）；实施线认知源=`docs/handoff/` 心跳 + `docs/increments/` 文档。
- **豁免条款**：实施线不执行 AOCI 启动认知检查与维护流程；实施线遇 AOCI 状态问题，报心跳给监督线即可，不得自行处理（#85）。
- **语义批次与传输**：在业务安静窗分批 authoring（逐条自撰 tag/F/R/A/S，≤50/批，`source_sha256` 原样回填；#304/#315 裁定链）；Attestation partial 禁重试（generation 已消费，#315）；传输不阻塞业务（#85 豁免口径）。
- **判定**：实施线调用 `aoci_*`=违规；监督线将 AOCI 语义撰写派给实施线=违规。
- **处置**：违规调用按 §4.2 处置；AOCI 状态以监督线亲自 `aoci_overview check_only` 机读为准，勿信心跳声称（rc16 服务端持久化缺陷教训，见裁定索引 #273）。
