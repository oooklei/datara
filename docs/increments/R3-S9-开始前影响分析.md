## 1. 目标与边界

本增量目标是让新的治理 Backend 能用规范化实体完整表达旧 I18-I23 的现有业务语义和历史记录，并能在隔离目标中经可重入迁移完成承接。规范模型以 Datara 新 Backend 为内部真源；旧库只读，不恢复旧 QC API/engine，不提前融合正式 Vue。

允许范围：`datara_rebuild_i0` additive schema/migration；`datara-backend/rebuild/governance/` 中的模型、repository/service/API；隔离验证页与 runner；本地及远端证据；设计、计划、状态和台账更新。

禁止范围：旧 `datara_meta` 的任何 DDL/DML；旧 `datara-backend/api/*`、旧治理页面和正式菜单/路由；删除/重命名源资产；DROP/TRUNCATE；自动重放历史 DDL；从目标删除 R3-S7 fixture；打印用户口令或导出完整样本业务数据；把可结构化字段塞入 JSON 以绕过建模。

## 2. 前序影响、实物基线与差异

- R3-S6 已在 `datara_rebuild_i0` 安装通用治理 schema；S7 在该 schema 写入过 UI fixture。目标“当前非空”不能直接解释为旧资产已迁入，必须利用 `source_system/source_table/source_id` 和批次号分开统计。
- S8 只读证据 `evidence/R3/s8-source-inventory-20261014.md`：旧 schema 有 57 表；目标隔离 schema 有 16 表。旧 I18 七表合计 45 行；I19 三表均 0；I20 两表均 0；I21 六表均 0；I22 七表中审批/码表/码值各 1 行、总计 3 行；`t_user` 4 行。历史计数是 2026-10-14 采样值，实施前必须重新 SELECT 并确认没有漂移。
- 当前 R3 schema 具有 asset/field/tag/tagging/lineage/quality rule/run/standard/metric/migration batch/item/audit 等通用实体，但缺少模型版本/ER 关系、指标维度和历史版本、质量任务/关联/异常/报告/告警策略、标准码值/命名规则/映射/审批/检查报告的规范化语义。
- 相关旧实现入口已在 S8 核实：I18 `common/models.py` 的 `DwModel*`/字典实体、`api/model.py` 与 `/model/*`；I19 `MetaTableExt/MetaTag/MetaTagging`、`api/meta.py`；I20 `Indicator/IndicatorVersion`、`api/ind.py`；I21 `Qc*` ORM 和六张表，旧 router/engine 已退役；I22 `Std*` ORM、`api/std.py` 与 `/std/*`；I23 `t_user` 与授权关系。旧 API/页面是语义证据，不是新 Backend 运行时依赖。

## 3. 规范化模型与来源映射

物理表名/字段最终以设计 §5.2 契约及实现 migration 为准；每个迁移实体必须有 `(source_system, source_table, source_id)` 唯一来源身份、`migration_batch_id`、非空 DB 生成的 `created_at/updated_at/generated_at`，并保留源创建/更新时间的独立字段，避免用目标生成时间覆盖历史时间。

| 源域 | 新模型族 | 迁移顺序与关系要求 |
|---|---|---|
| I23 `t_user` 与旧静态角色权限 | 既有 rebuild_user/rebuild_project_member + legacy identity mapping | 先对齐稳定用户 ID 和角色权限映射到 R1 冻结的 Role/Permission/ROLE_PERMISSIONS；不新建动态 RBAC 真源。S9 全量盘点若找到旧项目成员关联表再迁移该关系，否则不推断历史项目成员。登录名冲突、权限点无映射则隔离该记录并显式报错。只导入兼容凭据哈希；否则保留账号身份映射并进入密码重置流程，不读写明文凭据。 |
| I18 domain/layer/engine/model/field/relation/version | governance domain、warehouse layer/engine/model/field/relation/version | 字典先于模型；模型先于字段/关系/版本。ER 两端字段需解析成关系子行；保存画布位置、模型状态、字段精度/标志和完整历史 snapshot。最近 DDL 仅归档文本，不执行。 |
| I19 table extension/tag/tagging | asset metadata extension + 既有 asset/tag/asset-tag + legacy tag reference | 以 datasource/db/object 自然键映射 asset；可解析挂接落 asset-tag，任意 target_type/key 与未解析引用落规范化引用表，不丢 source mapping。 |
| I20 indicator/version | 既有 semantic metric + metric profile/dimension/version 子实体 | 指标到 asset/字段引用可以 unresolved；profile 保存来源/周期/单位/定义/输出任务，维度独立建行，状态与每版快照完整。 |
| I22 element/code/value/naming/mapping/approval/check | standard element/code set/value/naming/mapping/approval/check report，加既有 standard identity | 先元素与码表，再码值/规则/映射，再审批和检查报告；保留父子关系、版本、状态、意见、来源目标。审批旧业务键用 source identity 关联，不假造新审批目标。 |
| I21 rule/task/task-rule/run/exception/report/alarm | 既有 quality rule/run + rule definition/task/task-rule/run legacy details/exception/report/alarm policy | rule definition 规范化保存目标键、类型、参数、阈值和状态；run legacy details 保留旧触发/计分/统计，即使目标 asset 无法解析也不造假资产。当前采样为 0 行仍须实现完整实体、空集合 API 和约束测试。QC 新 API 不负责执行旧引擎；历史数据只迁移，未来执行由新 quality worker/治理服务负责。 |

迁移器需把“迁移批次元信息”和“每条来源对象 checkpoint”作为独立事实；每源行的结果为 imported/skipped/conflict/rejected，携带稳定目标 ID、规范化摘要、错误和重试计数。唯一键冲突必须比较摘要并判定同内容幂等跳过或异内容冲突，禁止覆盖。目标外键限制使用 RESTRICT/NO ACTION；回滚由批次拥有关系显式处理，不做级联删除业务记录。

## 4. 影响面和向后兼容/隔离策略

- 影响后端：治理 models、additive Alembic/rebuild migration、repository/service、治理 API schema、迁移器和 tests/rebuild；避免把 R1 identity 或 R3 S1-S7 已提交文件大范围重排。
- 影响数据：目标仅 `datara_rebuild_i0` 新增表/列与新批次记录。R3-S7 fixture 原样保留，迁移源记录带独立批次标识；目标现有通用实体如果要与历史来源合并，必须通过稳定自然键和显式映射服务完成，不可按名称猜测覆盖。
- 影响消费者：R5 lineage、R6 governance、R11 AI 工具可能引用新实体，故冻结新 API schema 后同步 contract tests；新增 API 必须 project-scoped 并写审计事件。
- 隔离验证页：只改 rebuild validation HTML/runner，不改正式 SPA。页面按参考系统对象浏览、详情、版本/关系、质量任务/报告、标准码值审批等真实操作流组织；预置非敏感 fixtures 可供用户直接操作。页面调用 R1 token bootstrap 与新 Backend API。
- 部署：仅在 192.168.1.9 的非正式端口和隔离容器/库执行。部署前记录镜像、compose effective config、service/container/schema identity 和恢复点；不得重启旧 `datara-api` 或修改生产正式前端入口。

## 5. 细化执行步骤与每步验收

1. 重做只读基线：对旧源表/目标表精确 count、字段/索引/外键/默认值、数据库版本与上海时间；对目标所有 S7 fixture 做来源标签盘点。若源表计数与 S8 证据漂移，更新证据和迁移范围后再继续。
2. 模型契约先行：为来源身份、版本、历史关系、时间戳、项目授权、迁移状态、错误恢复和回滚编写失败测试；验证非法外键、重复键、版本间断、孤儿关系和未解析 target 的处理规则。
3. 新增 ORM 和 additive migration：按设计 §5.2 实现全部规范化实体，包括 `legacy_tag_reference`、`semantic_metric_profile`、`quality_rule_definition`、`quality_run_legacy_details`；验证 offline diff 仅增加目标对象，不出现旧 ORM 导入、DROP/TRUNCATE、旧 schema 引用或 `create_all` 副作用。
4. 新增 repository/service/API 和 migration dry-run：支持按域预览源/目标数、冲突、映射、关系/孤儿、将写入行；支持域级暂停、逐行 checkpoint、幂等重跑和错误查询；所有写请求 project scoped/audited。
5. 本地门禁：R3-S9 定向 pytest、后端全量 `pytest tests -q`、Ruff、compileall、前端隔离页 lint/test、`vue-tsc --noEmit`、`git diff --check`。本机只做代码与逻辑检查，不伪造远端 MySQL 证据。
6. 建参考驱动验证页：从 OpenMetadata/DataHub 与相应标准/质量管理产品的可验证 UI 用户流程选择对象目录、详情/版本、映射、任务/异常/审批；建立有标签 fixture，用户能在表单里查看并执行，不是只有 API 按钮。对关键正/负路径作 browser-use 验收；阻塞时依 R2-14 在同一页面用 Playwright。
7. 远端部署前核环境与备份：只读确认受限目标 schema、mysql/API/worker/redis 等依赖健康、当前镜像和日志；对目标 schema+数据做一致性快照并验证可读、hash 可复核。备份失败或隔离身份不明确即停止。
8. 先 dry-run，不写数据：旧库使用经验证的 SELECT-only 身份；目标写权限限定 rebuild schema。人工审阅每个域的 expected/imported/skipped/conflict 数及关系计划，任何非预期更新/删除均为硬阻断。
9. 批次导入：仅当 dry-run、快照与本地/页面契约门禁均通过，按设计 §5.2 顺序分域导入目标隔离 schema。所有请求/脚本输出不得携带口令、连接串或完整业务样本；进程/容器日志实时记录时间戳和退出码。
10. 全面对账：逐表核对源总数 = imported + 同内容 skipped + 显式 rejected；目标 source identity 覆盖率 100%（可解释拒绝者逐条列出）。比较字段摘要、FK/关联边、版本/审批链完整度、孤儿/重复自然键、源/目标时间字段及 DB generated timestamps。任何未解释差异 >0 不通过。
11. 异常恢复：注入重复提交、源记录改变、非法 FK、批次中断恢复、双请求并发和无引用约束回滚；检查无重复、无覆盖、批次可重入、回滚仅作用于本批次且目标仍可启动。测试用 fixture 必须与真实迁移 batch 分开，不能销毁用户数据。
12. 控件级验收与运行稽核：验证页执行浏览/筛选/详情/版本/映射/审批/质量任务结果查看；数据库行、API响应、页面值一致；容器与依赖健康、日志窗口无新增 ERROR，所有相关记录时间戳来自 DB/backend。
13. 证据、台账、独立提交：将源/目标快照指纹、dry-run、执行统计、parity SQL/摘要、UI run/截图索引、服务与日志检查、恢复演练写入 `docs/increments/evidence/R3/`；更新 R3 状态、计划和台账后只提交 R3-S9 文件，严禁混入其他脏改动。

## 6. 验收标准与停止门

- 结构覆盖：I18-I23 每个旧表均映射到规范实体/关联，零数据源也验证空集行为；字段、自然键、状态/枚举、时间、关系、版本、作者及来源身份均有映射表。
- 数据保真：各来源记录均有 imported/skipped/rejected/conflict 的逐行终态和原因；未解释 source ID 缺口、字段差异、关系差异、孤儿、目标重复数均为 0。关系和历史版本/审批链完整率 100%。
- 幂等与可靠性：重复完整执行无重复/覆盖；中断恢复后 checkpoint 一致；并发任务有互斥/去重；目标批次回滚可验证，旧源行数/哈希不变。
- 行为与时间：关键控件闭环；查询响应契约稳定；新增业务/运行/迁移记录的 `created_at/updated_at/generated_at` 非空，来源业务时间单独保真，时间语义 Asia/Shanghai 明确。
- 工程门：Ruff、compileall、pytest 全绿；前端静态页/runner、`vue-tsc --noEmit` 全绿；远端 API/容器/数据库/中间件健康和日志窗口有带时间戳证据。
- 停止条件：任何违反源只读/目标隔离、快照不可用、schema 漂移、mapping 歧义、身份/权限越权、额外变更、浏览器及 Playwright 均阻塞、parity 差异、服务错误，均停止该批次并回写证据/台账，禁止以局部成功宣告 PASS。

本文件是开工影响分析，不是迁移执行批准的替代品；用户已批准模型方向。实际远端写入仍需先通过该增量本地、控件和快照/dry-run门禁，执行范围严格限隔离目标。

## 本轮映射实现细化（继续遵守本影响分析）

- 每次 dry-run/import 请求必须显式提供经授权的目标 `project_id`；旧 I18-I23 源对象缺少项目关系时，不按所有者、名称或当前用户推断项目成员关系。未提供目标项目即拒绝生成可导入映射。
- 规范实体外键只接受由 `(source_table, source_id)` 身份映射表解析出的目标 ID。目标 ID 尚未生成的同批父行使用 `TargetIdentityReference` 符号引用；只有引用在当前批次源身份集合（包括源表已明确声明的唯一键别名）中存在，图校验才放行。未知引用保持 unresolved 并阻断；不得自动置空或做模糊同名匹配。旧模型的业务域关系声明为 `biz_domain -> t_biz_domain.name`，映射时保留域表原 ID 主身份，同时显式登记域名关系别名。
- 当前纯映射覆盖 I18 七张源表（domain/layer/engine/model/field/relation/version），并通过本地契约测试；图校验检查同批模型引用、重复源身份和关系两侧字段是否存在。关系若指向批外已存在目标模型，dry-run 必须带上该模型已读字段快照；缺快照不能宣称字段关联校验完成。I19-I23 映射、dry-run、API、验证页和远端门禁仍须逐项实施。
- 离线 dry-run 计划契约要求明确 project-bound `I18TargetSnapshot`：只读快照包含项目、时区明确的采集时间、SHA-256 摘要、来源身份到目标 ID/语义指纹、目标模型字段集合、项目范围唯一键占用者。仅依据该快照分类 create/unchanged/conflict/blocked；内容不一致及自然键占用均为 conflict、不自动更新；父记录冲突/阻断会阻断新子记录。快照项目不匹配、数据行项目不匹配、缺少现存身份目标 ID 均 fail closed。
- 目标快照 repository 已按 project scope 批量 SELECT 新库 domain/layer/engine/model/field/relation/relation-field/version；重建一致的旧行语义，产出 source identity→target ID/指纹、关系字段、模型字段集、自然键占用和 SHA-256 快照摘要。SQLite 集成测试拦截 SQL 并确认只有 SELECT；其余项目数据不进入快照。仅证明本地 SQL 逻辑，不证明远程 MySQL 权限/性能/环境。
- 2026-10-15 本地测试基线：`pytest tests/rebuild -q` 72 passed；全后端 `pytest tests -q` 609 passed；Ruff、compileall、diff-check 均通过。只证明本地纯映射/计划逻辑和 SQLite SELECT repository，不证明旧库读取或目标库远端快照。
