## 一、范围与真源

### 1.1 本增量范围

增量 4 是项目上下文层之后的任务中心核心骨架，范围严格取自 WBS §四「增量 4」：

1. 迁移并挂载组件规格端点，保留 ETag/304 与 degraded 回落语义；
2. 落地任务中心布局蓝本四要素：顶部视角页签、画布多 Tab、Palette 双 Tab、工作流目录树；
3. 工作流类型收窄为 `wf/sync/stream` 三分类；
4. 对接 workflow 域六模型和 12 个现有端点，贯通创建、编排、保存、回读和发布；
5. 对接 trial 域试运行能力：草稿快照、单节点、指定节点/子图、变量覆盖、依赖模拟、DryRun、SQL 预检、转正式。

计划文件把前端目标目录写为 `datara-newweb/src/views/taskcenter/**`、`src/stores/dagTabs.ts`、`src/graph/**`。当前主工作区尚无 `datara-newweb/src`，因此增量 1 工程骨架（0.7 方案为其设计输入）及增量 2/3 的布局、路由与项目上下文是硬前置。本预研不把旧 `datara-web` 直接改造为交付目标。

### 2.3 workflow 后端已具备的六模型

`datara-backend/rebuild/workflow/models.py` 已定义：

| 模型 | 核心关系/约束 | 前端用途 |
|---|---|---|
| `workflow_definition` | `project_id` 非空；项目内名称唯一；持有当前版本 | 列表、工作流元信息、草稿入口 |
| `workflow_version` | definition 下版本号；不可变快照 digest；发布态 | 版本列表、版本详情、回看 |
| `workflow_node` | definition/version 归属；草稿以 `version_id=NULL` 区分 | 画布节点保存/回读 |
| `workflow_edge` | definition/version 归属；from/to 节点关系 | 画布连线保存/回读 |
| `workflow_schedule` | definition 关联调度配置 | 本增量对齐类型，完整 UI 后置增量 9 |
| `workflow_publish` | definition/version 发布记录 | 发布结果与审计呈现 |

现有 workflow 路由挂载于 `/api/v1/rebuild/workflows`，实际 12 端点为：定义 create/list/get/update/delete（5）、草稿节点 upsert/delete（2）、草稿边 upsert/delete（2）、publish（1）、版本 list/detail（2）。所有项目作用域调用均需携带 `project_id` 并服从项目授权闸门。

### 2.4 trial 后端已具备的能力

trial 路由挂载于 `/api/v1/rebuild/trial`。当前源码已不是 WBS 文字中的“2 端点”，而是 7 个路由：snapshot create/get、definition run/promote、run create/get/promote。`TrialRunOptions` 已提供：

| UI 能力 | 后端实锚 | 说明 |
|---|---|---|
| 草稿试运行 | `POST /definitions/{id}/snapshot` + run | 快照与正在编辑的草稿隔离，digest 幂等 |
| 单节点 | `options.node_codes=[one]` | 单节点是指定节点集合的特例 |
| 指定节点/子图 | `node_codes[]` 或 `start_node` | 两种语义不同：集合 vs 从起点向后可达子图 |
| 变量覆盖 | `test_variables` | 写入实例变量运行快照，来源为 test override |
| 依赖模拟 | `dependency_mock` | dependency id → 状态 |
| DryRun | `dry_run=true` | 只校验并返回拓扑 plan，无执行副作用 |
| SQL 预检 | `sql_precheck=true` | 执行前校验 SQL |
| 转正式 | promote 路由 | 要求当前草稿 digest 与试运行快照一致；重复 promote 幂等 |

`test_trial_runner_extensions.py` 覆盖 WF-15~WF-20，`test_trial_e2e.py` 覆盖 draft→snapshot→TRIAL run→output→promote。后端能力总体可接，但前端没有对应 client 与工作台交互。

### 2.5 关键现状差异

1. WBS 4.5 写“trial 域 2 端点”，当前实现有 7 路由；拆票前必须冻结前端只消费哪一组 canonical 路由，避免同时接 definition 风格和 run 风格重复面。
2. 旧前端 Palette 仍有 `etl` 推导与 mock seed 分支，不符合三分类裁定。
3. 旧前端页面有演示模块内容，权威设计只允许保留框架。
4. workflow 六模型已落库，但 12 端点并非每个模型一套 CRUD；前端应围绕聚合定义/草稿 DTO 设计，不应机械生成六套资源 client。
5. 组件 spec 端点仍在旧 `datara-backend/api/component_spec.py`，WBS 明确要求迁入 rebuild 后再由新前端消费。

## 三、目标架构与接口

### 3.1 前端分层建议

```text
/p/:projectId/task-center
  TaskCenterShell                 顶部视角页签和内容门控
    OrchestrationView             任务编排主视角
      WorkflowTreePanel           工作流目录树与三分类
      DagTabBar                   最多 5 个画布、关闭策略、持久化
      DagWorkspace (KeepAlive)    每个 definition 独立编辑会话
        ComponentPalette          spec 驱动组件库
        WorkflowCanvas            workflow node/edge DTO 适配
        Inspector/RunPanel        节点配置、校验、试运行
    RuntimeRouteOutlet            增量 8 接入点
```

推荐模块职责：

- `services/workflowApi.ts`：只负责 12 个 workflow 端点及 envelope 适配；
- `services/trialApi.ts`：只负责冻结后的 canonical trial 路由；
- `services/componentSpecApi.ts`：ETag 缓存、304、degraded 状态；
- `stores/workflowCatalog.ts`：当前项目的工作流列表、分类树、过滤；
- `stores/dagTabs.ts`：标签生命周期与本地持久化，不保存服务端业务真源；
- `stores/dagSession.ts`：按 definition 隔离 dirty、saving、revision、validation 状态；
- `graph/adapters/workflowDto.ts`：后端 node/edge 与画布模型双向映射；
- `graph/adapters/componentSpec.ts`：spec schema 到 Palette/Inspector 的只读适配。

### 3.2 数据流

1. 路由守卫确认 `projectId`，API 层自动注入同一 `project_id`。
2. 工作流目录树调用 list definitions，三分类是展示/筛选语义，后端分类字段若尚未具备不得由 localStorage 假造真源。
3. 打开 definition 时创建或激活 DAG Tab；get definition 一次回读 definition + 当前草稿 nodes/edges。
4. Palette 从 component spec 加载，拖入节点时写入 `{node_code,node_type,componentRef,params,position}` 的适配结果。
5. 保存采用显式 dirty 集合或草稿差量队列，逐个调用 node/edge upsert/delete；任一失败时保留 dirty 并给出可重试反馈。
6. 试运行先保存并确认回读一致，再创建 immutable snapshot，提交 options，读取 run output；promote 前再次检查 digest。

### 3.3 前端契约最小面

| 契约 | 最小方法 | 关键字段/约束 |
|---|---|---|
| workflow | create/list/get/update/delete definition；upsert/delete node；upsert/delete edge；publish；list/get version | `project_id` 必须来自 URL 上下文；统一 `{code,msg,data}`；错误不可吞并为成功空数据 |
| trial | create/get snapshot；run；get run/output；promote | `snapshot_id`、六项 options、`trial_snapshot_id`、digest、plan/logs/variables/stats |
| component spec | get spec with conditional request | ETag/If-None-Match、304 复用、degraded 明示；前端零私设组件 |
| tabs persistence | load/save last tabs and snapshots | 固定继承 `datara.dag.last*`、`snap.*` 键；数据需带 project/definition 身份与 schema version |

### 3.4 状态与并发纪律

- Tab 的 `key` 应由 `projectId:definitionId` 构成，避免跨项目串画布。
- 每个 Tab 独立维护 `clean/loading/dirty/saving/error`，关闭三选为保存并关闭、放弃并关闭、取消。
- KeepAlive 仅缓存 UI 实例；服务端回读数据与保存结果仍是真源。
- 保存期间禁止同一实体并发重复提交；不同 Tab 可并行，但切项目时必须清空或隔离旧项目会话。
- localStorage 只保存恢复线索和明确允许的草稿快照，不能替代 workflow 草稿表。

## 结论

增量 4 后端 workflow/trial 核心能力已经基本具备，主要工作量集中在新前端从零建立项目隔离的任务中心壳、spec 驱动 Palette、画布 DTO 适配、可靠草稿保存和试运行交互。当前最大的不确定性是 trial canonical 路由、工作流分类持久化以及 node/edge 非原子保存策略。建议先发 4-P0 契约冻结票，再按上述 22 票推进；未解决三项开放问题前，不应把 L⛏ 包直接合并成一张实现票。
