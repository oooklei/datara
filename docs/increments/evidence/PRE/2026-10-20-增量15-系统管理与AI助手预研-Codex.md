## 一、范围与真源

### 1.1 增量范围

本增量承接 G 系统管理组和 H 全局 AI 能力，包含五条业务链：

1. 权限管理：消费 identity 域四角色 RBAC，形成用户/角色/项目成员权限管理闭环；
2. API 管理：开放 API 定义、发布、启停与权限范围管理，新建模而非旧实现迁移；
3. API-Key 管理：密钥签发、吊销、轮换、作用域与调用日志关联，新建模；
4. LLM 模型配置：新建 `rebuild/llm/` 独立域、`rebuild_llm_model` 表和 6 端点，提供配置与连通性测试页，作为 FV-02 产品化解阻路径；
5. AI 悬浮助手：认证后应用壳全局单实例挂载、十类页面上下文、八工具统一信封调用；不增加一级菜单。

脱敏与审计虽归 G 组聚合，但 WBS 明确为“裁决前不开发页面”，不纳入本增量实现。调用日志只作为 API 管理附属能力，呈现形态尚待用户确认。

## 二、现状证据

### 2.1 RBAC 与 identity 域

`rebuild/identity/contracts.py` 已冻结四角色：`admin/developer/operator/viewer`，并以 `ROLE_PERMISSIONS` 映射项目、工作流、任务、数据源、SQL、调度、血缘、质量、标准、安全和审计权限。`authorize()` 已被各域授权闸门复用。

`rebuild/identity/models.py` 当前有三张核心表：

| 表 | 已有能力 | 限制 |
|---|---|---|
| `rebuild_user` | 用户名、密码摘要、平台角色 | 单一 role 字段，不是自定义角色/权限配置模型 |
| `rebuild_project_member` | 项目成员及项目内角色 | 角色沿用四角色字符串 |
| `rebuild_active_token` | 登录 token 与角色快照、撤销 | 角色变更后的 token 失效策略需明确 |

`rebuild/api/app.py` 已提供 login/logout、项目成员新增/列表/删除等接口；新增成员接口可承担成员角色写入。但未见全局用户列表、用户创建/停用、平台角色更新、角色权限矩阵读取等正式管理端点。因此 WBS 15.1 所称“权限管理闭环”不能只做现有项目成员页，需先冻结产品范围和补齐管理契约。

### 2.2 API 管理与 API-Key

在 `datara-backend/rebuild` 与对应测试中未发现开放 API 定义、API-Key 签发或 API 调用日志业务模型/路由。现有 `/openapi.json` 是 FastAPI 描述文档，不等于产品“API 管理”。权威设计和 WBS 已明确：此域是用户裁定的新建模，§6.2 旧逻辑迁移规则不适用。

### 2.3 LLM 配置与 FV-02

`ai_copilot/config.py` 当前只接受四个环境变量：`LLM_PROVIDER/LLM_BASE_URL/LLM_MODEL/LLM_API_KEY`；配置必须四项齐全，provider 白名单为 `siliconflow/volcengine`，base URL 必须是 HTTPS，api_key 使用 `SecretStr`。`adapter.py` 在未配置时明确报 LLM disabled。

当前仓库没有 `rebuild/llm/`、`rebuild_llm_model` 或 `/api/v1/rebuild/llm-models`。`cryptography>=42.0` 已在 requirements 中；未检出 httpx 依赖，实施连通性测试前需确定复用的 HTTP 客户端或补依赖。

权威设计 §5E 已批准以下目标：数据库默认模型优先、环境变量兜底；API key 使用 AES-256-GCM 可逆加密以供出站调用；响应仅掩码；默认模型全局唯一且禁删；连通性测试返回状态、摘要与耗时。

### 2.4 AI Bridge 与旧验证面

`rebuild/ai_bridge.py` 已冻结 8 个工具及顺序：

1. `search_schema`
2. `validate_sql`
3. `run_sql`
4. `get_workflow`
5. `validate_workflow`

## 四、目标方案

### 4.1 总体架构

```text
G 系统管理菜单
  PermissionsView ─────── identity/admin API
  ApiManagementView ───── openapi domain
  ApiKeyManagementView ── openapi domain
  LlmModelsView ───────── llm domain ── encrypted provider credential

AuthenticatedAppShell
  RouterView
  AiAssistantLauncher ─── context providers
      AiAssistantDrawer ─ ai_bridge tools/tool-calls
                           └─ default LLM resolver: DB first, env fallback
```

建议域边界：

- `identity`：平台用户、固定四角色、项目成员、权限矩阵；
- 新建 `openapi`：开放 API、API-Key、调用日志；避免与 FastAPI OpenAPI schema 命名混淆，最终 Python 包名可用 `api_management`，URL 仍由契约冻结；
- 新建 `llm`：模型配置、密钥加密、默认模型解析、连通性测试；
- `ai_bridge`：只保留工具发现与调用信封，消费 llm 默认模型解析端口，不承载配置 CRUD。

### 4.2 权限管理目标

权限页建议拆成两层：

1. 平台用户：管理员查看用户、创建/停用用户、修改四角色；固定角色不可编辑权限集合。
2. 项目成员：项目 owner/admin 添加、改角色、移除成员；沿用 `project_permission_error` 的项目隔离。

必须补的后端契约候选：用户列表、新建、启停、修改平台角色、角色权限矩阵只读查询。项目成员已有新增/列表/删除，可确认“重复新增是否等价更新角色”；若语义不明确，增加显式 PUT。

安全规则：最后一个 admin 不可降级/停用；用户不能提升到高于操作者的角色；角色变更后撤销或刷新既有 active token；所有管理动作写审计。

### 4.3 API 管理与 API-Key 新建模建议

建议最小模型分三表：

| 模型 | 核心字段 | 约束 |
|---|---|---|
| `rebuild_api_definition` | id、name、path、method、description、required_permission、status、version、created_by、timestamps | method+path+version 唯一；仅允许登记受控 facade，不允许任意代理 URL |
| `rebuild_api_key` | id、name、key_prefix、key_hash、scopes_json、expires_at、status、last_used_at、created_by、revoked_at、timestamps | 原始 key 仅签发响应显示一次；库内只存 hash，不可逆；支持吊销和轮换 |
| `rebuild_api_call_log` | request_id、api_id、key_id、principal/project、status_code、latency_ms、result、error_code、requested_at | 不记录原始 key、敏感 body 或完整 SQL；索引时间/api/key |

API-Key 与 LLM provider key 必须采用不同策略：开放 API-Key 用 hash-only 验证，LLM key 因需出站调用才用 AES-256-GCM 可逆密文。二者不得共享表或序列化器。

最小服务链：创建 API 定义→发布/启用→签发 key（一次性明文）→携 key 调用受控 API→鉴权 scope/有效期/吊销状态→写调用日志→管理页可检索。调用日志写入失败的 fail-open/fail-closed 策略需按调用类型裁定，至少不能伪造审计成功。

### 4.4 LLM 独立域目标

按 §5E 原样落实 `rebuild_llm_model` 字段与 6 端点：

| 方法与路径 | UI 动作 | 关键语义 |
|---|---|---|
| GET `/api/v1/rebuild/llm-models` | 列表 | key 掩码，分页 |
| POST `/api/v1/rebuild/llm-models` | 新增 | name 冲突 409；默认位原子切换 |
| PUT `/api/v1/rebuild/llm-models/{id}` | 编辑/启停 | api_key 留空不覆盖 |
| DELETE `/api/v1/rebuild/llm-models/{id}` | 删除 | 默认模型 409；前端二次确认 |
| POST `.../{id}/test` | 连通性测试 | 最小对话、connect 10s/总超时 30s、耗时与摘要 |
| PUT `.../{id}/default` | 设默认 | 仅 active 可设，全局唯一 |

加密服务使用独立 `LLM_ENCRYPTION_KEY`，密文需包含算法版本、nonce 和 ciphertext/tag 的可解析封装，以便未来轮换。完整 key 只在写入、测试出站和 AI 请求期短暂存在内存，禁止日志、响应和证据落盘。

默认配置解析接口建议为后端内部 port：每次请求或短 TTL 缓存读取数据库默认 active 模型；数据库无可用默认时才加载四环境变量。读取时点必须统一，避免设置默认后必须重启才生效。

### 4.5 AI 全局悬浮助手目标

- `AiAssistantLauncher` 在认证 AppShell 中只挂一次；跨业务路由保持抽屉会话，页面上下文随路由更新。
- 十类上下文：项目、工作流、节点、SQL、数据源、变量、运行记录、数据统计、元数据、血缘。上下文由路由 meta + 显式 provider 生成，不读取页面私有组件状态。
- 对话链建议分两类：纯问答/生成 SQL 走 LLM adapter；实际动作全部走 `ai_bridge/tool-calls`，不得绕过权限和审计。
- NL→SQL 必须为 generate→展示→用户确认→`run_sql`，禁止自动执行生成文本。
- 未接线工具显示“能力暂不可用”并携注册表状态；不渲染假成功。
- FV-02 未解除时允许交付 UI 骨架与 mock 契约测试，但生产入口要显示明确不可用/配置引导，不把 mock Agent 接到正式入口。

## 七、验收与风险

### 7.1 验收矩阵

| 验收面 | 必验判据 | 证据 |
|---|---|---|
| RBAC | 四角色、平台/项目两层、越权拒绝、token 失效 | pytest + Playwright + 审计记录 |
| API 管理 | 定义→发布→key 签发→调用→日志 | 契约测试、真实 8001 网络记录、日志回链 |
| API-Key 安全 | 原 key 仅一次显示、DB hash-only、轮换/吊销/过期 | DB 断言 + 响应断言，证据不得含真实 key |
| LLM 6 端点 | CRUD/test/default 与全部异常 | pytest + 前端 contract tests |
| 红线 8 | `api_key_cipher` 非明文、响应掩码、测试不回显 | DB/JSON 成对断言；证据使用专用假 secret |
| FV-02 | DB 优先/env 兜底、默认 active 模型真实测试成功 | resolver 测试 + 外部最小请求记录（脱敏） |
| AI 八工具 | 名单无缩水；每项 enabled 状态与 handler 一致 | 注册表快照 + 逐工具成功/拒绝/错误测试 |
| AI 主权 | generate 不执行；run_sql 仅 R5-A；所有动作经权限与审计 | 注入端口断言、审计 request/tool_call id 回链 |
| 全局挂载 | 认证业务页单实例、登录页无入口、十类上下文、无一级菜单 | Playwright + 菜单配置 diff |
| S6 | 凭证与加密 key 不入代码、日志、心跳、证据 | secret 扫描与部署清单核对 |

### 7.2 主要风险

| 风险 | 等级 | 缓解/门禁 |
|---|---|---|
| 把 FastAPI OpenAPI schema 当成产品 API 管理 | 高 | 新建模评审，术语与包名显式区分 |
| API-Key 与 LLM key 共用存储策略 | 高 | API-Key hash-only；LLM key AES-GCM；分表、分服务、分测试 |
| 密钥出现在响应、日志或测试证据 | 高 | 统一掩码 serializer、日志过滤、专用假 secret、红线 8 自动断言 |
| 默认 LLM 切换并发造成多个默认 | 高 | 事务内清零+设定，数据库约束/锁及并发测试 |
| 加密主密钥丢失或轮换破坏存量 | 高 | 版本化密文、轮换 runbook、双钥读取窗口、备份恢复演练 |
| FV-02 只测 TCP/HTTP 而误报解除 | 高 | 以最小真实生成成功、默认 resolver 生效及无泄露为判据 |
| 八工具注册表被误报为八工具已接线 | 高 | registry 明确 enabled/disabled；逐工具 handler 与测试才可转 GREEN |
| mock Agent 被接入正式入口 | 高 | mock 只在测试构建/验证页；生产 bundle 和正式路由均无引用 |
| 权限 UI 隐藏替代后端鉴权 | 高 | 所有管理端点 admin/permission 校验；直接请求越权测试 |
| 角色变化后旧 token 继续高权限 | 高 | 角色变更原子撤销 token；跨 worker 数据库 token store 验证 |
| API 调用日志记录敏感 body/SQL/key | 高 | 字段白名单、摘要化、容量与保留策略评审 |
| 全局抽屉从页面私有状态抓取敏感数据 | 中 | 显式 context provider + 字段白名单；路由切换清理过期上下文 |
| 外部供应商波动拖延整个增量 | 中 | 真实联调单票挂起；其余本地能力按阻塞传导规则继续 |

## 结论

增量 15 不是单纯的“系统管理页面包”。它包含三种不同安全语义：固定四角色 RBAC、面向入站调用的 hash-only API-Key、面向出站 LLM 的可逆加密凭证；必须分别建模和验收。现状中 RBAC 核心已存在但管理面契约不足，AI Bridge 已有八工具信封但默认仅 `run_sql` 接通，API 管理与 LLM 域尚未落地。建议先完成 15-P0 契约冻结，再按 23 个主票推进；FV-02 仅挂起最终真实 LLM 联调，不应阻塞配置、安全、UI 骨架和 mock 契约工作。
