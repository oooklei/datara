## 逐项依据

### RR1 — FAIL

目标提交 §3.1（第55–64行）已将 A1–A7 名称和总体映射改回标准 v4 原义，A5 也明确四项均属 DS 复刻范围、不得豁免。但逐项仍有以下问题：

- A1（第55行）：仅要求保留红灯证据，没有标准 v4 A1 所要求的时间戳实证，也没有把红灯证据关联到后续绿灯实现提交。
- A2（第56行）：写成“GREEN 终判=Codex PASS”，较标准 v4 第98行允许的“Codex 或用户授权线”收窄了评审者范围。
- A3（第57行）：写出 JSON+PNG 成对、remote-final，但没有给出可复核的摘要对象、配对标识及远端一致性验证字段/步骤。
- A7（第61–64行）：逐项列出 DDL、preview、token/key 红线，优于笼统豁免；但直接以“无凭证面”判 token/key N/A，未解释 backfill 输入范围中的 `worker/environment` 与凭证边界。该处证据不足，需明确字段仅为非敏感标识/引用，或说明脱敏、密钥引用及禁止回显约束。

标准锚：`docs/increments/2026-10-17-核心业务功能实现规范与验收标准.md` 第97–103行（A1–A7 原义）。

### RR2 — FAIL

目标提交 §3.1 场景表（第67–88行）已给出四能力测试向量、注入、断言、命令与证据路径的列结构，但内容尚不足以称为可直接执行的实现级验收：

1. 第71–88行多数运行命令使用 `pytest ...` 省略号；仅首行命令完整。按目标提交当时的仓库状态，测试入口亦未实现，故这些只能是待建测试提纲，不能判为可执行 PASS 谓词。
2. 第78行日期边界样例错误：闭区间 `2024-02-28` 至 `2024-03-01` 应为 `02-28/02-29/03-01`，提交写为 `02-28/03-01/03-02`，会固化错误预期。
3. failover 场景没有分别覆盖 PASS 主题中的 SUBMITTED、FAULT_TOLERANCE、RETRY 恢复；重试 attempt/超时/取消竞态、人工失败恢复、backfill 失败/停止及部分失败等未充分落到场景表。部分优先级阈值仍是“<阈值”而无具体数值。
4. 故障矩阵（第90行起）部分断言仍是“错误处理+重试”“幂等”等不可观测措辞；backfill Leader/Worker N/A 仅解释展开阶段或 scheduler 驱动，未覆盖整条批次执行/恢复范围；重复消息没有指定唯一键、持久副作用计数及最终状态。

因此 RR2 只能认定结构改善，不能判已完全闭环。后续改版需将未实现入口明确标作“待实现”，给出完整测试标识/启动与注入方式、精确日期向量、可度量阈值和有边界的 N/A 理由。

### RR3 — FAIL

目标提交第82行仅在“C4 批准持久 ComplementBatch”时验证 run→batch 映射；第24行仍将无批次对象列作现状缺口。它没有定义 C4 不批准持久实体时可接受的替代关联（稳定键、持久位置、查询面、重启恢复和验收谓词），所以不是对两种 C4 结果均闭环的条件验收。

后续监督线已裁定 C4 批准持久批次（handoff #220）。当前 main 清单第87–88行改为“批准分支验收 / 拒绝分支不执行”，已按实际裁定收敛，不再要求未选分支作为实施前置。

### RR4 — PASS

目标提交第25行准确表述项目 preference 影响手工启动的 `workflowInstancePriority`，不是节点 task priority 覆盖；同时区分 `SERIAL_PRIORITY` 实例冲突策略与队列权重。与 DS `start-modal.tsx:199-203` 及优先级实现锚一致。

### RR5 — PASS

目标提交第24行及补强项明确 DS 的串行下一日期由当前 workflow instance SUCCESS 触发，失败/停止不触发，并指出任务级 `CONTINUE` 不等于补数批次失败后继续。第80行只覆盖成功正向路径；建议另补失败/停止后“下一日期未启动”的负向断言，但不改变该项语义修订通过。
