## 1. 总体结论

v4 的主方向与方案裁定链基本一致，未发现删除或实质弱化用户原始五项核心业务要求的情况。建议在进入用户 K2 过目或形成生效版本前，修复下列交叉引用和边界表达，避免读者将不同裁定、不同批次及不同外部集成误读为同一事项。

原始五项核心要求在 v4 中仍有对应条款：

1. SQL IDE 参考 DBX 并融合原版 SQL IDE：S1。
2. 独立测试页遵从被测组件自身交互逻辑，并以真实表单、默认值、校验、交互顺序及结果反馈验收：S2。
3. DolphinScheduler 依赖组件能力：S4 与 R4 验收清单。
4. SQL IDE 能力及贯穿系统的变量规范：S1、S3、R5-A/R5-B；SQL IDE 后端变量处理仍被列为重点。
5. AI 助手集成能力与定位：S5、R8；状态注记没有从标准中删除原始要求的文字或其方法论定位。

因此，建议把 v4 中“原始业务要求”“当前路线图状态”和“阶段验收范围”明确分层表述；未被本轮设计裁定纳入当前路线图的能力，不应被误读成原始需求已经取消。

## 2. 逐项评审意见

### N2-1：S3 的 `V2/D3` 交叉引用存在歧义

- 分类：问题 / 疑问
- 优先级：P1（可能使变量契约与 DS `parameterPassing` 的裁定归属被错误追溯）
- 位置：标准 S3“与 DS `parameterPassing` 关系”及 v4 修订记录；设计稿 §5.1 D3 实际指 OM/DH 移出路线图，而不是变量透传裁定。
- 结论：**采纳修订建议**。
- 理由：当前将 `parameterPassing` 的独立建模和分别验收标为“V2/D3 修订”，但设计稿 D3 的定义是 OM/DH 路线图处置。此处编号不能唯一定位依据，读者可能据此把变量裁定误认为 OM/DH 裁定。
- 建议拟修条文：

  > 与 DS `parameterPassing` 的关系：变量解析与 VarPool OUT 运行时透传分别建模、分别验收；合并存储或快照属于实现集成选择，不得抹掉透传行为。此处依据为“参数透传反馈 V2（parameterPassing）”及设计稿 §5.1 对应裁定，不引用 D3（D3 专指 OM/DH 路线图处置）。`parameterPassing` 的最终取舍仍按 A5 议程裁定。

- 后续动作：核实“参数透传反馈 V2”的正式编号/原始反馈锚点后，将占位描述替换为可唯一检索的引用；若编号无法确认，保留语义并移除错误编号。

### N2-2：S5 的路线图状态注记与 R8 验收清单不一致

- 分类：问题
- 优先级：P1（会令当前 R8 验收承诺与路线图裁定冲突）
- 位置：S5 状态注记称 OM/DH 已移出路线图、语义源归 R3 自有治理域；§4/R8 的验收项仍要求“OpenMetadata/DataHub 语义源接入”。
- 结论：**采纳修订建议**。
- 理由：D3 明确原 Phase 3 OM/DH 试点删除、未来接入须新裁定；若验收清单仍以“接入 OM/DH”为当前必交项，会产生未获裁定的范围回流。保留它们作为原始能力方向或未来研究参考，不等于当前阶段必须集成。
- 建议拟修条文：

  > R8 当前验收：验证 Datara 自有治理域（R3）作为当前元数据/语义上下文来源；完成数仓语义层、自研 Agent 与 Vanna 工具调用思想的分阶段集成验证。OpenMetadata/DataHub 仅保留为原始需求背景及研究参考，不属于当前路线图交付项；接入须另行形成裁定并更新本标准。

- 后续动作：同步检查正文中所有 R8 四能力列表及验收清单，统一区分“原始目标/参考能力”和“当前已批准路线图交付”。不得仅修改 S5 注记而遗漏验收项。

### N2-3：S6 的通用主权原则需要组件级证据要求

- 分类：建议 / 补充需求
- 优先级：P1（属于安全与架构验收的证据完整性）
- 位置：S6 将主权边界扩展到 DS、DBX、Vanna、OM、DH 等外部组件；紧邻引用的 R8-V 四项证据只覆盖 Vanna PoC。
- 结论：**有条件采纳**。
- 理由：将 Datara 身份、项目、变量、数据源、权限、审计和 run_id 作为唯一真源的总原则正确；但仅引用 Vanna 的四项证明不能自动证明其他组件已满足同等要求。不能把单个 PoC 证据泛化成所有集成均验收通过。
- 建议拟修条文：

  > 每个外部组件/集成批次均须提供与其实际边界相匹配的主权证据：身份及项目范围绑定、变量/运行上下文映射、数据源凭证归属、权限判定、审计事件和外部 ID 映射。R8-V 的四项主权证据仅作为 Vanna PoC 的首个实例；DS、DBX 及其他外部集成应分别提交证据，不得以该实例替代各自验收。

- 条件：对不涉及某类数据或边界的组件，允许标记“不适用”，但需说明理由并提供可核验的替代证据；不能仅因引用 S6 总原则就默认通过。

### N2-4：R5-A 的阶段范围对手写 DDL 执行及 SQL 查询能力描述不完整

- 分类：疑问 / 问题
- 优先级：P1（影响当前批次范围、验收及与 R5-B 的边界）
- 位置：R5-A 声明只读态、DDL 执行属于 R5-B；但对象编辑项括号仍列“浏览 + DDL 提取 + 手写 SQL 执行”作为初步形态。标准没有明确该“执行”是否只表示后续写入闭环，也未列明只读 SELECT 执行、结果网格、历史、导出、取消等能力在 R5-A/R5-B 的归属。
- 结论：**部分采纳**。
- 理由：U1/U3 已明确写入闭环和对象编辑全链路归 R5-B；该阶段裁定应维持。需要补充消除“手写 SQL 执行”对 DDL/DML 写入执行的歧义，并明确只读查询是否属于当前 R5-A 验收，否则实现团队可能将其错误延后或将写入能力提前纳入。
- 建议拟修条文：

  > R5-A 的 SQL 执行范围须按语句/副作用分类：只读查询（例如经权限及只读策略确认的 SELECT）及其结果反馈能力，若纳入本批次，应在验收清单列明结果网格、执行状态、查询历史、导出和取消等适用项；会产生写入或 DDL 副作用的 SQL 执行，以及对象编辑落库、发布、审计、回滚，均归 R5-B。DBX DDL 精读是冻结只读契约和确认对象定义读取方式的前置，不代表 R5-A 执行 DDL。

- 待澄清后落条款：只读 SELECT 执行、结果网格、查询历史、数据导出及取消是否全部属于 R5-A，需与批次计划及 DBX 融合清单对齐；在澄清前不得据此宣称已完成验收。

### N2-5：S1 应明确 DS/DBX 的参考边界及 DBX 融合范围

- 分类：建议
- 优先级：P2（减少“复刻”被误读为运行时依赖或只做局部研读的风险）
- 位置：S1 融合规范及其 D9 关联说明。
- 结论：**有条件采纳**。
- 理由：现有 S1 已有“参考源码和文档、与原版融合、冲突优先 DBX”核心规则，且方案明确不引入 DS/DBX 运行时。因此无需新增例外或改变总体技术路线；建议在 S1 增加一条执行边界，强调全面研读覆盖 DBX 全部相关能力，而非仅 DDL，并明确参考业务语义不等于引入对方运行时。
- 建议拟修条文：

  > DS/DBX 的“复刻/参考”指基于其源码、文档及产品交互理解业务语义并在 Datara 后端实现适配，不代表引入其运行时或依赖其非稳定 Web API 作为公共集成契约。DBX 研读与融合覆盖相关数据源能力、查询编辑、结果、历史、资产、异步执行及导出等范围；与原版 SQL IDE 的冲突按用户规则以 DBX 为准，原版特色吸收项单独登记。

- 条件：条文应保持与 D4/D9 一致，避免把 DBX 非稳定 Web API 表述为可直接依赖的契约；覆盖范围可通过 D9 融合清单逐项追踪，不必在正文重复实现细节。

### A. 新条款与原始核心要求/D9 的一致性

新增条款规定：每个可引用变量的输入位须有校验按钮，走 `/check-reference` 并显式展示 SYNTAX、UNDEFINED、TYPE_MISMATCH、SCOPE_INVISIBLE、CYCLE 五类诊断；同时展示当前时点解析值，走 `/preview`/run-snapshot；交互随对应模块实现及前端重构阶段落地，最终逐输入位扫描验收。标准锚点为 `docs/increments/2026-10-17-核心业务功能实现规范与验收标准.md:137`，提交说明见 `3191c0b`。

该补充与五项原始要求整体一致，尤其将第四项“变量体系贯穿全系统、支撑设计/运行/维护时数据透传”具体化为输入位级交互验收；也与第二项要求的真实字段、校验、交互顺序及结果反馈一致。它没有改变第一项 DBX 优先的规则、第三项 DolphinScheduler 依赖完整性、第五项 AI 助手能力或其优先级。

D9 是 DBX 全面研读并融合原版 SQL IDE 的执行令，与此新增条款没有冲突：SQL IDE 中支持变量引用的实际输入位应纳入同一全域清单；这不改变 DBX 冲突优先规则，也不意味着以变量按钮/label 代替 DBX 全量研读和融合点、冲突、特色吸收项产出。S3 将交互安排在各模块前端实现/前端重构阶段，与标准 S3 的 SQL IDE 前后端分工及后端先冻结原则相容；不能据此声称目前所有模块的 FE 已完成。

### C. 需要在后续实施/验收中控制的边界与风险

1. **“当前值”与 run-snapshot 不是同义词。** `/preview` 根据当前变量定义与提供的上下文进行解析；`/run-snapshot` 是某次运行已持久化的 attempt 快照。建议后续 UI 验收将标签区分为“当前解析预览”和“运行快照”，不得在没有 instance/attempt 的编辑态用历史值冒充当前值；若验收要求强不可变性，还需验证写入路径/DB 约束不会改写既有 attempt 行。
2. **完整表达式的展开语义未完全由当前 preview 实现证明。** `VariableResolver.preview_resolution` 明确只解析表达式中的第一个引用（`service.py:304-322`）。当字段含多个变量引用或变量与普通文本组合时，当前 `resolved_value` 不等于整段表达式的完整展开结果。验收前应裁定 label 展示“每个引用的变量值”还是“整段文本完整展开值”，并使 FE 行为与 BE 契约一致。
3. **五诊断码的自动化覆盖不等于已有测试全覆盖。** `service.py:234-265` 实现五类诊断分支；当前 `datara-backend/tests/rebuild/test_r2_variables_api.py:122-157` 明确验证 UNDEFINED、SCOPE_INVISIBLE、SYNTAX、CYCLE，但该片段没有 TYPE_MISMATCH 的 `/check-reference` 断言（保存时类型不匹配与引用校验诊断不是同一断言）。新条款要求五类结果作为 UI 能力，建议验收补齐 TYPE_MISMATCH 的 API→FE 展示用例。
4. **敏感值 label 的显示边界必须继承已裁定口径。** v4 R2 清单 `:141` 要求业务敏感值忠实原值（仅本系统登录密码例外）；测试 `test_r2_variables_api.py:64-66` 也确认变量 API 返回敏感原值。故不能擅自掩码或替换；同时前端实现不得把现值写入 URL、常规日志、埋点或非必要持久缓存，并必须依赖项目授权。该条款增加可视性，不增加扩大访问授权的依据。
5. **run-snapshot 当前路由授权不足以支撑跨模块通用展示。** `variables/api.py:221-228` 对 `/run-snapshot` 仅做 token principal 检查，然后按传入 instance_id/attempt_no 读取；没有通过 project_permission_error/authorized_session 校验运行实例所属项目。快照记录模型只保存 instance_id/attempt_no（`variables/models.py` 的 `TaskInstanceVariableRuntimeRecord`），未见 project_id 绑定。快照值可含原始变量值，不能让任意有效用户通过猜测 instance_id 读取。若新条款允许在页面调用 run-snapshot，必须先补运行实例到项目的归属校验和跨项目拒绝测试；否则把 run-snapshot 限于已有可信调用边界，并将编辑态 label 指向受项目授权的 `/preview`。
6. **“任一可引用变量输入位”的验收需要清晰库存。** 该条款覆盖范围是全域文本输入位，不等同于 R2 变量验证单页完成。逐模块清单应记录输入位、变量语法是否适用、项目/工作流/任务/attempt context 的来源、校验按钮、即时预览、错误反馈和延期批次；不支持变量引用的字段应依据业务契约明确标为不适用。SQL IDE 相关输入位并入库存，但仍按 D9 的 DBX 语义和冲突规则单独验证。

### D. Addendum 结论

**对新增标准条文本身：有条件通过。** 方向与原始五项要求及 D9 一致，BE 的 `/check-reference`、`/preview`、`/run-snapshot` 契约在代码中存在，当前条款把未来 FE 验收义务明确化；但“当前解析值”不应把 preview 与运行快照混为一谈。若要将该条款宣称实现或验收通过，至少需澄清多引用表达式的展示语义、补齐 TYPE_MISMATCH 诊断测试，并修复/裁定 run-snapshot 的项目授权边界。上述风险是对后续实现验收的反馈，不是对用户已批准标准的改写或撤销。
