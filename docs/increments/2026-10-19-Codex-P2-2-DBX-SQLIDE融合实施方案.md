# P2-2：DBX 语义参照下的原版 SQLIDE 融合实施方案

- 日期：2026-10-19
- 性质：P2-2（R5-A SQL IDE 自研）实施方案输入；仅定义实施顺序、冲突处理和吸收项，不实施代码、不冻结 A5 契约。
- 来源：P1-7 研读 `2026-10-19-P1-7-DBX融合研读-Claude线.md`（提交 `7c61093`）；路线依据 `2026-10-17-分阶段混合集成方案-设计.md` §0 D9、§4 Phase 2、§7 P2-2；R5-IDE 分层依据 `2026-10-14-datara-platform-rebuild-design-执行附录.md` §7.2、§8.1–8.3。
- 目标：将 DBX 已研读的能力语义转化为 Datara R5-A 的可分期实施输入，并吸收原版 SQLIDE 的界面操作优势；避免把 DBX 变成 Datara 的运行时或权威源。

## 1. 范围和约束

### 本方案覆盖

P2-2 按批准任务池定义为 R5-A SQL IDE 自研：DBX 为语义参照，融合 P1-7 清单中的适用项，并遵守 U1 只读边界；实施先后和范围依赖 A5 冻结。R5-A 能力面为只读数据源/schema/table/column 浏览、跨 Schema 查询、补全、异步结果集、分页/取消/历史/导出（执行附录 §7.2）。

### 明确不包含

1. R5-B 写入闭环：表/视图/函数/存储过程等 DDL 编辑、差异/发布/回滚。须满足 R5-A PASS 后另行申请授权、人工确认并独立验收；R5-A PASS 不授权 R5-B（执行附录 §7.2）。
2. DBX Tauri 壳、DBX 存储/调度实现、DBX Web API 直连或把 DBX 设为身份、项目、变量、权限、审计、运行关联 ID 的真源（研读稿 §7；分阶段方案 §0 D4、D6）。
3. 正式前端整体重构。Phase 3 F2 仅允许差异盘点，不改页面（分阶段方案 §7「Phase 3」F2）。
4. 新增或变更 A5 契约、R5-A 17 方法、数据模型、SSE 事件/DTO、权限语义及既定门禁。方案中的未冻结项进入 A5 裁定，不以实施便利代替冻结。

### 权威和冲突原则

- 语义冲突按用户 D9：DBX 优先；原版 SQLIDE 的特色仅在条件允许时吸收（分阶段方案 §0 D9）。
- Datara Backend 契约仍是执行、安全、权限、审计权威（P1-7 研读稿 §7）。D9 不授权复制 DBX 实现、绕过 Datara 权限，或改变已冻结的 Datara 主权边界。
- R5-A 始终只读。查询与元数据访问必须沿 Datara 已授权路径；任何会改变数据库状态的行为一律不进入 R5-A。
- 对未决契约或实证不足的 DBX 行为标记“待 A5/实施前验证”，不猜测，不据静态源码宣称目标库运行成功。P1-7 §9 明确区分代码路径证据与目标库运行证据。

## 2. 推荐实施顺序与阶段门

| 阶段 | 实施内容（DBX 优先语义） | 依赖/出口 |
|---|---|---|
| 0. 基线与冻结准备 | 固定 Datara Backend/FE 基线；逐条映射 P1-7 F/C/A 到 R5-A、R5-B 或范围外；复核已批准 R5-A 契约和 A5 未决项；建立每项来源锚、Datara 对应点、决策、证据等级的追踪表。 | 不改契约。A5 未决项先裁定；工作树或基线不一致时停止该项并重新取证。 |
| 1. 主权适配边界 | 定义 Datara datasource/project/permission/execution/audit 上下文到 IDE 请求的适配责任；DBX 概念仅经 Datara 内部适配层表达，不暴露 DBX DTO、驱动、凭证或持久化结构。 | 权限先于连接；每个请求可关联 Datara 既有上下文和审计链。R5-A 无凭证展示或持久化。 |
| 2. 数据源、连接与对象发现 | 按 F1、F2、F10 建立连接类别/生命周期和跨 Schema 上下文的 Datara 实现方案；以 DBX PoolKind 分级、driver runtime、schema provider 路由作语义参照。建立九类 R5 对象树及驱动能力门控，对照 13 类 ObjectSourceKind 时仅把 R5-A 所需只读对象纳入。 | 只复用 Datara datasource 与权限体系。短连接只在测连场景保留；池化/驱动进程治理须符合 Datara 运行约束。缺少目标驱动证据的对象能力标 U/待验证。 |
| 3. 编辑器输入与语句执行单元 | 按 F5、F6、F7、C1、C2、C7 采用 DBX 的完整语句边界、语义补全、格式化与编辑器交互模型；选择区只提供执行目标收集范围，不能切出半条 SQL 作为执行单元。Monaco 若受冻结架构约束保留，仅逐项移植其语义，不以替换编辑器内核作为前置。 | SQL 执行模式/只读保证遵从 Datara Backend 契约与 A5 冻结；语法、补全对不同方言的降级行为须显式定义。 |
| 4. 执行生命周期与错误映射 | 按 F3、F8、C6 规划多语句执行、事务策略、continue-on-error 策略、取消/超时及类型化错误；DBX 的 await 请求-响应与 Datara taskId/SSE 若冲突，按 P1-7 已定口径：DBX 执行语义优先，SSE 作为 Datara 传输适配层，保留冻结的 task/result 引用关系。 | 前置是 A5 对 execution DTO、事件名/负载、取消完成语义和错误码的冻结。R5-A 只允许只读 SQL；错误需保留定位信息并映射到 Datara 错误模型。 |
| 5. 结果集、分页、历史与导出 | 按 F4、F12、F13 以 DBX 结果网格语义规划多结果集、分页/虚拟滚动、结果限制、历史和导出；融合 Datara 服务端重放分页及历史 SQL 可复查优势。 | 遵守既定结果集协议的 cursor/offset、TTL、截断、取消与导出约束；服务端重放仅是结果传输/回看实现，不成为查询执行语义真源。 |
| 6. R5-A 集成验收 | 逐项验证对象浏览、跨 Schema 查询、语句边界、只读执行、异步结果、分页/取消/历史/导出和权限/审计边界；测试项引用冻结契约与实际运行证据。 | R5-A 单独 PASS 才可宣告该门禁通过；任何 R5-B 写入能力另行隔离。验证应覆盖真实目标驱动/数据库；静态代码检查不能代替运行证据。 |

阶段 1–5 可在文件所有权允许的前提下并行细化，但实现依赖按表中门禁顺序收敛。R5-A 的契约冻结、Backend 与 FE 适配不得因并行而先于 A5 冻结。

## 3. 冲突处理表（P1-7 C1–C7）

| 冲突 | 执行决策 | 本方案边界/待裁事项 |
|---|---|---|
| C1 编辑器内核：DBX CodeMirror 6；原版 Monaco | DBX 编辑器语义与 composable 交互优先。遵守 Datara 已冻结前端架构；若内核替换未获冻结，保留现内核，仅移植可验证语义。 | 将内核替换列为独立架构决策，不把它默认为 P2-2 必需条件。 |
| C2 执行粒度：完整语句边界；原版选中优先/全文兜底 | DBX 完整语句语义优先。选区与边界冲突时不执行不完整片段；仅当 A5 明确批准后，才可定义安全的选区兼容规则。 | 对注释、字符串、存储程序块及多语句选择的边界样例纳入冻结契约/验收案例。 |
| C3 对象枚举：13 类源码对象；原版三层元数据树 | DBX 对象粒度优先；R5-A 当前九类 MetaTree 是已收敛子集。不得因 DBX 枚举自动扩容；扩展对象树需 A5 裁定且有驱动证据。 | Table/Index 不属于 DBX `ObjectSourceKind`，仍按 Datara 元数据结构处理。编辑动作属于 R5-B。 |
| C4 连接：DBX 分级池化/驱动进程；原版 pymysql 短连接 | DBX 连接分类和池化语义优先；Datara 按自身 datasource/driver 与生命周期落地。短连接只保留在测连。 | 禁止复制 DBX 连接实现、凭证/密钥存储或进程协议；范围内细节由 Datara Backend 契约确定。 |
| C5 凭证：DBX SecretCodec；原版明文 | 采用 DBX 所代表的“不得明文存储”安全方向，并由 Datara 已批准安全基线决定具体机制。 | 本方案不指定密钥来源、加密格式、迁移状态机，也不改 R5-A 数据模型；这些属于独立安全设计/后端裁定。 |
| C6 生命周期：DBX await；原版 taskId+SSE | 执行语义向 DBX 对齐；Datara taskId/SSE 保留为传输适配。 | 事件、终态、重连/取消完成语义必须以 A5 冻结结果为准，不能按 DBX UI/API 直接替换。 |
| C7 交互工程：DBX composable；原版轻封装 Monaco | DBX 的补全、悬停、拖拽、诊断、快捷键等逐项评估并优先实现适用语义。 | 不一次性复制全部编辑器能力；只纳入 R5-A 范围且有用户价值/契约支持的条目。 |

## 4. 原版 SQLIDE 吸收清单（A1–A8）

| 项 | 融合决定 | 所属阶段/条件 |
|---|---|---|
| A1 悬浮表/视图生成 SQL | 吸收为只读编辑器草稿快捷入口；生成文本不自动执行。 | 阶段 3；仅对象能力已授权且支持生成时显示。 |
| A2 结果 Tab 回显 SQL、单元格复制 | 吸收；结果与执行 SQL/语句索引建立稳定关联，复制不改变数据。 | 阶段 5；受结果协议和多结果集映射约束。 |
| A3 Ctrl+Enter / Ctrl+S / Ctrl+Shift+F | 吸收快捷键体验；运行仍受 DBX 语句边界/Datara 只读权限约束，保存只操作 Datara 允许的 SQL 资产。 | 阶段 3/5；Ctrl+S 的目标存储/权限需既有资产契约支持，否则只列待裁。 |
| A4 结果页间漂移提示 | 必须吸收；服务端重放分页时如不能保证快照一致性，应明确提示结果可能漂移。 | 阶段 5；提示基于实际分页一致性语义，不虚报快照保障。 |
| A5 服务端重放分页 | 必须吸收为 Datara 结果检索/审计友好方案；DBX 结果分页语义优先，重放不改变执行单元或执行权限。 | 阶段 5；需与冻结的 cursor/offset、结果 TTL、历史标识对齐。 |
| A6 `${var}` 分色和分类补全 | 吸收变量视觉/补全体验，变量求值、作用域和快照完全服从 Datara 变量权威。 | 阶段 3；不把变量值或解析权交给 DBX/编辑器。 |
| A7 失败即停、警告收集、取消标记 | 吸收失败呈现、警告收集与取消反馈；执行控制策略按 DBX 语义及 Datara 冻结契约实现。 | 阶段 4；禁止把旧 `api/ide.py` 执行循环直接当新 Backend 契约。 |
| A8 独立数据源中心页面 | 保留 Datara 既有独立数据源中心与 IDE 解耦的信息架构，不在 IDE 内复制一套数据源真源。 | 阶段 1；只做入口/上下文集成，不扩展正式前端改造范围。 |

## 6. 实施前检查与停止条件

实施分解前应确认：

1. A5 已冻结本阶段使用的 R5-A 方法/DTO、执行事件、结果分页、取消、历史和导出边界；未冻结部分先走裁定。
2. 任务文件所有权、基线、依赖版本和 Datara Backend 权限/审计接线已核对；不得借 DBX 参照导入运行时依赖或 DBX 外部 API。
3. F/C/A 追踪表中的每个“必须/吸收”项均有验收场景和证据定位；不支持驱动或只有静态证据的能力保持待证状态。
4. R5-A 的测试/验收只运行只读 SQL 与只读元数据路径；涉及写 SQL、DDL、数据修改、凭证明文或超出授权 schema 时停止并转入正确门禁。
5. R5-A 最终 GREEN 依据独立证据与既有门禁，不以 UI 完成、源码存在、DBX 有对应能力或历史 `/ide` 证据替代。
