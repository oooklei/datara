## 二、单线多增量运行模型（用户裁定 2026-10-20）

- **不分组**：所有实施团队（Trae 线 1+5、Claude 线 1+3、Codex 线 1+3）围绕**同一条增量序列**推进；同一时刻仅一个「当前增量」处于实施态，前一增量未过退出标准不进入下一增量实施（外部阻塞导致的等待除外，见 §五）。
- **增量内并行**：增量内任务包按「责任线建议」分派；文件域不重叠的任务包可并行，重叠的串行。
- **责任线建议性质**：仅为本计划起草时的分工建议，监督线派单时可按实际负载调整；**验收终判**（独立评审）按 v4 A2 归 Codex 线或用户授权线。
- **增量 0 先行**：增量 0 = 后端全部准备工作对齐 + 前端全部准备工作对齐；增量 0 未收口前不启动增量 1 实施。
- **每增量交付节奏**：任务包完成 → 增量验收门核验 → 退出标准逐条核验 → STATE.md 回写 → 进入下一增量。
- **复杂工作包 to-tickets**：标注 ⛏ 的任务包在进入实施前由监督线用 to-tickets 技能分解为可派发票（见 §六 汇总），本计划不预先拆票。
- **阻塞传导（用户裁定 2026-10-20）**：外部阻塞项（T55 卡增量 9 / R3 契约收口卡增量 12 / FV-02 卡增量 15）挂起期间，允许跳至后续**不依赖该阻塞项**的增量先行开发，回归后补融合宣告；单线不空转。跳增量动作由监督线裁定并在 STATE.md 登记。

## 七、计划维护纪律

1. **STATE.md 回写方式**：每增量过退出标准后，监督线在 `docs/handoff/STATE.md` 活动区追加一条（S# 递增，append-only），格式对齐现有条目（线别 / 时间 / 单号 / 状态 / 交付 / 证据 / 阻塞 / 下一单）；增量序列整体进度以「当前增量=N」形式登记于快照节。全量 pytest 865P/1s/0F 与 vitest ≥905P 基线随各增量递增刷新并登记。
2. **增量范围变更**：增量范围 / 顺序 / 任务包增删属**计划修订**，须用户裁定后由监督线修订本计划（版本号递进 + 修订记录登记）；实施线不得自行扩缩范围，实施中发现范围问题报监督线。
3. **本计划自身修订**：文末修订记录表**只增不改**；每次修订登记版本 / 日期 / 缘由 / 批准者；重大改版（推翻既有裁定级）须经用户授权后重写。
4. **与权威设计联动**：权威设计 v3 修订时，本计划受影响增量须同步评估影响面并在修订记录登记；本计划与权威设计冲突时以权威设计为准。
5. **证据分离**：各增量的实施级文档（evidence 证据 / 验收单）落 `docs/increments/evidence/`，与本计划分离；本计划只维护任务真源，不堆积证据。
6. **归档纪律**：已归档文档（`docs/increments/archive/**`、`docs/archive/**`）只作考古身份，不得作为本计划实施依据。
