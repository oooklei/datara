## 1. 背景与用户裁定（2026-09-28）

**现状实测**：目录实测 **75 组件**（catalogHash=83929cf7c3c5c660，含 30 个 demo-only 无执行实现）；dag profile **35 个 DAG type**（`src/graph/profiles/dag.ts`，含 33 paletteVisible + 2 runtimeOnly 物化节点）——**本文循环单位 = 35 type**（一个 type 即一个基线化单元；demo-only 组件在其 type 基线化时随声明一并裁决去留）；治理三表 `t_component/t_component_version/t_component_log` 已建但为空；D1 发布闸门八项、D2 componentRef 回填（R6 + 物化器）、D3 offline/rollback 已落地（pytest **261** / vitest **351**）。M-B0 基建已交付（`t_baseline_progress` + 工作台三区 + 八段编辑器 + 认可发版 + 底稿导出 + 清库脚本 + 血缘预留）。治理库无任何版本，组件以代码声明 + dag_catalog.json 存在——**没有任何组件完成基线化**。

用户裁定（原始口径，本文唯一需求来源）：

1. **全部未基线化**：所有组件及版本均未基线化，需重新设计形成版本，成为可实测已验证组件；所有组件可删除和重建（含修改表单界面）；**用户认可发布版本后才可作为治理基础**。
2. **工作流与实例全可删**：所有工作流及实例均可删除，按新发版组件校验重构；发版前无冻结与限制一说。
3. **存量处置**：前端大改声明层为主，后端 executor 允许微调适配（不承诺零改，但已验证逻辑为主要资产）。
4. **发版载体**：新建「基线化工作台」，用户认可即发版；D1 八项闸门降为**体检清单**（逐项报告、不拦截），问题留用户裁决。
5. **清理方式**：一次性清库（工作流定义 + 运行实例）+ 可选 JSON 归档。
6. **验收口径**：**每组件单独过 1.9 真实数据流**（本地 pytest/vitest 全绿 + 设计器实测 + 1.9 部署实测）→ 用户在工作台点认可。
7. **范围锁定**：本轮仅做 **builtin 预制组件**（发版后 `t_component.scope=builtin`）；用户组件（design_component 流程）后期另行立项。
8. **表单八项**：组件表单按八段结构设计（见 §3），提供低代码式设计界面。
9. **血缘预留**：预判涉及数据流与血缘分析的组件须预留前后端血缘接口与交互（见 §5.4）。

## 2. 生命周期三态（核心语义）

| 态 | 载体 | 行为语义 |
|---|---|---|
| **未基线化 unbaseline** | 代码声明（现状 37 type） | 自由删改、可删除重建、无闸门；目录页标「未基线」徽标 |
| **基线化中 baselining** | 工作台底稿 + `t_baseline_progress` | 持有声明底稿/新旧 diff/体检报告/实测记录；设计器可改 |
| **已基线化 baselined（v1 published）** | `t_component` + `t_component_version`(v1) | 用户在工作台点「认可」写入 → **D1-D3 治理语义自此全套生效**：发布闸门恢复硬拦截、componentRef 冻结恢复（原红线 3 依据）、已发版不可直接编辑 |

「用户认可」是治理基础的唯一来源；认可动作 = 工作台「认可发 v1」按钮（§5.2）。

## 3. 表单八项 DSL 规范

表单声明固定八段骨架 + 字段属性，为**纯数据声明**（存 spec JSON，随版本冻结）：

| # | 段 | 内容 | 能力 |
|---|---|---|---|
| 1 | 输入 inputs | 上游数据接入（数据集/字段选择） | 必选/可选、可见性 |
| 2 | 输出 outputs | 产出声明（目标表/文件/流） | 必选/可选、可见性 |
| 3 | 参数 params | 运行参数 | 必选/可选、默认值、提示 |
| 4 | 条件 conditions | 跨字段/跨参数条件显示 | showIf 纯数据表达式（可见↔不可见） |
| 5 | 限定约束 constraints | 取值范围/格式/枚举/跨字段校验 | min/max/regex/enum/联合校验 |
| 6 | 排除 exclusions | 互斥与排除项 | 某字段取值后排除另一字段选项 |
| 7 | 引用变量 refs | 字段值可引用的变量 | 字段级 `allowVarRef` + 变量域白名单 |
| 8 | 输出变量 exports | 组件执行后对外产出的变量 | `[{key, from, type, desc}]` |

字段属性（通用）：`required`（必选/可选）、`visible`（可见/不可见，含条件可见）、`default`、`hint`。

**变量规格呼应（既有裁定，不改口）**：
- 解析链：节点参数 > 工作流变量 > 环境组 > 全局（DAG组件化编排规范 §变量解析）
- 引用变量段：组件表单**仅可引用不管理**——变量引用选择器下拉列当前工作流变量 + 环境变量 + 全局参数，选中插入 `${var}`；变量域白名单 = 工作流变量/全局参数/环境组/内置时间变量/上游节点输出
- 输出变量段：`from: result | log | output`——result 取 executor 返回值、log 抓任务日志键（F48 变量打印追溯）、output 取输出 schema；下游经 `${节点.变量}` 或工作流变量中转引用（I12-G3 先例）

**关键协同**：现有 `FieldSchema.showIf / onChange / text` 三个不可序列化函数字段（红线 2 存量问题）随逐组件重设计**逐组件消灭**——八段式声明天然纯数据，M3 迁库的序列化前提由基线化自动完成。

**低代码设计界面**（设计器表单区升级，通用基建一次建成）：
- 八段分组结构化编辑器（tab/分组切换）+ 字段属性面板（必选↔可选、可见↔不可见、条件、约束、排除、变量域——全部可视化点选，不手写 DSL）
- 实时预览：右侧即节点配置抽屉最终渲染，所见即所得
- 逐组件循环只填声明，不重复造编辑器

## 4. 前端入口与基线化工作台

### 4.1 前端入口路径

| 入口 | 路由 | 组件 | 用途 |
|---|---|---|---|
| 画布/palette | `/dag` | TaskCenterView → GraphWorkbench | 拖拽组件到画布编排工作流（M-B2 组件在 palette「数据计算」分组） |
| 基线化工作台 | `/meta/baseline` | BaselineWorkbenchView | 底稿编辑/八项体检/1.9 实测记录/认可发 v1 |
| 组件设计器 | `/meta/components/design/:type?` | ComponentDesignView | 单组件八段 DSL 声明编辑（草稿编辑/实时预览/冻结） |
| 组件目录 | `/meta/components` | ComponentCatalogView | 组件只读清单（已发 v1 进「治理库」区） |

**Palette 分组**（dag profile）：
- 「数据计算」：sql, shell, python, ssh, procedure, http, file, assert
- 「通用」：notify
- 「逻辑控制」：start, end, conditions, switch, fork, join, merge, delay, dependent, loop
- 「数据同步」：src_base_orch, tgt_base_orch, file_sync_orch, endpoint_select, field_map, field_map_union, condition_set
- 「流处理」：stream_input, stream_fuse, stream_output, page_board
- 「变量」：variable
- 「运维/自检」：smoke
- 「模板」：demo_pipeline

### 4.2 基线化工作台（三区布局）

路由 `/meta/baseline`，三区布局：

1. **清单看板**：37 type 按优先级分组（同步类 9 → ETL 类 → 流处理类 → 逻辑控制类），状态徽标（未开始/设计中/待实测/待认可/已发 v1），进度与 `t_baseline_progress` 联动。
2. **设计区**：复用现有设计器（ComponentDesignView）声明编辑 + 八段表单编辑器（§3）+ 与旧代码声明自动 diff。
3. **证据区**：八项闸门体检报告（即 D1 发布闸门八项，出处见组件管理与发布治理设计 §发布闸门；逐项 ✓/✕ + 说明，**只报告不拦截**）+ 血缘/变量声明检查 + 1.9 实测记录（批次/数据流/结果备注）+「申请认可」→ 用户点「认可发 v1」。

**联动**：
- 目录页：已发 v1 进「治理库」区；未基线化组件标草稿灰
- 画布校验：未发版组件走 R6 宽松口径，已发版走严格口径（复用 D2 双模式，无新机制）

## 5. 后端设计

### 5.1 进度表 `t_baseline_progress`

字段：`type`（组件类型，唯一）、`status`（pending/designing/testing/confirming/published）、`check_report`（JSON：八项体检逐项结果 + 血缘/变量检查）、`test_records`（JSON 数组：1.9 实测批次/数据流/结论备注）、`confirmed_by`、`confirmed_at`、`create_time/update_time`。v1 发出前 `t_component` 无行，进度独立成表。

### 5.2 认可发版端点

`POST /components/{type}/baseline/publish`（admin）：跑八项体检逐项落 `check_report`（不拦截）→ 写 `t_component`(scope=builtin) + `t_component_version`(v1, published, spec=声明 JSON) + `t_component_log` 审计。复用 D1-D3 全部表结构与既有 publish 语义，不另起炉灶。

### 5.3 底稿导出（一次性）

管理脚本：`dag.ts` 37 type 声明 → 工作台初始底稿（+ `t_baseline_progress` 初始化 37 行 status=pending）。设计改造从此在声明层进行，代码 nodeTypes 退化为默认底稿来源。

### 5.4 血缘与变量预留（前后端接口位）

- **声明层**：spec 增 `lineage: {assets: [{role: 'source'|'target', pick: <字段key>, assetType: 'table'|'file'|'stream'}]}`——执行类组件（sync/ETL/流）基线化时**必填**，逻辑控制类豁免；随 D2 spec_hash 冻结
- **接口**：`GET /components/{type}/lineage-decl`（读已发版组件血缘声明）；`GET /lineage/graph` stub（声明级血缘图：由已发版组件声明组装的静态读写关系；运行时字段级血缘留 I5 既有 `t_lineage_edge/t_lineage_field` 表位，本轮不实现）
- **交互**：组件详情/节点运行详情预留「血缘」入口（未发版空态「待基线化」）；体检清单加「血缘声明完整性」「输出变量声明与 executor 实际产出一致性」项（提示不拦截）
- **运行时契约**：exports 声明由 F48 变量解析链消费，executor 按声明产出；语义分析步逐组件判定实际产出变量

## 6. 清库与归档（一次性）

`scripts/archive_and_purge.py`：
1. 导出 `t_wf_definition`（graph_json）+ `t_wf_instance`/`t_task_instance`/任务日志等实例表 → 本地 JSON 归档目录（可复盘不可回库）
2. 打印统计（各表行数）→ 用户确认 → 清空相关表
3. CLI 触发；归档目录不入库不进 git

## 8. 逐组件五步循环（验收纪律）

1. **语义分析**（每组件第一步）：读后端 executor 实现语义 + 现有声明 → 设计册产出八项表单规格草案（输入/输出/参数各哪些字段、必选可选、可见性、条件/约束/排除、引用变量域、输出变量、血缘声明）
2. **用户确认规格草案**（不确认不动手实现）
3. **实现**：前端表单声明（八段编辑器已就绪，只填声明）+ 必要的后端微调
4. **验证**：本地 pytest/vitest 全绿 → **单独过 1.9 真实数据流**
5. **认可发 v1** → 设计册归档、进度表置 published

纪律：1.9 不可达时该组件挂「待实测」，不阻塞下一组件的**设计**；发版必须等实测通过 + 用户认可。
