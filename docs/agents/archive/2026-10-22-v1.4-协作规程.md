## 一、组织架构（用户裁定 2026-10-20）

| 角色 | 编制 | 职责 |
|---|---|---|
| A 主监管 | 1 主会话，可有只读子智能体 | 面向用户、目标锚定、系统健康、异常与管理优化；不做例行派单/验收/裁定/编码 |
| B 裁定席 | 1 主会话，可冷备 | D0-D2 裁定；D3 仅可逆、限域、带回滚和 TTL；D4 生成用户决策卡 |
| C 流程控制席 | 1 主会话 + 冷备 | STATE/mailbox、队列、状态迁移、writer epoch、Git commit/push 唯一 Owner |
| V2 验收席 | 1 或多席分片，单 business_key 单 Owner | 独立验收；R0/R1 终判，R2 建议，R3 转裁定 |
| P2 派单席 | 1 或多席分片，单 WBS 分区单 Owner | 预研、拆票、依赖 DAG、路径冲突和 READY 库存 |
| I1 集成席 | 1 主会话，可按环境槽扩展执行器 | 192.168.1.9 环境、租约、共享代码、集成与联调；不 push |
| Trae 实施线 | 1 主智能体 + 5 子智能体 | 后端收口与部署域实施 |
| Claude 实施线 | 1 主智能体 + 3 子智能体 | 前端承接与生产实施域 |
| Codex 实施线 | 1 主智能体 + 3 子智能体 | 设计深化、独立评审（v4 A2 终判）与实施 |

- **实施线启动**：全由用户通过提示词命令进行，**禁止任何 CLI 命令拉起**（本条取代归档规范的 CLI 启动登记制与命令模板）。
- **子智能体边界**：子智能体只获得本票 Context Pack，结果由所属主会话聚合；不得直接写共享状态、对用户作终局承诺或跨席派单。
- **通信边界**：各实施线主智能体是唯一外部通信出口；实施线通过 outbox 投递，不写 STATE/mailbox。
- **文件域**：任务单必须声明 allowed_paths/forbidden_paths，并发 ACTIVE 票文件域零重叠；共享代码仅 I1 在集成窗口写，STATE/mailbox 仅 C 写。
- **AOCI 边界**：开发期所有角色停用 AOCI，禁止 MCP/CLI/索引维护及资产改写；发版代码冻结后由隔离维护会话一次性对齐。

### 1.1 A/B/C 分席与接管机制（2026-10-22 v1.4 覆盖）

- **专席不互相代做**：A 面向用户，B 裁定，C 控制；V2/P2/I1分别拥有验收、派单、集成阶段终局输出。
- **单写锁**：STATE.md、mailbox.jsonl、writer epoch 与 Git commit/push 任一时刻仅 C 可写；I1 只形成集成包和 pathspec manifest。
- **接管三步**：原 C 写 HOLD_POINT（在飞、阻塞、水位、epoch）→ 备 C 追加接管确认 → 发布新 writer epoch 后获得写权；未完成三步只读。
- **用户指令路由**：用户日常指令进入 A；A 转为目标/政策或 D4 决策，C 只接收结构化执行结果。
- **多席扩展**：V2/P2 可按不重叠 business_key/WBS 分区并行；同一阶段同一 business_key 只能有一个 Owner 和一个终局结果。

### 1.2 信箱单写者汇总机制（用户裁定 2026-10-21，v1.3）

- **背景**：多窗多线无锁直写 mailbox.jsonl 已两度致行截断/多尾字符/行序与 ts 矛盾（s223-l8-01-archived 截断、s224-ack-remind 多尾引号），用户裁定改单写者汇总。
- **范围**：`mailbox.jsonl` 与 STATE.md 均由 C 单写；历史只增不改，纠偏使用 supersedes。
- **单写者**：C 任一时刻唯一持有 mailbox.jsonl/STATE.md 写权；其他角色一律**只投递不直写**。
- **投递**：写入需求落 `docs/handoff/outbox/<投递方>/`（trae / claude / codex / gov-wait 待命监督角；一信一文件，文件名 = 信id.json，UTF-8 无 BOM，格式同现行信件八字段 id/ts/from/to/type/ref/body/status）；目录不存在时自建。投递后在本线 STATE 心跳注明待收口，提醒值班角。
- **收口（值班角串行原子）**：按 ts 排序逐件 ConvertFrom-Json 预验证（坏件移 `outbox/reject/` 并在收口回执披露，不投递）→ append mailbox.jsonl（UTF-8 无 BOM）→ 全文件逐行复验 → 已投件移 `outbox/sent/` 留对账 → 按需发收口回执信。
- **接管兜底**：C 失联且 outbox 积压超 30 分钟时，由备 C 依 §1.1 三步接管；其他角色无接管权。新 C 首次收口前验证全文件、mailbox 水位和 writer epoch。

## 二、运行节奏

运行模型全文见 WBS §二「单线多增量运行模型」，本规程只作执行性重申：

1. **单线推进**：三支实施线围绕同一条增量序列；同一时刻仅一个「当前增量」处于实施态，前一增量未过退出标准不进入下一增量实施。
2. **增量内并行**：文件域不重叠的任务包可并行，重叠的串行；WBS 的「责任线建议」仅为分工建议，监督线派单时可按实际负载调整。
3. **阻塞传导**：外部阻塞项（FV-02 / T55 / R3 等，见 WBS §5.1）挂起期间，经监督线裁定并在 STATE.md 登记后，允许跳至后续不依赖该阻塞项的增量先行开发，回归后补融合宣告；单线不空转。
4. **任务库存**：P2 将复杂包拆成可执行票，并维持 READY 覆盖约实施能力 1.5 倍；派票前必须完成依赖 DAG 与 allowed_paths 冲突检查。
5. **每增量交付节奏**：任务包完成 → 增量验收门核验 → 退出标准逐条核验 → STATE.md 回写 → 进入下一增量。
6. **用户裁决门**：WBS §5.2 的 ⭕ 待裁项，裁决前不开发对应页面/建模。
7. **阶段收尾=受控提交**：I1 形成集成包，C 在 V2/I1 结果、pathspec manifest、HEAD/preimage、diff 审查和无凭据检查齐全后 commit/push；AOCI 开发期不进入提交链，发版冻结后单独维护。

## 三、分派 / 回报 / 验证闭环

### 3.1 派单（监督线）

- **唯一载体**：P2 生成 dispatch manifest、C 落账后才是正式派单；会话口头派单、历史任务推断和设计标签均无效。
- **任务单内含**：task_id/business_key/revision、目标、最多三个权威锚、allowed/forbidden paths、依赖、DoD、证据、停止规则、下一事件和租约。
- **编号规则**：沿用现行惯例——T 系列（Trae 线）、C 系列（Claude 线），其余线/专项前缀在派单时声明；修订/收口核查单加 r 后缀（如 T56r、C21r）。心跳与 S# 编号互不混用。
- **防重复派单**：派单前对照 STATE.md 活动区与 WBS 已交状态（S156 重复派单教训）。

### 3.2 回报（实施线）

- **领单回执**：「任务号 + 认领 + 产出承诺」（#45 延续）。
- **交付回报**：结果 + **证据成对**——代码交付附测试命令与输出定位；文档/对照表交付附核对表与出处；「报告 PASS」不算独立复现（#265 延续）。页面/链路类交付按 v4 A3 走真实控件证据。
- **自解释条款**：交付回报必须以「下一单：已派/待派 + 触发条件」收尾（#286 延续）。
- **登记**：实施线一信一文件投递 outbox；C 原子校验后落 STATE/mailbox。实施线不 commit/push，C 通过提交门后代办提交。

### 3.3 验证（V2）

- **独立核查**：V2 对照 v4 门禁逐项核验；所有可执行验证在 192.168.1.9 执行，实施者不得验收自身交付。
- **验收终判**：R0/R1 由 V2 签 PASS/REWORK；R2 输出建议交 B；R3 进入 B 裁定。无独立结论不标 GREEN。
- **结论回写**：V2 投递结构化结论，C 推进状态；FAIL/证据不匹配退回实施线并写明最小差异。
- **委托留痕**：用户专属闸受委托执行时，证据须标注「经用户委托」并可回溯。

## 四、心跳纪律（STATE.md）

- `docs/handoff/STATE.md` 为冷启动首读与唯一现行台账：**append-only**，仅在文件尾部追加；改写、重排、删除历史心跳原文即违规。过期描述以显式状态注记覆盖，历史原文不删不改。
- **结构**：快照区（每监督窗刷新）+ 活动区（S# 序号，只追加）；历史活动原文归档至 `docs/handoff/archive/`，归档卷只读。
- **每监督窗**由监督线追加一条 S# 心跳，格式对齐现有条目：`S# | 线别 | 时间 Asia/Shanghai | 单号/主题 | 状态`，正文含交付 / 证据 / 阻塞 / 下一单。
- **编号实锚**：S# 全局递增，取 git log 与台账正文最大号 +1；撞号时先落库者保留、后落库方改号并披露。
- **≤60 行硬上限**：超出即把最旧活动条目整体归档至 `docs/handoff/archive/`（文件名含序号区间），快照区同步刷新。
- **单写者**：STATE.md 仅 C 追加；其他角色通过 outbox 投递结构化事件。

## 五、质量红线（8 条）

1. **诚实汇报**：禁假成功、假证据；PARTIAL / 未闭环 / 阻塞如实标注，接受中间态为终态（弱 PASS）即违规；没有核实过台账/git 实锚的结论不许报，无法核实即标「未核实」。
2. **证据成对**：一切交付/复核/验收必须附测试命令与输出定位 + 证据文件（落 `docs/increments/evidence/<域>/`）；失败证据保留并登记失败 run 编号，静默重跑覆盖失败证据即违规。
3. **契约纪律**：契约/集成测试先 RED 后 GREEN（TDD）；契约改动走宣言→再冻结流程（新版本号 + 心跳通报 + 会签），不静默改词；前置未冻结维持 RED 不抢跑。
4. **基线不退化**：全量 pytest tests/rebuild（当前 865P/1s/0F）与 vitest 契约基线只增不退，随增量刷新并登记；数字允许演进，禁止多版本漂移不收敛。
5. **归档件只读**：`docs/increments/archive/**`、`docs/handoff/archive/**` 及旧台账只作考古身份，不得作为现行实施依据，不得写入。
6. **AOCI 全停**：开发期所有角色禁止调用、维护或改写 AOCI；发版冻结后仅隔离维护会话可一次性对齐。
7. **用户专属闸**：确认短语、验收授权、破坏性操作一律由用户下发；agent 不得代写或绕过；委托执行须留痕（见 §3.3）。
8. **凭据安全**：token/key 明文零入库、零心跳、零证据文件；凭据只经环境注入或单向 stdin 传递；泄露一律立即轮换 + 留痕。

## 七、修订规则

1. **修订须用户裁定**：未经用户批准不得修订本规程；每次修订递增版本号并在文末修订记录表登记（只增不改）。
2. **新裁定回写**：用户在运行中作出的新裁定，经监督线落 STATE.md 后按需并入本规程对应节；裁定原文以 STATE.md 为准。
3. **冲突效力序**：用户裁定 > 权威设计（`docs/increments/2026-10-19-纠偏重构前端权威设计.md` v3）> 验收规范 v4 > WBS 计划 > 本规程；低位于高位冲突时以高位为准，并按第 1 条修订本规程。
4. **负面清单**：不重排历史编号；不引入第二套门禁；不复制辅助设施内容进本规程。
