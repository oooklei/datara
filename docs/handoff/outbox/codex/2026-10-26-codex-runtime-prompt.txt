================================================================
 Codex 运行规范（提示词）—— Token 纪律 v1.0  2026-10-26
 用法：每个会话开始时整段粘贴本文件内容，或并入 AGENTS.md。
 背景：2026-10-26 实测 32 会话 1250 轮 API 调用、92.4M input
 tokens（97% 缓存读），单会话最高 7.77M、单轮上下文膨胀至
 184K、5 小时配额被打穿到 99%。根因=长会话重灌上下文+反复
 全量跑测试。以下规则为硬约束，违反即返工。
================================================================

【一、会话纪律（最高优先级）】
1. 一票一会话：一个 handoff 票 = 一个会话；票完成立即收尾，
   跨票状态只通过字条/回执传递，禁止依赖会话记忆续作。
2. 轮次红线：单会话 API 轮次 > 30 时，无论任务是否完成，
   先把当前状态写入字条（已完成/剩余步骤/复现命令），然后
   提示用户重启会话再继续。
3. 配额自保：观察到 used_percent >= 80%（token_count 事件的
   rate_limits.primary）即触发第 2 条的收尾流程，禁止顶满。
4. 禁止为同一逻辑步骤并开多个会话/rollout（三胞胎模式）。

【二、测试执行纪律】
1. 迭代期只跑目标文件：
   npx vitest run <目标测试文件路径>
   禁止在修改-验证循环中反复跑全量套件。
2. 全量验证每票只做一次（票尾）：
   npx vitest run --reporter=dot
   基线：96 文件 / 816 用例全绿，任何回退立即停下报告。
3. 输出截尾：命令输出一律接管道截尾，例如
   ... | Select-Object -Last 20
   失败时只对失败的测试文件重跑获取详情，禁止把整段失败
   日志原样留在上下文里（单段大输出可达数万 tokens）。
4. vue-tsc 同理：
   npx vue-tsc -b 2>&1 | Select-Object -Last 10
   以 EXIT 码为准，EXIT=0 即通过，不逐条读警告。

【三、文件操作纪律】
1. 读文件先 Grep 定位行号，再按 offset/limit 局部读取；
   禁止无目的整读 300 行以上的文件。
2. 编辑用最小锚点替换（SearchReplace），同一文件多轮修改
   用累积编辑，禁止每轮重读全文再整写。
3. 大文件（如 WorkflowGraphWorkbench.vue 约 800 行）读一次
   结构、之后只对目标片段操作。

【四、提交与证据纪律】
1. 按文件名精确 git add，严禁 git add -A / git add .。
2. 提交格式：feat(newweb): [F-xx] 摘要；.git 提交由用户侧
   把关，Codex 遵守只读边界。
3. 每票完成：写八字段回执 JSON（id/ts/from/to/type/ref/
   body/status）至 docs/handoff/outbox/codex/；证据续写
   .codex-evidence/FE-MERGE-*/（日志只存截尾后的关键行）。

【五、红线（不因任何进度压力放宽）】
1. 三层 stash（stash@{0}/@{1}/@{2}）在 IdeView/LoginView
   并集验证通过前一律不 pop / 不 drop；从 stash 取内容只许
   git show 'stash@{n}:<path>' 只读提取。
2. 基线不回退：vitest 816 绿、vue-tsc EXIT=0。
3. 用户已批裁定不重议：streamApi I8 九键、resources 默认
   sql、归一目录（llm-models/sec/open）、收编三冲突裁定
   （main.ts 任取 / SshNode 取 c63c / LLM 表单取 c63c）。

【六、会话启动自检（开始干活前先逐条确认并简短回显）】
 1) 本会话对应哪一票（票号 + 目标文件）？
 2) 我的迭代测试命令是什么（精确到文件）？
 3) 当前轮次计数 = 0，超过 30 轮我将主动收尾。
 4) 我需要的上下文是否已从字条/回执拿全（缺就先要，
    不自己全量扫描补齐）？
 5) 收尾时我要交什么（回执 JSON + 截尾验证记录）？

================================================================
 执行顺序冲突时按编号小的优先；本规范与 handoff 交接单冲突
 时以交接单为准并当场向用户报告冲突点。
