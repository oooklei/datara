# Codex 实施线持续交付工作流

## 目标

持续消费 Datara 监督线分配给 Codex 的可开工库存，完成实现、测试、证据和回执，直到监督线权威库存确认为空且目标设计全部有验证闭环。

## 触发

- 事件触发：`docs/handoff/mailbox.jsonl` 出现发给 `Codex` 或 `all` 的新派单、解锁、验收或裁定。
- 恢复触发：已完成任务的前置条件被后续消息解除。
- 每轮冷启动先读 `docs/handoff/STATE.md`，再读取 mailbox 尾部和 Codex outbox/sent 状态。

## 权威来源与优先级

1. 最新用户裁定与监督线 mailbox 派单正文。
2. `docs/handoff/STATE.md` 当前基线。
3. 任务引用的 WBS、权威设计、拆票登记与证据底稿。
4. 主工作区 `D:\需求\数据治理工具\Datara` 当前文件和实跑结果。

发生撞号时遵守 R-43：按行序和明确勘误确定有效编号，不删除或改写历史记录。

## 每票执行

1. 从任务 body 提取范围、前置、验收锚、禁区和交付件。
2. 检查共享工作区所有权与并行改动；不覆盖其他执行线在飞文件。可独立任务可交给子智能体并行。
3. 在主工作区实施。所有 shell 命令使用 `rtk` 前缀。
4. 仅运行任务要求或验收锚授权的定向、相邻或全量测试，记录终态输出；失败时诊断并修复，命令路径错误单独披露。
5. 生成 evidence，列明源码锚、行为对照、测试输出、文件清单、SHA256、限制和剩余硬前置。
6. 向 `docs/handoff/outbox/codex/<id>.json` 写恰好八字段回执：`id,ts,from,to,type,ref,body,status`，UTF-8 无 BOM。
7. 不写监督线专属 `STATE.md` 或 `mailbox.jsonl`；等待监督线验收时继续处理其他已解锁票。

## 固定边界

- `.git` 只读，不 commit，不 push。
- Codex 实施线禁用全部 `aoci_*`。
- 不修改冻结域或他线所有文件，除非最新派单明确授权。
- 不把尚未具备消费面的组件伪装成完成；准备段与运行验收段分别回执。
- 前端回归按任务要求执行类型检查、Vitest 和构建；后端按任务要求执行 pytest 与必要的静态编译。

## 完成判定

只有同时满足以下条件才结束循环：

- mailbox/STATE 明确确认 Codex 无可开工、排队或待解锁任务；
- Codex outbox 无待消费交付或 ACK；
- 所有 Codex 票均有监督线验收或明确转交记录；
- 目标设计的实现、测试、验证和遗留项终态均有权威证据。

暂时没有新消息不等于库存为空。等待同一外部状态连续出现时按会话目标的阻塞审计规则处理；新派单到达即恢复本工作流。
