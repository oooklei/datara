## 1. 背景与问题

### 1.1 当前形态

**【实测】** 截至 `catalogHash=83929cf7c3c5c660`（2026-09-28 快照），系统内 7 个 ViewProfile 中 4 个声明了 `nodeTypes`，合计 **75** 个组件定义：

| Profile                       | 组件数 | executionModel  | 说明                      |
| ----------------------------- | --- | --------------- | ----------------------- |
| `dag`                         | 35  | `dag-engine`    | 真实执行（含 2 个 runtimeOnly 物化节点）|
| `etl`                         | 17  | `demo-only`     | 仅前端声明，后端无实现             |
| `stream`                      | 10  | `demo-only`     | 仅前端声明，后端无实现             |
| `topo`                        | 13  | `canvas-device` | 画布设备，设计上不执行             |
| `er` / `lineage` / `relation` | 0   | —               | palette-only，无 NodeSpec |

全系统无执行实现的组件共 30 个（dag 3 + etl 17 + stream 10）。DAG 引擎硬缺口 3 个：`stream_input`、`stream_fuse`、`stream_output`。（2026-09-26 校验加注：这 3 个类型在**流任务链路**（I11，`worker/stream`/`master` 流编排）另有真实执行实现；此处缺口仅指其在 **dag-engine 工作流内**不可执行，并非流能力整体缺失。）

### 1.2 三个结构性问题

1. **组件定义是硬编码的 TS 常量。** 75 个组件全部写死在 `src/graph/profiles/*.ts` 中，新增组件必须改代码、重新构建、重新部署。没有"设计"这个动作，因此也没有"设计者"这个角色。
2. **无版本概念。** 组件没有版本号。工作流节点只记 `nodeType` 字符串，因此无法回答"这个工作流用的到底是哪个版本的组件"、"升级组件会不会影响线上工作流"。
3. **声明与执行脱节的根因未消除**（本文记作 **GAP-30**；2026-09-26 更正：原引「G-14」系引用错位——DAG 规范文档 §10.2 的 G14 为「死代码/死常量」项，与本问题无关，大文档中无对应 G 编号）。历史上出现过"可声明、不可执行"的组件（声明了但后端没有对应实现）。当前通过 `executionModel` 显式标注了 30 个缺口，但**没有任何机制阻止新的缺口产生**——因为发布环节不存在。

### 1.3 本文档要解决的问题

| 问题             | 解决章节                  |
| -------------- | --------------------- |
| 谁有权新增、谁有权发布    | §14 RBAC              |
| 怎么保证声明的组件一定能执行 | §13 发布闸门              |
| 工作流怎么锁定组件版本    | §9 componentRef 冻结（已落地：R6 回填 + 物化器注入；红线 3 冻结语义待基线化后启用）|
| 拖入画布时发生什么      | §11 dropPolicy、§12 交互 |
| 组件下线了怎么办       | §8 状态机、§9.4 影响面       |

## 2. 设计目标与非目标

### 2.1 目标

- **G1** 组件可由用户在界面上设计并保存草稿
- **G2** 组件的发布必须通过机器可校验的闸门，杜绝 GAP-30 类"可声明不可执行"（§1.2.3）
- **G3** 工作流对组件的引用是版本冻结的，历史可复现
- **G4** 组件声明是纯数据（可 JSON 序列化、可 diff、可迁移）
- **G5** 全生命周期有审计记录，可回答"谁在何时发布了哪个版本"
- **G6** 组件下线、升级、回滚有明确语义，不静默影响线上工作流

### 2.2 非目标（明确不做）

- **N1** 不做用户自定义执行器。MVP 仅允许绑定**既有** executor，不开放用户脚本、HTTP 节点、沙箱代码等新执行基础设施。
- **N2** 不做组件市场、跨租户分发、组件评分与推荐。
- **N3** 不改造 dag-engine 执行引擎本身。本设计只约束"什么可以被发布"，不改变"怎么执行"。
- **N4** M0/M1 不引入数据库迁移框架（仓库当前无此依赖，见 §17）。
- **N5** 不做组件的可视化拖拽式编排（组件内部逻辑），M1 的表单只声明**元数据与表单字段**。

## 3. 红线（原三条；红线 3 已移出，待基线化后启用，见文末注）

以下红线为不可协商约束，任何实现方案若违反则不予合入。

### 红线 1：发布时必须绑定真实执行契约

**任何进入** **`published`** **状态的组件，必须能证明它可以被执行。**

- `executionModel = dag-engine` → 必须声明非空 `executor`，且该 `executor` 必须在既有 dispatcher 注册表中真实存在
- `executionModel = canvas-device` → 必须显式声明 `executable = false`，允许发布（画布/可视化节点，设计期产物，运行期不执行）
- `executionModel = demo-only` → **禁止发布**

依据：GAP-30（§1.2.3）。**【实测】** 现有 30 个 `demo-only`/缺口组件若流入发布态，等于原地重建该缺口。

### 红线 2：声明与 dropPolicy 必须是纯数据

组件声明（NodeSpec）与拖入策略（dropPolicy）必须可完整 JSON 序列化。

- 禁止函数、箭头函数、类实例
- 禁止 `eval`、模板字符串拼接出的代码、`new Function`
- 禁止在声明中引用后端模块路径、SQL 片段、脚本内容
- 允许的"动态"仅限**声明式引用**（如 `prefillFromUpstream: ["ds_id", "table"]`），由运行时解释，而非由声明提供实现

依据：`【实测】` 当前 NodeSpec 中有 5 个不可序列化函数字段（`FieldSchema.showIf` / `onChange` / `text`、`NodeSchema.summary` / `ports`）。这些是**存量事实**，M3 迁入库表前必须先消除或降级为纯数据表达式。

> 原红线 3「工作流节点必须冻结 componentRef」（禁止引用"最新版"、显式"升级到 vN"）已移出红线清单（2026-09-28）：组件管理与发布治理尚未基线化，该约束**待代码与功能基线化后再启用**；冻结语义（§9）保留为设计目标与 M3 迁库落位依据。

## 4. 概念模型与术语

| 术语                          | 定义                                   |
| --------------------------- | ------------------------------------ |
| **组件（Component）**           | 一个可被拖入画布的原子执行/交互单元，有唯一 `type`        |
| **组件版本（Component Version）** | 组件在某一时刻的**不可变**声明快照                  |
| **草稿（Draft）**               | 组件的可编辑工作副本，可反复修改，**无版本号**            |
| **NodeSpec**                | 组件的声明本体：分类、端口、变量、表单字段、校验规则           |
| **dropPolicy**              | 拖入画布时的行为策略，纯数据，见 §11                 |
| **componentRef**            | 工作流节点对组件的版本化引用 `{ type, version }`   |
| **executor**                | 既有执行器 handler 名，如 dag-engine 的注册 key |
| **发布闸门（Publish Gate）**      | 发布前必须全部通过的校验集合，见 §13                 |
| **内置组件**                    | `scope = builtin`，随代码发布，来源为 Git JSON |
| **用户组件**                    | `scope = user`，由用户在界面上设计，来源为库表       |
| **实测 / 提案**                 | 见文首标记约定                              |

### 5.1 真源演进

这是本设计最需要早确认的一点，否则 M3 会出现双真源冲突：

```
M0：  Git JSON (dag_catalog.json)  ──唯一真源──▶  导出器  ──▶  快照/只读 API
M1：  Git JSON (内置)  +  库表 (用户草稿)     ← 双真源，但按 scope 切分，互不重叠
M2：  同上，库表增加 published 版本
M3：  库表  ──唯一真源──▶  导出器  ──▶  dag_catalog.json（降级为构建产物）
```

**M3 的判据**：`dag_catalog.json` 不再被人工编辑，只由导出器从库表生成。届时 `--check` 语义从"防止手改"变为"验证库表与产物一致"。

**设计决策：版本一旦创建即不可变。** 改声明 = 新建版本。已发布版本的 `spec_json` 与 `spec_hash` 任何时候都不得 UPDATE。这是 §9 版本冻结的存储层保证。

## 8. 组件状态机（已落地）

```
                  freeze_version
                      │
                      ▼
    ┌──────────► draft ──────────┐
    │             │              │ publish (通过闸门)
    │             │ update_draft │              ▼
    │             │ (原地修改)   │         published ◄──── rollback
    │             ▼              │              │              │
    └────────── draft            │              │ offline      │
                                  │              ▼              │
                                  └─────────── offline ────────┘
                                  
                     archive（M3+ 预留，当前不实现）
```

| 状态          | 可编辑草稿     | 可被新工作流引用 | 可被既有工作流引用      | 可被发布     |
| ----------- | --------- | -------- | -------------- | -------- |
| `draft`     | 是         | 否        | 否              | 是（需闸门通过） |
| `published` | 否（需先新建草稿） | 是        | 是              | —        |
| `offline`   | 否         | **否**    | **是**（历史可复现优先） | 是（重新上线）  |

**关键语义：`offline`** **不阻断既有工作流运行。** 理由：可复现性优先于管控便利性（原红线 3 依据，该红线已移出清单待基线化后启用，§21 变更记录）。若 offline 会让线上工作流直接失败，那下线操作就是一个高危生产动作，需要额外的审批流，超出本设计范围。改为：offline 后禁止新引用，既有引用照常运行，同时提供 §9.4 影响面查询。

**设计决策：已发布版本不可编辑。** 修改流程是"新建草稿 → 冻结为新版本 → 发布"，不存在"直接改线上版本"。

## 9. 版本引用与冻结

### 9.1 componentRef 结构

**【提案】**

工作流 GraphDocument 的每个节点保存：

```json
{
  "id": "node_abc123",
  "type": "dag-shell",
  "componentRef": { "type": "dag-shell", "version": 3 },
  "label": "执行 Shell",
  "config": { "rawScript": "echo hi" }
}
```

`type` 保留在节点上是为了兼容现有渲染代码（大量位置直接读 `node.type`）；`componentRef` 是权威引用。两者必须一致，由 M1 的一致性校验保证。

### 9.2 禁止 latest 语义

工作流 JSON 中**不得**出现 `"version": "latest"`、`"version": null`、或缺省 `componentRef`。CI 与 API 校验均需拒绝。

**理由**：一旦允许 latest，组件一次发布就会静默改变所有既有工作流的行为，且这种改变在工作流自身的版本历史中不留痕迹。

### 9.3 升级语义

升级是**显式、逐工作流、留痕**的操作：

1. 用户在组件详情页查看"被引用情况"（§9.4）
2. 选择目标工作流 → 执行"升级到 vN"
3. 该工作流 `componentRef.version` 改为 N，**并产生一个新的工作流版本**（走 `t_wf_definition` 既有版本机制）
4. 组件 `published_version` 变更**不触发**任何自动升级

### 9.4 影响面查询

`GET /api/v1/components/{type}/impacted` 返回引用该组件的工作流清单：

- 工作流 code / name / 当前 release\_state
- 引用的 componentRef.version
- 与 `published_version` 的差距（是否落后）

用途：升级前评估、下线前评估。

### 9.5 迁移影响（重要）

引入 componentRef 后，**存量工作流的节点没有** **`componentRef`** **字段**。M2 需要一次回填：以各 Profile 当前的内置组件版本（视为 v1）回填所有存量节点。

**【实测】** 存量 DAG 工作流有 37 个 type 引用（含 3 个仅后端类型 `smoke` / `src_select` / `tgt_select`），需一并回填，否则 DAG 工作流将无法通过发布闸门。

### 9.6 物化产物与 componentRef（2026-09-26 校验补充）

端点合一后，工作流装载期由 `materialize_sync_exec` 物化 `sys_exec_*` 执行节点（md5 确定性 id 保 failover 幂等、assert 入边改写，见 DAG 规范文档 §2.11）。本设计对物化产物的裁定：

- 物化节点**不要求**设计态 componentRef——它是装载期派生产物，非设计态实体；工作流侧发布闸门对其豁免
- 物化器按被物化源组件（`endpoint_select` / `sync` / `file_sync`）的 published 版本**自动注入** componentRef 到物化节点，保证运行期可追溯「当时用的哪版组件」
- §9.5 回填脚本对 `sys_exec_*` 节点跳过（保持幂等）

### 10.2 字段白名单

**【实测】** 现有 27 个控件类型、17 个 `pick` 引用键。**【提案】** 声明中 `uiType` 与 `pick` 键必须落在白名单内，否则闸门拒绝。这样白名单是**可执行的约束**而非文档约定。

### 10.3 存量函数字段的处置

**【实测】** 当前 5 个不可序列化函数字段及其处置方向：

| 字段                     | 出现位置 | M3 迁库前的处置                                                                                                                                                                                                                                                    |
| ---------------------- | ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `FieldSchema.showIf`   | 字段   | 降级为声明式条件表达式（DSL），不迁函数                                                                                                                                                                                                                                        |
| `FieldSchema.onChange` | 字段   | **移出声明**，改为按 `uiType` 内建的行为                                                                                                                                                                                                                                  |
| `FieldSchema.text`     | 字段   | 同 `onChange`，内建                                                                                                                                                                                                                                              |
| `NodeSchema.summary`   | 节点   | 降级为纯文本或 `template` 字段                                                                                                                                                                                                                                        |
| `NodeSchema.ports`     | 节点   | **不能简单降级**（2026-09-26 更正）：`endpoint_select` 等组件的 `ports(data)` 按 baseMode 分型动态产出双具名口（`sourceRef`/`targetRef`），需**条件端口 DSL**（`showIf` 的端口版），复杂度等同 D2——已拆出为遗留决策 **D7**（§20.2）；**已裁定（2026-09-27）：listRef 镜像 DSL（§10.3.1）**，endpoint\_select 实为静态 outputs 不需 DSL |

**这是 M3 的前置阻塞项。** 红线 2 要求纯数据，因此这 5 处必须在 M3 之前完成降级。M1/M2 的用户组件不受影响——设计器只允许产出纯数据声明。其中 `ports` 因端点合一的动态双具名口需求复杂度最高，已拆出为遗留决策 D7（§20.2），M1 表设计应预留 `conditionalPorts` DSL 位以免 M3 返工。

#### §10.3.1 D7 裁定：conditionalPorts = listRef 镜像 DSL（2026-09-27，方案 A）

**【实测修正】** D7 拆出时的主要动机已被落地实现化解：端点合一 C37 `endpoint_select` 的 `sourceRef`/`targetRef` 实际为**静态** **`outputs`** **数组**（不随 baseMode 分型，下游按需引用，formLinkage 具名端口引用走同一渲染路径），不依赖 `ports(data)`。37 个 DAG type 中现存函数 `ports` 仅 3 处：`conditions`(C3)/`switch`(C4) 均为 `data.branches` 列表镜像（`{id: b.id, label: b.name}`），`assert`(C25) 为常量二元分支（通过/不通过）。消费点仅 2 处：DataNode 渲染（`ports?.(data) ?? outputs ?? []`）与分支完整性校验（仅对有 `ports` 的 schema 生效，端口空=「未配置分支」错误、逐端口连边缺失=警告）。

**【裁定】** conditionalPorts DSL 仅一种形态——**列表字段镜像**，不引入端口级 showIf（现存无此需求，YAGNI；未来如需，与字段 showIf DSL 同一 M3 项扩展）：

```json
"conditionalPorts": { "listField": "branches", "idKey": "id", "labelKey": "name" }
```

| 键           | 必填 | 语义                                           |
| ----------- | -- | -------------------------------------------- |
| `listField` | 是  | 端口列表镜像的声明字段（其值须为对象数组，对应 rows/branches 类表单字段） |
| `idKey`     | 是  | 行内端口 id 键（连线 `sourceHandle` 取值）              |
| `labelKey`  | 是  | 行内端口 label 键（画布端口徽标文案）                       |

运行时语义：`data[listField]` 逐行产出 `{id: row[idKey], label: row[labelKey]}`；字段缺失或非数组按空列表（沿用「未配置分支」校验语义）。**M3 迁库落位**：`conditions`/`switch` 函数 `portsOf` → conditionalPorts 声明；`assert` 常量分支 → 改静态 `outputs`（endpoint\_select 先例，迁库后 37 type 函数 `ports` 归零）；消费端以 `resolvePorts(schema, data)` 归一解析（函数 → conditionalPorts → outputs 优先级），分支完整性校验同口径切换，保证 assert 转 outputs 后校验语义不丢。闸门第 2 项（纯数据）同步增列：`conditionalPorts` 三键必填且字符串非空、不得与 `ports` 函数并存（用户组件设计器只产出该 DSL）。

## 11. dropPolicy 纯数据 DSL（提案）

**【提案】** dropPolicy 描述"组件被拖入画布时发生什么"。全部字段为枚举或模板字符串，禁止函数。

| 字段                    | 类型        | 取值                                             | 语义                                                                                                                                                                    |
| --------------------- | --------- | ---------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `snapToGrid`          | boolean   | `true` / `false`                               | 落点是否吸附网格                                                                                                                                                              |
| `autoName`            | string    | 模板，如 `"{type}_{n}"`                            | 自动命名模板，`{n}` 为序号                                                                                                                                                      |
| `prefillFromUpstream` | string\[] | 17 个 pick 键的子集                                 | 从上游节点预填哪些字段（**与 Inspector 既有 pick 机制的划界**，2026-09-26 校验补充：pick 是 Inspector 内沿上游**实时联动**取值，管表单期；prefillFromUpstream 是 drop 时**一次性快照预填**，管拖入期。两者并存、语义不同，同一字段可兼用，不构成双真源） |
| `autoConnect`         | object    | `{upstream, downstream}`，各取 `nearest` / `none` | 自动连边策略                                                                                                                                                                |
| `maxInstances`        | integer   | `0` = 不限                                       | 单个工作流内的实例数上限                                                                                                                                                          |
| `openInspectorOnDrop` | —         | **废弃**（2026-09-26 裁定：拖入必弹窗已成默认行为，此字段删除，见 §12）  | —                                                                                                                                                                     |

**约束**：

- 整个对象必须可 `json.dumps` 往返
- 不允许出现函数、表达式字符串、模板引擎语法（仅允许 `{type}` / `{n}` 这两个固定占位符）
- `prefillFromUpstream` 的每个键必须是 §10.2 白名单成员
- `maxInstances > 0` 时，超限应拒绝拖入并提示，而不是静默替换
- **upstreamMax 不属于 dropPolicy**（2026-09-26 校验补充）：输入引用数上限（`pick.upstreamMax`，缺省 1，现有 2/3/5 三档）随字段走（`NodeSpec.fields[].pick`），管的是「单字段可引用几个上游输出」；`maxInstances` 管的是「单工作流内同组件实例数」。两者治理域不同，勿混同（引用数语义见 DAG 规范文档 §2 Step6-R2）

**为什么需要** **`prefillFromUpstream`**：当前 75 个组件中大量存在"上一个节点选了数据源，下一个节点自动带上同一个数据源"的手工重复操作。声明式预填把这个模式变成数据，而不是散落在各组件的 `onChange` 回调里。

## 12. 表单设计器交互（2026-09-26 裁定修订：configure-first）

### 12.1 拖入弹窗三段式（用户裁定，原 sketch-first 提案作废）

**默认行为**：拖入组件 → **必弹模态窗口**（属性+配置参数设置）→ **校验通过后节点才落画布** → 右侧 Inspector 供拖入后修改。

- 校验不全（必填缺失/值域无效/引用无效）→ 确认按钮禁用并警示缺失项，**节点不落画布**（拖入无效）；取消/ESC → 节点消失
- 弹窗打开即执行 prefillFromUpstream（§11 划界语义）+ 上下文值域解析（数据驱动，见实施计划 F2/F3）
- 前置拦截：maxInstances 超限、offline 组件不弹窗直接 toast 拒绝
- 节点落画布即「已配置」态；Inspector 修改若破坏必填，走既有 W1 角标 + 保存闸门链

**理由（用户裁定）**：杜绝「先落一堆未配置节点再回头补」的失控画布；配置先行保证画布上每个节点都是有效的。

### 12.2 渲染复用（实现约束）

**弹窗表单与 Inspector 表单必须共用同一渲染组件**（Inspector 字段渲染抽为可复用件）——数据驱动值域过滤、校验、联动逻辑一处实现两处消费，禁止双实现漂移。`openInspectorOnDrop` 声明字段**废弃**（弹窗已是默认行为）。

### 12.3 前提条件

**渲染组件必须能渲染该 NodeSpec 的所有字段**（弹窗与 Inspector 同一组件，一条验收覆盖两处）。这条是 M1 设计器的硬性验收项：渲染能力必须覆盖 §10.2 全部 27 个控件类型，不能只支持子集后就开放拖入自定义组件。

## 13. 发布闸门（提案）

`POST /api/v1/components/{type}/publish` 必须按序通过以下全部检查，任一失败则拒绝且**不落 published 状态**：

| 序 | 检查项                                                                                                                         | 失败返回          | 依据              |
| - | --------------------------------------------------------------------------------------------------------------------------- | ------------- | --------------- |
| 1 | 调用者具备 `publish_component`                                                                                                   | 403 `NO_PERM` | 红线 / §14        |
| 2 | 声明为纯数据（可 JSON 往返，无函数/脚本/代码片段）                                                                                               | 422           | 红线 2            |
| 3 | 字段合法：`uiType` ∈ 27 控件白名单，`pick` 键 ∈ 17 键白名单                                                                                 | 422           | §10.2           |
| 4 | dropPolicy 合法：枚举值合法、模板占位符合法、无函数                                                                                             | 422           | §11             |
| 5 | **执行契约**：`demo-only` 禁止发布；`dag-engine` 必须有 `executor` 且该 executor 在 dispatcher 注册表中存在；`canvas-device` 必须 `executable=false` | 422           | **红线 1**        |
| 6 | 组件 type 不得与系统内置目录重名（方案 A 全局唯一，见 §15.3 重订）                                                                                   | 422           | §15             |
| 7 | 乐观锁：`draft_rev` 与请求携带值一致                                                                                                    | 409           | §16             |
| 8 | 引用完整性：声明中引用的外部实体（脚本库脚本等）必须真实存在                                                                                              | 422           | 2026-09-26 校验补充 |

**闸门第 5 项是本设计的核心。** 它把"是否有真实执行实现"从一个人工核对项变成了发布路径上的强制检查。**【实测】** 若该检查在 M0 时刻就存在，当前 30 个无执行实现的组件会有 27 个（etl 17 + stream 10）被直接拦下，dag 的 3 个 stream 缺口也会被拦下。第 5 项同时覆盖 `runtime-only` 节点（`runtimeOnly=true` 标记，如 `sync`/`file_sync`）：该类组件必须强制 `paletteVisible=false` 且只能被装载物化消费（见 DAG 规范文档 §2.11），不得以任何形式出现在设计态 palette。（2026-09-28 修正：`runtime-only` 不是 `executionModel` 第 4 值，而是独立的 `runtimeOnly` 布尔标记——`executionModel` 仍为 3 值：`dag-engine`/`demo-only`/`canvas-device`；runtime-only 节点的 executionModel 视其执行方式仍属 `dag-engine`，仅以 `runtimeOnly` 标记区分设计态可见性。）

**设计决策：闸门不可绕过。** 不提供 `--force`、不提供管理员豁免、不提供"先发布后补实现"。若未来确有例外需求，应作为独立议题重新评审，而不是加一个开关。

## 14. RBAC 权限（提案）

### 14.1 权限位

**【提案】** 在 `api/auth.py` 的 `ROLE_PERMS` 中新增两个权限位：

| 权限位                 | 含义              |
| ------------------- | --------------- |
| `design_component`  | 设计、保存组件草稿、冻结新版本 |
| `publish_component` | 发布、下线、回滚组件      |

### 14.2 角色矩阵

现有四角色 `admin` / `dev` / `analyst` / `viewer`，映射如下：

| 权限                  | `admin` | `dev` | `analyst` | `viewer` |
| ------------------- | :-----: | :---: | :-------: | :------: |
| 查看组件目录              |    Y    |   Y   |     Y     |     Y    |
| `design_component`  |  **Y**  | **Y** |     N     |     N    |
| `publish_component` |  **Y**  |   N   |     N     |     N    |
| `edit_definition`   |    Y    |   Y   |     N     |     N    |
| `run_instance`      |    Y    |   Y   |     Y     |     N    |
| `view_all`          |    Y    |   Y   |     Y     |     Y    |

变更后的 `ROLE_PERMS`：

```python
ROLE_PERMS = {
    "admin":   ["manage_user", "edit_definition", "run_instance", "view_all",
                "design_component", "publish_component"],
    "dev":     ["edit_definition", "run_instance", "view_all",
                "design_component"],
    "analyst": ["run_instance", "view_all"],
    "viewer":  ["view_all"],
}
```

**【实测】** 权限校验复用既有 `require_perm(perm)` 依赖，它在无权限时抛 `ApiError(NO_PERM, status_code=403)`。M1/M2 的新端点直接使用该依赖，无需新增机制。

### 14.3 依据

对应已确认的决策：**`dev`** **可设计但不可发布，`publish_component`** **由** **`admin`** **独占。** 理由是发布闸门第 5 项（执行契约绑定）是一个需要判断"这个组件将来会不会被执行"的决定，把它交给能改代码、能提交 MR、能对执行引擎负责的 `admin` 更合适。

**设计决策：不做组件级的 ACL。** 当前只有 `dev` / `admin` 两类参与者，组件可见性由角色而非组件粒度控制。引入 ACL 需先回答"谁可以看别人设计的组件"，本阶段不预设答案。

## 15. type 全局唯一性策略（提案 · 决策记录）

### 15.1 问题

**【实测】** `op_script` 在 `etl` 与 `stream` 两个 Profile 中**重复定义**，两份内容一致。当前风险是**静默同步漂移**（改了一处忘了另一处），而不是语义冲突。

组件引入 `componentRef` 后，type 成为引用主键，重名会带来歧义：`componentRef: {type: "op_script", version: 2}` 指向哪一份？

### 15.2 两案对比

| 维度      | 方案 A：禁止重名                                | **方案 B：允许重名 + 内容一致**          |
| ------- | ---------------------------------------- | ----------------------------- |
| 规则      | 全局 type 唯一                               | 同 type 的所有定义必须 `spec_hash` 一致 |
| 破坏性     | **高**：`etl` / `stream` 的 `op_script` 需改名 | **无**：现状已满足                   |
| 存量工作流影响 | 改名需重写所有引用 `componentRef`，并产生新工作流版本       | 无                             |
| 漂移防护    | 结构性消除                                    | 由 CI 守卫（§15.4）                |
| 未来真冲突   | 天然支持同名不同义（通过命名区分）                        | **不支持**，需先改 A                 |
| 实施成本    | 改名 + 引用回填 + 回归                           | 加一条 CI 断言                     |

### 15.3 决策（2026-09-27 核查修订：原「采纳方案 B」已废止）

**实际落地为方案 A（禁止重名，全局唯一）。**

原 §15.3 提案采纳方案 B，理由是「当前唯一重名内容一致，方案 A 为不存在的问题付破坏性成本」。实施阶段权衡后改采方案 A，代码证据：

| 落点                                               | 事实                                                                          |
| ------------------------------------------------ | --------------------------------------------------------------------------- |
| `datara-backend/common/models.py:516`            | `type` 列 `unique=True` —— 全局唯一由**存储层**结构性保证，不依赖应用层校验                        |
| `datara-backend/api/component_design.py:514-516` | 发布闸门第 6 项 `hash_consistency`：组件 type 命中系统内置目录即 422 拒绝，消息为「同名定义一致性无法证明，拒绝发布」 |

改采 A 的代价与理由（复核后认为 A 的破坏性成本可控）：

1. **重命名面极小**：全仓唯一的跨 Profile 重名是 `op_script`（`etl` / `stream` 两份）。组件表 `t_component` 为 M1 新建，**存量库无组件数据**；存量工作流记的是节点 `type` 字符串，`op_script` 保持原名即可被 `t_component` 一条记录吸收（`profile` 字段允许多值语义待 D5 收敛）。
2. **A 消除的是歧义本身**：方案 B 的「重名必须 `spec_hash` 一致」是一条**持续性约束**，需要 CI 守卫 + API 校验 + 迁移合并三件套共同维持，任一环节漏掉就退化为静默歧义；而 `componentRef: {type, version}` 以 type 为引用主键，结构上不该存在二义性。
3. **闸门第 6 项本就是保守拒绝**：`run_publish_gates()` 落地时已按 A 实现，文档不同步才是缺陷源。

**本节与 §13 闸门第 6 项口径统一为方案 A。** 任何重走方案 B 的提议须单独立项，并同时完成 §15.4 全四项落地，不得隐式切换。

## 16. 并发与乐观锁（提案）

**【提案】** 组件草稿采用**乐观锁**，字段为 `t_component.draft_rev`。

- 每次保存草稿：`draft_rev += 1`，请求须携带读取时的 `draft_rev`
- 不匹配 → 409 `COMP_LOCK_CONFLICT`，返回当前服务端版本供前端 diff
- **仅在保存草稿与发布时校验**，不做编辑过程中的实时锁

**理由**：不做悲观锁。组件设计是低频、长耗时、可能持续数分钟的操作，悲观锁会导致"张三开着编辑器去开会，李四无法编辑"的体验问题。乐观锁在冲突时提示用户合并，符合此类操作的特征。

**设计决策：草稿内容不进** **`t_component`** **表。** 草稿保存在 `t_component_version` 中 `state = draft` 的那一条（或独立草稿存储）。主表只存身份与状态。这样"主表无 spec"与"版本不可变"两条约束不会互相打架。

## 17. 数据库落地方式（提案）

**【实测】** 仓库无独立数据库迁移框架。`common/db.py` 依赖 SQLAlchemy 2.0，通过 `Base.metadata.create_all` 建表，并用 `_ensure_column` 做列补丁。

**【提案】** M1 的 `t_component` / `t_component_version` / `t_component_log` 沿用同一机制：

- 首次启动 `create_all` 自动建表
- 后续新增列通过 `_ensure_column` 补丁
- **不引入 Alembic 等迁移框架**（对应非目标 N4）

**风险与缓解**：该机制适合"加表加列"，不适合"改类型 / 删列 / 大数据量回填"。M1 阶段表是空的，回填 §9.5 的 `componentRef` 是唯一的数据迁移操作，需单独脚本并可重复执行（幂等）。

### 18.4 错误码

**【实测】** 现有 `common/resp.py` 采用符号常量 + `ApiError(code, status_code=...)`。M0 已使用 404（未知类型）与 409（仅后端类型）。

## 22. 基线化阶段（2026-09-28 立项）

> 设计定稿：[组件基线化与逐组件发版设计.md](./组件基线化与逐组件发版设计.md)；执行台账：[组件基线化/README.md](./组件基线化/README.md)

### 22.1 与本设计的分工

- 本文 M3 一次性迁库**改道**为「逐组件基线化即入库」：不再批量迁移内置组件，而是按 DAG type 逐个走五步循环（语义分析 → **用户确认规格** → 实现 → 1.9 真实数据流实测 → 用户在工作台点「认可发 v1」）。
- 认可动作写入治理三表：`t_component(scope=builtin)` + `t_component_version(v1, published)` + `t_component_log` 审计——本文的表结构（§7）、状态机（§8）、乐观锁（§16）、审计（§7.3）全部复用，不另起炉灶。
- v1 发出前 `t_component` 无行：发版前进度独立承载于 `t_baseline_progress`（type 唯一 / status / draft_spec / draft_rev / check_report / test_records / confirmed_by / confirmed_at）。

### 22.2 三态生命周期

未基线化 unbaseline（代码声明，自由删改可重建）→ 基线化中 baselining（工作台底稿 + `t_baseline_progress`，设计器可改）→ 已基线化 baselined（v1 published，**本设计全套治理语义自此生效**）。「用户认可」是治理基础的唯一来源。

### 22.3 闸门降级为体检清单（阶段例外）

基线化期间 D1 八项发布闸门降级为**体检清单**：逐项 ✓/✕ 报告、不拦截，问题留用户裁决；体检结果随认可动作落 `check_report`。组件经认可发 v1 后：发布闸门恢复硬拦截、componentRef 冻结（原红线 3）恢复、已发版不可直接编辑（§9 冻结语义启用）。

### 22.4 表单声明（八段 DSL）

基线化组件声明采用**八段骨架**（inputs / outputs / params / conditions / constraints / exclusions / refs / exports，纯数据，随版本冻结），条件可见性以声明式 conditions 表达——既有 `FieldSchema.showIf / onChange / text` 三个不可序列化函数字段（§10.3）随逐组件重设计**逐组件消灭**，M3 序列化前提由基线化自动完成。血缘声明 `spec.lineage.assets`（§5.4 预留位）随 spec_hash 一并冻结。
