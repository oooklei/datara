# 项目 33 电商核心业务仿真基线

此目录是可复核的业务 SQL 资源源文件；2026-10-30 通过 Datara 资源上传 API 写入 1.9 项目 33。退款与库存脚本为版本 1；订单支付脚本因日批样本日期修正为版本 2。当前三份文件的 SHA-256 与各自最新资源版本的 digest 完全一致。

| 资源 | 业务检验 | DBX 源连接 | 只读执行结果 |
| --- | --- | --- | --- |
| `ecom_order_payment_reconciliation.sql` | 订单到支付的日汇总对账 | `datara-mysql-src` | 2026-10-14：2,777 单、订单额 27,635,199.79、关联支付额 62,370,434.19、1,243 单无支付；无截断 |
| `ecom_refund_overpayment_check.sql` | 退款总额超过已付金额的异常订单 | 同上 | 100 行、4 列，无截断；脚本含 `LIMIT 100` |
| `ecom_inventory_safety_check.sql` | 仓库低于安全库存与负库存数量 | 同上 | 5 行、4 列，无截断 |

这三份 SQL 已直接通过 DBX 0.6.60 `/api/query/execute` 只读实测。日期和库存阈值在 SQL 中固定为当前源数据快照值；注释标明其对应的项目变量。资源管理目前只保存 SQL 文件，尚未证明从资源到 DBX 的变量替换和一键运行链路，因此不把这些文件的存在记为脚本开发端到端完成。

同批次通过 Datara 变量 API 写入项目级 `biz_date`、`source_schema`、`warehouse_schema`、`settlement_currency`、`quality_max_failure_rate`、`order_batch_size`、`refund_sla_hours`、`inventory_safety_stock`，描述均带 `[ECOM-SIM-20261030]`。业务日期初设 2026-10-22；发现该日仅 1 条订单后，修正为最近的完整日批 2026-10-14（2,777 条订单、2,271 条支付、166 条退款）。既有 `${global.biz_date}=2026-10-28` 保持原值；源库和质量阈值的项目作用域解析也已确认。数据由同一仿真标记识别，后续清理临时验证数据时应保留。

项目中既有的 `_clean_cross.py`、`test-upload.sql`、`smoke_check.sh` 等资源未删除：当前没有足够的归属证据证明它们属于本轮临时验证数据。

治理目录同批次新增 5 个项目标签（订单、支付、退款、库存、个人信息），其中订单与个人信息标签挂载到现有 `ec_retail.ods_order` 资产 #16；新增 4 项标准和 4 项指标定义，均保留 `draft` 状态。支付金额与退款金额分列，不把二者相减后直接称为确认收入；金额精度与业务日期标准在财务口径确认前同样保留草稿。这些定义使目录可用于业务讨论，但没有执行引擎结果，不能视为指标验收通过。

随后从 `ec_retail` 元数据与实际行数建立 5 个项目资产：`dim_user`（11 字段、60,002 行）、`dim_supplier`（7 字段、1,501 行）、`ods_payment`（6 字段、200,002 行）、`ods_refund`（5 字段、15,000 行）、`dim_inventory`（5 字段、20,000 行）。另增会员、供应商两个标签，并将对应业务与敏感度标签挂到上述资产。原有 `ods_order` 资产 #16 仍缺字段元数据，这是既有目录缺口，尚待通过可审计的资产更新接口修正。

截至本轮只读核对，项目 33 为 8 个资产、7 个标签、4 项标准草稿、4 项指标草稿、3 条旧质量规则、0 条质量运行、10 个资源、11 个项目变量。质量运行保持空白，因为现网规则绑定错误且仍只执行结构校验；不能为填充界面制造 0 行的伪运行。新增资源、变量、资产及目录定义均经正式 API 写入；原有测试资源未删。
